## `requirement-reviewer` への入力

- 入力: レビュー対象そのもののパス。候補レビューでは `要件契約候補` そのものを渡し、候補内容を別の入力ファイルへ複製してはならない。派生レビューでは固定済み `要件契約` と、そこから派生したレビュー対象そのものを渡す。各入力対象のパスは直接読める状態で渡し、宣言済み参照は入力対象を起点にたどって読む。
- 担当検査ID: 今回検査する `RR-OBL-<連番>` または `RR-CONTRACT-1`。`RR-OBL-<連番>` は、候補レビューでは候補の `固定した区別` と `伝播した拘束` の各項目、派生レビューでは固定済み `要件契約` 内の対応する項目に対応させ、親エージェントが付ける。加えた拘束が0件の候補では `RR-CONTRACT-1` だけとなる

## `requirement-reviewer` が必要な情報

- レビュー対象の構成は次のいずれか
  - 候補レビュー: 親エージェントが `context-clarification` の探索結果から作成した semantic patch 型の `要件契約候補`。`依頼引用` は必須、`固定した区別` と `伝播した拘束` は該当する内容がある場合だけ必要。各項目が存在する場合は、その項目の認可元・根拠への到達情報を含める。作業段階、未決事項・判断主体・戻り先を要求しない。基底にある要求を別表現へ写した完全集合を候補へ含めてはならない。加えた区別や拘束の列挙が空である（＝依頼引用だけの候補である）ことを入力不備として扱ってはならない。要件レビュー結果と `判定結果` を候補へ前倒ししてはならない。`依頼引用` は依頼本文と後続の訂正・追加・選択の逐語引用だけとし、後段が会話の記憶なしに現在の拘束へ到達できる状態で候補内に保つ。指示対象を解決した表現へ言い換えてはならない。解決した指示対象は、加えた拘束として置く。
  - 派生レビュー: 固定済みの `要件契約` と、そこから派生した仕様または作業契約。依頼引用、契約の認可元と根拠へ到達できるもの
- 各拘束または検査が認可元・根拠・情報所有先に依存するときは、候補レビューでは候補から、派生レビューでは固定済みの `要件契約` または派生レビュー対象から一意に到達できること。必要な参照が入力対象にない場合は、参照欠落として検査対象とする。宣言した参照の実体は、レビュワーが入力対象を起点にたどって直接読める状態でなければならない。
- 各担当検査が直接読む参照は、その条項または検査が依存し、かつその条項または検査が宣言した参照先に限る。リポジトリ根拠、外部一次資料、テスト、コマンドは、その依存がある場合に限り直接確認する。
- 契約が自然言語を対象とするときは、その対象部分、正本、保つ意味、意味の欠落やずれを判断する基準、利用経路を担当検査から直接たどれるようにする。
- 検査条件と共通出力形式は専用エージェント定義に含まれるものを使い、レビュー対象を起点にたどれる宣言済み参照以外の入力を追加しない。
