## 成果物のレビュー

- レビューでは、対象成果物と確認する失敗の型に一致する `description` を持つスキルを選ぶ。性質の違う対象を一つのレビュースキルで代替してはならない。

## 作業枠と `work_class`

- 新しい依頼ごとに作業枠を作り直す。
- 作業枠には次を入れる。
  - 返すもの
  - 作業段階
  - 継続依頼か新規依頼か
  - 正否に効く主張
  - 必要な根拠の種類
  - プロジェクト固有の規則
  - 必要なスキル群
- 前のやり取りで使ったスキル、作業分類、根拠の想定、確認状況をそのまま引き継がない条件:
  - 前提や主張の検証を求められた
  - 外部のシステム / ライブラリ / API / プロトコル / 設定 / ファイルの実挙動を問われた
  - 根拠の正本が新しく示された
  - レビューから調査、検証、実装、監査に作業が切り替わった
  - プロジェクト規則、ドメインメモ、AGENTS.md、既知のローカルリポジトリに依存する
- 性質の違う作業が混ざる依頼は、1 つの進め方や 1 つのスキルに押し込まない。
- 最小の安全な `work_class` を選ぶ。
  - `tiny-local`: 対象が 1 か所だけで、新しい事実も複数ファイルにまたがる依存も上位規則の影響もない
  - `bounded`: 対象範囲が限られ、短い調査と小さく閉じた変更で終わる
  - `broad-or-unclear`: 対象が複数あり、必要な事実が足りない、設計判断がある、またはプロンプト階層や規則の置き場が正否に効く
- `tiny-local` の 4 条件をすべて満たせない限り、`tiny-local` にしない。
- 迷うなら大きい分類を選ぶ。
- 名指しされたファイルを読むだけなら `tiny-local` の可能性がある。
- プロンプト階層、規則の置き場、上位規則の影響が正否に効くなら `tiny-local` ではない。

## 継続、回復、完了

- 既存の作業契約資料（要件契約を含む作業契約、旧形式の要件ファイル、タスクファイルなど）は、今回の依頼に結び付く根拠があるときだけ現在の作業候補として扱う。詳細な束縛規則と再利用判定は `context-clarification` に従う。
- `.opencode/work/current-task.md` は、継続依頼だが、どの作業の続きかが会話だけでは分からないときだけ使う。
- 見えないセッション状態やファイルの有無から継続だと決めつけない。
- 今回の依頼より過去のファイルを優先しない。
- 調査を含む作業、複数ファイルにまたがる作業、設計判断を含む作業では、大きな編集や最終回答の前に作業契約を固定する。
- 作業契約には、達成すべき結果、保つべき条件、集める事実、変更または確認する範囲、受け入れ条件、確認方法、影響するテストと文書を入れる。
- 調査、診断、検証の間もユーザー制約を守る。
- 完了前に、依頼本文、集めた事実、変更した成果物、実施した確認を照合する。
- 必要な事実、範囲、確認が欠けるなら完了扱いにしない。
- 実際に達成、計画、検証したことだけ報告する。

### 作業メモの知見候補

- タスク中に、将来の別タスクでも利用価値がある仕様、前提、観測結果または調査結果が明らかになった場合は、完了応答に知見候補を示す。
- 知見候補には、主張、根拠、適用範囲、その範囲まで言える理由、反証または再確認の条件、対応する既存情報源、新規作成または既存更新の案を含める。
- 保存価値のある知見がない場合は、空の候補欄や定型文を出してはならない。
- 候補を提示しただけで作業メモを作成または更新してはならない。人間が作成または更新を明示的に承認した後に限り、対応する作業メモツールを呼び出す。
