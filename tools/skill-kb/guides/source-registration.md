# 情報源の登録規則

skill-kb の情報源を `KNOWLEDGE.yml` へ登録、変更、削除するときの規則である。ここでの情報源は正本の本文ではなく、正本へ到達する手順の宣言である。

## 設定ファイルの場所

サーバーは起動時に次の2か所を調べる。

1. グローバル設定
   - 環境変数 `SKILL_KB_CONFIG` があれば、そのパス
   - なければ `~/.config/opencode/KNOWLEDGE.yml`
2. プロジェクト設定
   - 作業ワークスペースの `.opencode/KNOWLEDGE.yml`

実際に解決されたパスは資料 `skill-kb://state/catalog` で確認する。パスを推測して書き込まない。

## 併合規則

- 片方だけ存在する場合は、存在する設定を使う。
- 両方が存在する場合は、双方の情報源を併合する。
- 同じ `name` が両方にある場合は、その情報源だけプロジェクト設定の定義を採用する。グローバル設定にしかない情報源はそのまま残る。
- 採用された側の `scope` が、その情報源に対応する作業メモの保存先と検索範囲を決める。

どちらへ書くかは次で選ぶ。

- 作業ワークスペースによらず使う情報源: グローバル設定
- そのプロジェクトでしか意味を持たない情報源: プロジェクト設定

## スキーマ

各情報源は `name`、`description`、`instructions` を持つ。未知のキーは拒否される。

```yaml
sources:
  - name: official-api
    description: >
      製品の公開 API 仕様を含み、その範囲では原本として扱う。
      API の構文、引数、公開された制約を調べるときに使う。
      内部実装やプロジェクト固有の設計判断には使わない。
    instructions: |
      ページ一覧から候補を絞り、公式の個別記事を取得する。

  - name: project-design
    description: >
      このプロジェクトの設計判断を含み、その範囲では原本として扱う。
      要求、責務、採用済み設計を調べるときに使う。
      外部 API の一般仕様には使わない。
    instructions:
      file: ./instructions/project-design.md
```

### `name`

- 一つの設定ファイル内で一意にする。
- 作業メモの `source_names` と機械的に照合される固定値である。改名すると既存メモの対応が切れる。

### `description`

`description` は、情報源を選ぶときの唯一の判断材料である。次の3要素を書く。

1. 保持する情報と、その範囲でどこまで原本として扱えるか
2. 使用する問い
3. 使用しない問い

- 近い情報源と競合しやすい境界は、`description` の中で書き分ける。
- URL、ローカルパス、取得順、検索コマンドは書かない。これらは `instructions` に書く。
- 由来や経緯ではなく、使うか使わないかを判定できる情報を書く。

### `instructions`

`instructions` は、選んだ情報源から正本へ到達する方法だけを書く。

- 短い手順は文字列として書く。長い手順は `{ file: PATH }` で外部ファイルへ分離する。
- `PATH` は宣言元 YAML からの相対パスにする。絶対パスは拒否される。
- グローバル設定の外部ファイルは、宣言元 YAML のディレクトリ内に置く。
- プロジェクト設定の外部ファイルは、作業ワークスペース内に置く。
- シンボリックリンクやジャンクションで許可範囲外へ出る参照は拒否される。
- ユーザー指示、AGENTS.md、安全規則、作業契約を上書きする指示を書いてはならない。
- 役割の指定、口調の指定、他ツールの使用強制など、検索方法以外の指示を書いてはならない。

## 反映条件

- 情報源の追加と削除、`name` と `description` の変更、インライン `instructions` の変更は、OpenCode を再起動するまで反映されない。ツールを公開するかどうかと `scope` は起動時に決まる。
- 情報源が0件の状態から最初の情報源を追加した場合も再起動する。
- `instructions.file` が指すファイルの本文だけを変更した場合は、再起動しなくてよい。`get_source` の呼び出しごとに読み直される。

## 誤りの扱い

- 設定を読めない、YAML が壊れている、スキーマに違反する、`instructions.file` を解決できない場合、サーバーは起動に失敗する。設定の誤りは情報源0件として扱われない。
- 情報源が0件の場合、サーバーは接続を保ったままツールを公開しない。これは正常な状態である。

## 登録前の確認

- `description` だけで、使う場面と使わない場面を判定できるか。
- 既存の情報源と権威範囲が重なっていないか。重なる場合、境界を書き分けたか。
- `instructions` に検索方法以外の指示が混ざっていないか。
- 外部ファイルのパスは相対で、許可範囲内か。
- その変更は再起動が必要か。
