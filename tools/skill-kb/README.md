# skill-kb

`skill-kb` は、設定された情報源の選択、候補検索、正本へ到達する検索方法を提供し、情報源に対応する作業メモを扱うローカル MCP サーバーである。`get_source`、`query_source`、作業メモ用の4ツールを公開する。情報源の登録規則は `instructions` と resource として公開する。

## 必要な環境

- Node.js 26
- npm 12
- ローカル stdio MCP を利用できる MCP クライアント

依存導入、型検査、ビルド、試験は、このディレクトリで順に実行する。

```powershell
npm ci
npm run check
npm run build
npm test
```

## 情報源登録規則

情報源の登録、変更、削除に使う規則は [`guides/source-registration.md`](guides/source-registration.md) にまとめている。この本文をMCP resource `skill-kb://guide/source-registration` として公開し、情報源が0件の状態でも読めるようにする。接続時の使い方は [`guides/server-instructions.md`](guides/server-instructions.md) に書く。

## 設定層と候補検索

グローバル設定、隣接する `KNOWLEDGE.local.yml`、プロジェクト設定、隣接する `.opencode/KNOWLEDGE.local.yml` の順に、同じ `name` のフィールドを上書きする。通常の設定には環境に依存しない値を置き、環境依存の値は local 設定の `query_options` などへ置く。詳細なスキーマとパス規則は登録規則を参照する。

`query_module` を持つ情報源は `query_source` で候補検索できる。モジュールの named export `query` は、問いと `query_options` を受けて `Promise<string>` を返す。`query_source` の結果は正本の引用ではない。

## 情報源が0件のときの挙動

設定が1か所も見つからない場合、見つかった設定の `sources` が0件の場合、または全ての情報源が設定不成立で除外された場合は、情報源0件として扱う。これは正常な状態である。サーバーは接続を確立したまま稼働し、どのツールも公開しない。作業メモは一つ以上の現在有効な情報源へ対応づけるため、対応先を検証できない状態では作業メモツールも公開しない。起動時に標準エラーへ、情報源が未設定であること、探索した設定のパス、設定不成立の診断を出力する。

YAML の構文が壊れている場合は起動に失敗する。YAML として読めるが設定全体または個別の情報源が不正な場合は、MCP サーバーを停止せず、不正な情報源だけをカタログから除外して診断を出力する。

## 作業メモ

作業メモは、作業中に明らかになった暗黙の前提、未文書化の観測結果、再調査に費用がかかる調査結果、再利用できる探索経路などを残す低権威の補助情報である。正式な仕様、設計資料、公式資料、現在のコード、ユーザーの現在の明示判断より権威が低い。

作業メモと正本が矛盾する場合は正本を優先する。重要な判断へ利用する前に、メモの根拠、適用範囲、反証条件、再確認条件を現在の状態へ照合する。作業メモを根拠として正式な情報源を自動更新しない。

### 保存までの流れ

タスク中に将来の別タスクでも利用価値がある知見が明らかになった場合、完了応答で「知見候補」を提示する。候補には、主張、根拠、適用範囲、その範囲まで言える理由、反証または再確認の条件、対応する既存情報源、新規作成または既存更新の案を含める。保存価値のある候補がない場合は、空の候補欄を出さない。

候補の提示だけでは作業メモを作成または更新しない。人間が作成または更新を明示的に承認した後に限り、`create_work_note` または `update_work_note` を呼び出す。

### 情報源との対応

各メモの `source_names` は、現在の統合済みカタログに存在する情報源名を一つ以上持つ。この対応は、どの情報源を調査するときにメモを検索するか、将来どの正式資料への反映を検討できるかを示す。自由なタグや分類階層ではない。作業メモ自体を `KNOWLEDGE.yml` の独立情報源にはしない。

一つのメモを複数の情報源へ対応づけられる。同じ名前の情報源がグローバル設定とプロジェクト設定の両方にある場合は、統合済みカタログで採用された側の `scope` を使う。

### 保存場所と検索範囲

保存先は、対応する情報源の最も狭い範囲で決まる。

- 全ての対応先がグローバル情報源の場合: `~/.local/share/chezmoi/.opencode/work-notes/`
- 一つでもプロジェクト情報源を含む場合: `<workspace>/.opencode/work-notes/`

一つのメモを両方へ複製しない。現在見えるグローバル保存先とプロジェクト保存先の間では、`file_name` を一意にする。

検索範囲は次のとおりである。

- グローバル情報源: グローバル保存先と現在のプロジェクト保存先
- プロジェクト情報源: 現在のプロジェクト保存先だけ

これにより、グローバル情報源だけに関するメモは作業ワークスペースによらず再利用でき、プロジェクト情報源を含むメモは無関係なワークスペースへ混入しない。作業メモの保存先は `get_source` が返す正本の検索対象と分離され、作業メモツールを通した場合だけ参照される。

### Markdown形式

一つの作業メモを、一つの YAML フロントマター付き Markdown ファイルとして UTF-8 で保存する。ファイル名をメモの識別子として使う。

```yaml
---
source_names:
  - source-documents
created_at: 2026-07-30T07:00:00.000Z
updated_at: 2026-07-30T07:00:00.000Z
---
```

本文は次の節を持つ。

- 表題
- 主張
- 根拠
- 根拠から主張を導ける理由
- 適用範囲
- この適用範囲とした理由
- 反証条件
- 再確認条件

実験、実行結果、計測、再現操作に基づくメモには「観測・再現情報」も加える。対象、対象版または commit、実行環境、前提条件、方法、入力、観測結果を記録し、必要に応じて生の成果物、反復状況、既知の限界を加える。観測結果には実際に確認した内容を書き、主張には観測から導いた解釈または一般化を書く。観測情報を指定しない場合は空の節を生成しない。

### `create_work_note`

人間が保存を明示的に承認した知見を、新しいメモとして保存する。

- `source_names`: 現在のカタログに存在する情報源名の配列
- `file_name`: メモの識別子となる安全な `.md` ファイル名
- `title`: 表題
- `claim`: 将来の判断へ利用する主張
- `evidence`: 主張を支える追跡可能な根拠
- `reasoning`: 根拠から主張を導ける理由
- `scope`: 主張を適用できる範囲
- `scope_basis`: その範囲まで一般化でき、それより外へ広げない理由
- `defeaters`: 主張を撤回すべき反証条件
- `revalidate_when`: 根拠を再確認すべき変化
- `observation`: 観測・再現情報。観測に基づかない場合は省略する

存在しない情報源、危険なファイル名、絶対パス、ディレクトリ区切り、同名メモの再作成を拒否する。作成日時と更新日時はサーバーが付与する。

### `update_work_note`

人間が更新を明示的に承認した既存メモを更新する。呼出し前に `read_work_note` で現行全文を確認する。本文項目は `create_work_note` と同じで、更新理由を示す `change_reason` を追加する。

作成日時を維持し、更新日時を変更する。更新前の全文は、現在の保存先にある `.history/<file_name>/` へ退避する。履歴は通常検索の対象にせず、各版に残る更新理由とともに後から棚卸しできる。更新中の不完全な内容を現行ファイルとして残さない方法で置換する。

更新では対応する情報源を変更しない。`source_names` は現行メモと同じ集合を指定し、異なる対応先への変更は拒否する。存在しないメモは作成せず拒否する。作成と更新を兼ねる `upsert` は行わない。

### `grep_work_notes`

`source_name` で指定した情報源に対応する現行メモの YAML フロントマターと Markdown 本文を、`pattern` に指定した TypeScript／JavaScript の正規表現で検索する。返すのは固定順序のファイル名だけであり、一致行、抜粋、要約は返さない。メモを利用するときは `read_work_note` で全文を読む。

無効な正規表現はエラーにする。一致なしは正常な空結果として返す。返却は100件を上限とし、超過時は `truncated: true`、`total_match_count`、`returned_match_count` と、パターンを絞る案内を返す。

### `read_work_note`

`source_name` と `file_name` を指定し、その情報源に対応するメモの Markdown 全文を省略せず返す。対応しない情報源、不正なフロントマター、危険なファイル名は拒否する。返却結果には、作業メモが正本ではなく、重要な利用前に根拠の再確認が必要であることも含める。

## MCP クライアントへの接続

ビルド後の `dist/src/index.js` をローカル MCP として登録する。`command` のスクリプトパスは実環境の絶対パスへ置き換える。

```json
{
  "mcp": {
    "skill-kb": {
      "type": "local",
      "command": [
        "node",
        "C:\\absolute\\path\\to\\tools\\skill-kb\\dist\\src\\index.js"
      ]
    }
  }
}
```

既定以外のグローバル設定を使う場合は `environment` を追加する。

```json
{
  "environment": {
    "SKILL_KB_CONFIG": "C:\\absolute\\path\\to\\KNOWLEDGE.yml"
  }
}
```

`cwd` は指定しない。MCP クライアントは、作業ワークスペースでサーバーを起動し、プロジェクト設定をそのワークスペースから解決する。

## 変更の反映

- 情報源の追加・削除、`name`、`description`、`instructions`、`query_module`、`query_options` の変更後は MCP サーバーを再起動する。情報源0件の状態から最初の情報源を追加した場合も再起動する。ツールを公開するかどうかと、情報源の `scope` は起動時に決まる。
- `KNOWLEDGE.local.yml` の追加、削除、変更も再起動する。
- `instructions.file` が参照するファイル本文だけを変更した場合は再起動しなくてよい。

## 既知の依存監査結果

`@modelcontextprotocol/sdk` 1.29.0 は、HTTP 静的配信に使う間接依存 `@hono/node-server` の中程度の脆弱性を npm 監査で報告する。`skill-kb` は stdio だけを使用し、HTTP サーバーと静的配信を登録しない。高重大度以上を対象にした `npm audit --audit-level=high` は成功する。
