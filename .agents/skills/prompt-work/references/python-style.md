# Python 風の指示の書き方

スキル本文を、AI が読む Python 風の指示として書くときの決まり。
本文を Python 風に書いたスキルを作成・編集するとき、自然文のスキルをこの形へ変換するときに従う。

Python の構文は、手順の順序、分岐、繰り返し、制約や前提の効く範囲、名前を使える範囲、判定の位置を表すために使う。実行するためのプログラムではない。
各手順の中身と判定の基準は、文字列の中に自然文で書く。
段階や手順の目的と理由は、コメントに書く。
構文を使うのは、自然文として読んでも同じ意味になり、`if` の行だけを見てその判定を確かめられる範囲に限る。
書いた本文は、検査スクリプト（`scripts/check_pystyle.py`）で、この決まりの形の上の違反を確かめる。調べる項目と調べない項目は、スクリプトの冒頭に書いてある。意味が意図や原文と合っているかは、このスクリプトでは確かめられない。

## ファイルの形

- `SKILL.md` は frontmatter で始め、その後に本文全体を 1 つの ```python のコードフェンスに入れる。Markdown の見出しや、フェンスの外の文は置かない。
- フェンスの中は、次の順に置く。
  1. 本文で使う補助関数の宣言（「補助関数」の文面と順のまま）
  2. 段階の外に置く名前の宣言（「`define` と段階の引数の書き方」）
  3. スキル全体の流れを表すメインの段階と、メインから呼び出しをたどって届く段階（「段階を置く順」）
  4. 末尾に、メインの段階を呼ぶ 1 行
- 段階の関数名は、その段階の節の名前として扱う。ほかの段階や手順から参照するときは、「段階の名前」の形で関数名を書く。
- 手順が引く表や一覧と、ほかの担当に読ませる資料は、参照資料に Markdown のまま置いてよい。置いた場合は、それを使う手順の `do` から、パスと節の名前で名指す。
- 本文を読んで進める者が行う順序、分岐、繰り返しは、参照資料に書かず、本文の構文で書く。本文の手順が使う用語の定義も、参照資料に出さず、本文に書く。参照資料は、手順が読むと書いた所でしか読まれないためである。

## 段階を置く順

- メインの段階を、段階の先頭に置く。
- その後に、メインから呼び出しをたどって、段階を初めて呼ぶ順に置く。たどるときは、呼ぶ側の本文に書いてある順に進み、呼んだ段階の中を先にたどってから、呼ぶ側の続きへ戻る。
- いくつもの段階から呼ばれる段階は、メインからたどる呼び出しの数がいちばん少ない呼び出し元の所に置く。その数が同じ呼び出し元がいくつもあれば、その中でいちばん先に置く呼び出し元の所に置く。
- `whenever` に渡す段階のうち、段階の外に定義するもの（「`whenever` の書き方」）は、この順に含めない。それを渡す段階のうち、いちばん先に置くものの直前に置く。その段階がメインなら、メインの直前に置く。メインより前に置く段階は、これだけである。同じ所に置くものがいくつもあれば、その段階が渡す順に並べる。
- `whenever` に渡す段階の本文は、渡した所に書いてあるものとして、順を数える。

## 補助関数

```python
def condition(prompt: str) -> bool: ...
def constraint(prompt: str): ...
def context(prompt: str): ...
def do(prompt: str): ...
def define(prompt: str): ...
def whenever(prompt: str, stage): ...
```

宣言は、そのスキルの本文で使う補助関数のものだけを、上の順に置く。
補助関数の意味は、名前と Python の構文の意味だけで表す。

- `condition` は判定
- `constraint` は守る制約
- `context` は前提として使う情報
- `do` は行う手順
- `define` は名前とその名前が指すものの宣言
- `whenever` はきっかけと、それが起きたときに行う段階である
- `with` の効く範囲は、Python の `with` と同じく、ブロックの中で呼んだ段階の実行中も含む。

名前と構文から読めない動作の決まりを、docstring などで足さない。足した決まりは実行する AI に守られるとは限らない一方、レビューでは厳密に当てはめられ、それを満たすための文が増える。

## 使う構文

- 段階: `def 段階の名前():` と、その呼び出し。呼び出し元の対象を受ける段階は、`def 指摘の原因を確かめる(指摘):` のように引数で受け、`指摘の原因を確かめる(指摘)` のように名前を渡して呼ぶ（「`define` と段階の引数の書き方」）。
- 名前の宣言: `成立した指摘 = define("…")`（「`define` と段階の引数の書き方」）
- 分岐: `if`、`else`（`elif` は使わない）
- 繰り返し: `while`、`for 指摘 in 成立した指摘:` の形の `for`
- 同じ手順をもう一度行うことは、`while` で書く。段階が、呼び出しをたどって自分へ戻る形（再帰）は使わない。
- `break`: 入れ子になったループの内側では使わない。抜けるのは一番内側のループだけなのに、文として読むと外側のループまでやめるように読めるため。
- 制約: `with constraint("…"):`
- 前提: `with context("…"):`
- 割り込み: `with whenever("…", 段階の名前):`（「`whenever` の書き方」）
- 効く範囲が同じ `context`、`constraint`、`whenever` は、`with (context("…"), constraint("…")):` のように一つの `with` に並べる。
- 手順: `do("…")`。参照資料を読むことも、パスを添えて `do` の文に書く。
- `if` と `while` の条件には、`condition("…")` と、それをつなぐ `and`、`or`、`not` だけを置く。
- コメント: `# …`。段階や手順の目的と理由を書く（「コメントの書き方」）。

`for` のループ変数は、文の中でその対象を指す名詞と同じ語にする。`for 指摘 in …` と書いたら、文では「その指摘」と呼ぶ。ループ変数を指せるのは、そのループの中だけである。
ループの対象の名前（`成立した指摘` など）は、その名前が指す作業中の対象を表す。

使わない構文は次のとおり。

| 構文                                                                              | 使わない理由                                                                                                                                                                                                 |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `return`                                                                          | 戻り先と、文中の「ユーザーへ返す」との違いが読めない。続きの処理は `else` に入れ、返す相手は `do` の文に書く                                                                                                 |
| `import`                                                                          | パスを書けない。2 回目以降は何もしない意味になる                                                                                                                                                             |
| `define` による名前の宣言以外の代入、段階の呼び出しに渡す名前以外の引数、f 文字列 | 条件の中身が代入した場所や呼び出し元へ移り、`if` の行だけで判定を確かめられなくなる。過去の事実は `condition("…した")` で表す。手順の結果も名前に代入しない。ほかの段階から使えず、`return` が要るようになる |
| リスト、辞書、クラス、例外                                                        | 自然文として読める範囲を超える。例外は、作業を止める意味になる                                                                                                                                               |
| docstring                                                                         | 指示として読まれるかが分からない。指示は `do`、`constraint`、`context` に、目的と理由はコメントに書く。補助関数にも付けない（「補助関数」）                                                                  |
| 段階が、呼び出しをたどって自分へ戻る形（再帰） | 戻り先が積み重なり、呼んだ側の `with` が呼んだ先にも掛かり、終わる条件が 1 行で読めない。繰り返しは `while` で書く |

## 文字列の書き方

- 補助関数に渡す文字列は、1 文なら 1 行に書く。長くても、途中で折り返さない。長い 1 文は、分けられる手順や制限が残っている目印になる。
- 2 文以上なら、三重引用符で囲み、1 文を 1 行に書く。段落を分ける空行は、そのまま残してよい。
- 文字列は二重引用符で書く。三重引用符の中の行は、文字列を始めた行より 1 段深く字下げし、閉じる引用符は、始めた行と同じ字下げに置く。
- 箇条書きを含む文字列は、三重引用符で囲み、項目ごとに行を分ける。整形スクリプトと検査スクリプトは、この文字列の行の分け方を調べない。
- 書き方は、整形スクリプト（`scripts/format_pystyle.py`）でそろえられる。

## `condition` の書き方

- 一つの `condition` には、判定を一つだけ書く。述語が複数あれば、`and` か `or` で別の `condition` に分ける。名詞句の中の「や」「・」は分けない。
- 判定する内容は肯定形で書き、否定は `not` で表す。名詞句の中の否定と、判定の基準を添える文はこの限りではない。
- `and` と `or` を混ぜるときは、必ず括弧を付ける。前提になる条件を左に書く。
- `condition` は、その後の手順を行うか行わないかを分ける問いである。何を問うか（判定の基準）は、その `condition` の文の中に書く。
- 答えを何で決めるかが分かるように書く。差分、ファイル、記録、ユーザー発言の文面のように、AI の外にあるもので答えが決まる判定は、見る先を文に書く。ただし、見る先を書き換えても、判定が狙いどおりに動くとは限らない。
- `condition` は、判定できないときも真か偽を返し、どちらになるかは決まっていない。書き方でこれを防ぐことはできない。判定ごとに、誤った側へ倒れたときの害を考え、次の形を選ぶ。
  - 確かめたことを条件に先へ進む判定（完了する、修正範囲から外す、など）は、「…ことを確かめた」の形にする。確かめる手順は、その前の `do` に書く。`condition` は確かめたかを判定するだけで、確かめる手順にはならない。
    この形は、確かめたかどうかを先行する手順の結果から判定させるので、確かめていなければ偽と読まれやすい。ただし、判定できないときに偽になることを保証するものではない。
  - `not condition("…")` は、判定できないときに先へ進む側へ倒れうる。進んでも害の小さい判定（もう一度確かめる、など）だけに使う。

## コメントの書き方

- コメントには、段階や手順の目的と、その手順を採る理由を書く。理由を示す例も書いてよい。
- コメントに書けるのは、消しても、行う手順と守る制約が変わらない文だけとする。行う手順、制約、判定の基準、用語の定義、前提、許可は、コメントに書かない。書き手向けの覚え書きも書かない。
- 理由は、すぐ下の段階や手順を採る理由として、「〜だから、〜する」まで書く。事実だけを置かない。
- 段階の目的と理由は、その `def` の直前に書く。手順の理由は、その手順の直前に書く。その手順だけを囲む `with` があるときは、その `with` の直前に書く。コードと同じ行には書かない。

## `do`、`with constraint`、`with context` の分け方

- `do` の括弧の切れ目が 1 つのステップになる。`do` の文は、行う手順を述べる 1 文にする。独立した完了点を持つ手順を 1 つの `do` に並べず、別の `do` に分ける。
- `do` の文に、2 文目を続けない。その手順への禁止と基準、作るものが満たすことは `with constraint` に、説明と許可は `with context` に書く。囲む範囲は、この節の後の項で決める。箇条書きも `do` の文に入れない。1 文の中の節で言える限定（「必要な点だけを確かめる」など）は、`do` の文に書いてよい。
- `do` の文を 1 文にするために、いくつもの文を読点でつながない。2 文目以降の文は、それだけを行って完了したと言える手順なら別の `do` に、その手順の行い方や限りを定める文なら `with constraint` に移す。
- `do` の文の中に、分岐を書かない。「〜の場合は」「〜なら」で、その後に進む手順が変わる文は、`if` にする。表の行によって、その後に進む手順や段階が変わる場合も、その分岐を `if` にする。どの行でもその後に進む手順が同じ表は、参照資料に置いたまま名指してよい。
- `with constraint` と `with context` の文は、順序も完了も持たない。行動を書かない。
- 手順の順序や段階の呼び出しの順序が表していることを、`with constraint` に重ねて書かない。
- `with constraint` には、破りうるものを書く。禁止、条件、基準、範囲、完了条件がこれに当たる。
- `with context` には、守る・破るの対象にならないものを書く。前提、許可がこれに当たる。どちらに書くか迷う文は、それに反する行動を考えられるかで決める。用語の定義は、`with context` に書かず、`define` で宣言する。
- 一つの文に許可と禁止、定義と制約が混ざっているときは分けて、それぞれに書く。制約の意味を示す例は、その制約と同じ `constraint` に置く。
- `with context` に置く前提は、その範囲の中（そこから呼ぶ段階を含む）の `do`、`condition`、`whenever` が、判断の材料に使うものに限る。手順を採る理由を述べるだけの文は、コメントに書く。
- `with` が囲む範囲は、文ごとに決め、その文が効く手順をすべて含む、いちばん狭い範囲にする。効く手順が別々の段階にあるときは、間にあるほかの手順の結果を変えない文に限り、それらの段階を呼ぶ所を囲んでよい。間の手順の結果を変える文は、効く手順ごとに分けて囲む。同じ段階にあることを理由に、効く範囲の違う文を一つの `with` に並べない。
- いくつもの呼び出し元で同じ決まりが要り、`with` で囲むと範囲が重なる場合は、その決まりを持つ段階を作り、要る所から呼ぶ。
- 効く範囲が同じ `context`、`constraint`、`whenever` は一つの `with` に並べ、入れ子にしない。入れ子は、内側の効く範囲が外側より狭いときだけ使う。二つの文の効く範囲が、一部だけ重なって入れ子にできないときは、片方の文を、効く手順ごとに分けて囲む。
- 条件付きの決まりは、きっかけの後に行うことを足すものか、取りうる行動を狭めるものかで分ける。「〜したものだけを使う」「〜するまで〜しない」のように、取りうる行動を狭めるだけのものは、行動の制限として書く。行うことを足すものは、`constraint` の文に書かない。
- 行うことを足す決まりは、きっかけが起きる位置が流れの中で決まるなら、その位置に `if` で置く。位置が決まらず、範囲の中のどの手順の途中でも起きうるなら（依頼の訂正など）、`whenever` で書く（「`whenever` の書き方」）。
- `do` の文とは別の文で述べる行動の制限は、それを破る機会がある手順を囲む `with constraint` に書く。破る機会が一つの `do` の中だけなら、その `do` だけを囲む。制限を述べた手順より後の手順で破りうる制限は、その後の手順まで囲む。
- `constraint` は、範囲の中の行動が取りうる幅を狭めるもので、どの分岐へ進むかは決めない。判定も行動の一つなので、判定の答えを出すときに何を根拠にしてよいか、いけないかは、`constraint` に書ける。効くのが一つの判定だけなら、その `condition` の文に書く。いくつもの判定にまたがるなら、効く範囲を `with constraint` で囲む。
- `with constraint` に書いてよいのは、消しても、どの `if` があり、それぞれが何を問うかが変わらない文である。消すと問いそのものが変わる文は、その `condition` の文に書く。

## `define` と段階の引数の書き方

- 用語の定義は、`名前 = define("…")` で宣言する。手順が作って後の手順で使うもの（作業記録に残す記録など）の呼び名も、同じ形で宣言する。文には、その名前が指すものが何であるかと、どういうものをその名前で呼ぶかを書く。
- 宣言を置くのは、宣言の文が、名前の語からは分からないことを足すときだけにする。足すものは、範囲や条件（何をそう呼び、何を呼ばないか）、中身（何からできているか）、参照先（どの資料のどこか）のどれかである。名前の語が元々持つ意味を言い直しているだけなら、宣言を置かず、その語をそのまま文で使う。迷うときは、宣言を消して本文を読み、その語が指すものが変わるかで決める。変わらないなら、宣言を置かない。
- 宣言した名前は、文の中でもその語のまま使う。その名前が指すものを作る手順は `do` に書き、その文の中で名前を使う。
- 宣言した名前は、使える範囲のすべての文で、宣言した意味で読まれる。範囲の中の文で、その語を別の意味で使わない。宣言するときは、範囲の中でその語が出てくる文をすべて見て、どれも宣言した意味で読んでよいことを確かめる。別の意味で使っている文があれば、その文の語か、宣言する名前を変える。
- 名前には、指すものを絞った語を選ぶ。「結果」「対象」のように広く使う語を名前にすると、別の意味で使った文まで、宣言した意味で読まれる。
- 名前は、補助関数の宣言の後、メインの段階より前に宣言する。この名前は、どの段階でも使える。使う所が、一つの段階と、そこから引数で渡す先に限られる名前は、その段階の先頭で宣言する。この名前を使えるのは、その段階の中と、引数で渡した先だけである。段階の外で宣言した名前や、その段階の引数と同じ名前を、段階の中で宣言しない。
- 段階の文が、呼び出し元のループ変数、呼び出し元の段階の中で宣言した名前、呼び出し元が受けた引数を指すときは、それを引数で受ける。呼び出しでは、その名前を渡す。名前のほかは渡さない。
- 引数の名前は、`for` のループ変数と同じく、文の中でその対象を指す名詞と同じ語にする。`def 指摘の原因を確かめる(指摘):` と書いたら、文では「その指摘」と呼ぶ。
- ループ変数や引数の名前に、宣言した名前と同じ語を使うのは、それが、宣言した名前の指すものの一つを指すときだけにする。
- 宣言する名前、引数の名前、`for` の名前に、段階や補助関数の名前を使わない。

## `whenever` の書き方

- 範囲の中のどの手順の途中でも起きうるきっかけと、そのとき行うことは、`with whenever("きっかけ", 段階の名前):` で書く。きっかけを待ち受けるのは、その `with` の範囲にいる間だけである。
- きっかけは、`whenever` の文に書く。`condition` は使わない。`condition` は、その行に来たときに一度だけ判定するものだからである。
- きっかけが起きたときに行うことは、渡した段階の `do` に書く。`whenever` の文には書かない。
- 渡した段階を終えた後は、割り込まれた手順を続けるものとして書く。別の所へ戻らせるときだけ、戻る先を、渡す段階の `do` に書く。
- 渡す段階は、引数を取らない段階にする。渡す段階を、段階として呼ばない。渡す段階の中では、`whenever` を使わない。
- 一つの段階でしか渡さない段階は、その段階の中に `def` で定義し、渡す `with` の直前に置く。同じ `with` でいくつも渡すときは、その直前に続けて置く。その `with` でだけ渡す。こう定義した段階の文は、外側の段階の引数、外側の段階の中で宣言した名前、囲んでいるループのループ変数を指せる。
- いくつもの段階で渡す段階は、段階の外に定義する（置き場所は「段階を置く順」）。
- 段階の中の `def` は、`whenever` に渡す段階にだけ使う。その中に、さらに `def` を置かない。名前も宣言しない。

## 自然文のスキルを変換するとき

- 原文の文は、なるべくそのまま文字列に入れる。
- コメントにする目的と理由の文は、原文のまま移さず、置く場所の手順を採る理由として書き直す。書き直したコメントも、原文との照合の対象にする。
- 原文の「X とは Y である」の形の文を、形だけで用語の定義として扱わない。定義、前提、制約、言い換えのどれとして働いているかを見て、置き場所を決める。
- 原文から決まらない構造の選択（分岐を排他にするか、条件が重なったときの扱い、どこで終えるか、など）は、変換で黙って決めない。書き手向けの覚え書きに残し、ユーザーへ示す。
- 意味が変わっていないかは、変換した者とは別のサブエージェントに原文と照合させる。起きやすいずれは次のとおり。
  - `if` と `else` で、原文では重なりうる条件を排他にする。
  - 文を移した先の `with constraint`、`with context`、`do` が、原文で効いていた判定や行動に届かない。
  - 確かめる手順を、確かめたかを判定する `condition` に置き換える。
  - 宣言した名前と同じ語を別の意味で使っている原文の文を、そのまま移す。
  - 一つの `do` の文にあった制限を、その `do` だけを囲む `with constraint` に移して、後の手順で破りうる制限を届かなくする。
  - それだけを行って完了したと言える手順（「〜を選ぶ」「〜から決める」など）を、基準として `with constraint` に移して、手順を消す。
  - いくつもの文を読点でつないで、`do` の 1 文にする。
