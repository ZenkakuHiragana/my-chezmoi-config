# Python 風の指示の書き方

スキル本文を、AI が読む Python 風の指示として書くときの決まり。
本文を Python 風に書いたスキルを作成・編集するとき、自然文のスキルをこの形へ変換するときに従う。

Python の構文は、手順の順序、分岐、繰り返し、制約や前提の効く範囲、判定の位置を表すために使う。実行するためのプログラムではない。
各手順の中身と判定の基準は、文字列の中に自然文で書く。
構文を使うのは、自然文として読んでも同じ意味になり、`if` の行だけを見てその判定を確かめられる範囲に限る。

## ファイルの形

- `SKILL.md` は frontmatter で始め、その後に本文全体を 1 つの ```python のコードフェンスに入れる。Markdown の見出しや、フェンスの外の文は置かない。
- フェンスの中は、次の順に置く。
  1. 補助関数 `condition`、`constraint`、`context`、`do` の宣言（「補助関数」の文面のまま）
  2. スキル全体の流れを表すメインの段階
  3. メインから呼ぶ段階（呼ばれる順）
  4. 末尾に、メインの段階を呼ぶ 1 行
- 段階の関数名は、その段階の節の名前として扱う。ほかの段階や手順から参照するときは、「段階の名前」の形で関数名を書く。

## 補助関数

```python
def condition(prompt: str) -> bool: ...
def constraint(prompt: str): ...
def context(prompt: str): ...
def do(prompt: str): ...
```

補助関数の意味は、名前と Python の構文の意味だけで表す。`condition` は判定、`constraint` は守る制約、`context` は前提として使う情報、`do` は行う手順である。`with` の効く範囲は、Python の `with` と同じく、ブロックの中で呼んだ段階の実行中も含む。
名前と構文から読めない動作の決まりを、docstring などで足さない。足した決まりは実行する AI に守られるとは限らない一方、レビューでは厳密に当てはめられ、それを満たすための文が増える。

## 使う構文

- 段階: `def 段階の名前():`（引数なし）と、その呼び出し
- 分岐: `if`、`else`
- 繰り返し: `while`、`for 指摘 in 成立した指摘:` の形の `for`
- `break`: 入れ子になったループの内側では使わない。抜けるのは一番内側のループだけなのに、文として読むと外側のループまでやめるように読めるため。
- 制約: `with constraint("…"):`
- 前提: `with context("…"):`。効く範囲が同じ `context` と `constraint` は、`with (context("…"), constraint("…")):` のように一つの `with` に並べる。
- 手順: `do("…")`。参照資料を読むことも、パスを添えて `do` の文に書く。
- `if` と `while` の条件には、`condition("…")` と、それをつなぐ `and`、`or`、`not` だけを置く。

`for` のループ変数は、文の中でその対象を指す名詞と同じ語にする。`for 指摘 in …` と書いたら、文では「その指摘」と呼ぶ。
ループの対象の名前（`成立した指摘` など）は、その名前が指す作業中の対象を表す。

使わない構文は次のとおり。

| 構文                               | 使わない理由                                                                                                                  |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `return`                           | 戻り先と、文中の「ユーザーへ返す」との違いが読めない。続きの処理は `else` に入れ、返す相手は `do` の文に書く                  |
| `import`                           | パスを書けない。2 回目以降は何もしない意味になる                                                                              |
| 代入、引数、f 文字列               | 条件の中身が代入した場所や呼び出し元へ移り、`if` の行だけで判定を確かめられなくなる。過去の事実は `condition("…した")` で表す |
| リスト、辞書、クラス、例外         | 自然文として読める範囲を超える。例外は、作業を止める意味になる                                                                |
| コメント、docstring               | 指示として読まれるかが分からない。指示は `do`、`constraint`、`context` に書く。書き手向けの覚え書きは本文に置かない。補助関数にも付けない（「補助関数」） |

## `condition` の書き方

- 一つの `condition` には、判定を一つだけ書く。述語が複数あれば、`and` か `or` で別の `condition` に分ける。名詞句の中の「や」「・」は分けない。
- 判定する内容は肯定形で書き、否定は `not` で表す。名詞句の中の否定と、判定の基準を添える文はこの限りではない。
- `and` と `or` を混ぜるときは、必ず括弧を付ける。前提になる条件を左に書く。
- 判定の基準は、その `condition` の文の中に書く。
- 答えを何で決めるかが分かるように書く。差分、ファイル、記録、ユーザー発言の文面のように、AI の外にあるもので答えが決まる判定は、見る先を文に書く。ただし、見る先を書き換えても、判定が狙いどおりに動くとは限らない。
- `condition` は、判定できないときも真か偽を返し、どちらになるかは決まっていない。書き方でこれを防ぐことはできない。判定ごとに、誤った側へ倒れたときの害を考え、次の形を選ぶ。
  - 確かめたことを条件に先へ進む判定（完了する、修正範囲から外す、など）は、「…ことを確かめた」の形にする。確かめる手順は、その前の `do` に書く。`condition` は確かめたかを判定するだけで、確かめる手順にはならない。
    この形は、確かめたかどうかを先行する手順の結果から判定させるので、確かめていなければ偽と読まれやすい。ただし、判定できないときに偽になることを保証するものではない。
  - `not condition("…")` は、判定できないときに先へ進む側へ倒れうる。進んでも害の小さい判定（もう一度確かめる、など）だけに使う。

## `do`、`with constraint`、`with context` の分け方

- `do` の括弧の切れ目が 1 つのステップになる。複数の文を入れてよいのは、その `do` が終わったときに何が完了したかを 1 つの文で言える範囲だけとする。独立した完了点を持つ手順を 1 つの `do` に並べない。
- `with constraint` と `with context` の文は、順序も完了も持たない。行動を書かない。
- `with constraint` には、破りうるものを書く。禁止、条件、基準、範囲、完了条件がこれに当たる。
- `with context` には、守る・破るの対象にならないものを書く。用語の定義、前提、許可がこれに当たる。どちらに書くか迷う文は、それに反する行動を考えられるかで決める。
- 一つの文に許可と禁止、定義と制約が混ざっているときは分けて、それぞれに書く。制約の意味を示す例は、その制約と同じ `constraint` に置く。
- 定義と前提は、それを使う箇所をすべて囲む `with context` に置く。
- 効く範囲が同じ `context` と `constraint` は一つの `with` に並べ、入れ子にしない。入れ子は、内側の効く範囲が外側より狭いときだけ使う。
- 条件付きの追加操作は、`constraint` の文に行動として書かない。「〜したものだけを使う」「〜するまで〜しない」のような、禁止または基準の形に書き換える。
- 行動の制限は、それを破る機会が一つの `do` の中だけなら、その `do` の文に書く。いくつもの手順にまたがるなら、効く範囲を `with constraint` で囲む。
- いくつもの判定に効く基準も、効く範囲を `with constraint` で囲む。
- きっかけ付きの規則は、きっかけが起きる場所に `if` で置く。きっかけがどの手順でも起きうる場合（依頼の訂正など）は、効く範囲の `with constraint` に条件ごと書く。

## 自然文のスキルを変換するとき

- 原文の文は、なるべくそのまま文字列に入れる。
- 原文から決まらない構造の選択（分岐を排他にするか、条件が重なったときの扱い、どこで終えるか、など）は、変換で黙って決めない。書き手向けの覚え書きに残し、ユーザーへ示す。
- 構文は `compile` で確かめる。`ast.parse` は、関数の中の `import *` のような誤りを見逃す。
- 意味が変わっていないかは、変換した者とは別のサブエージェントに原文と照合させる。起きやすいずれは次のとおり。
  - `if` と `else` で、原文では重なりうる条件を排他にする。
  - 文を移した先の `with constraint`、`with context`、`do` が、原文で効いていた判定や行動に届かない。
  - 確かめる手順を、確かめたかを判定する `condition` に置き換える。
