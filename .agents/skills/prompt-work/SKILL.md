# プロンプトと AI 委任に関する問題分析に係る作業規則

プロンプトの変更、スキルの調整、作業規則の変更と統治に関わる作業を行う場合に守るべき規則。

## 目的

- プロンプトを通常のコードや仕様と同様に保守対象として扱うための最小原則と運用ルールを定義する。

## 改善介入ポリシー

- 過去の失敗記録を参考にする。
  - 失敗記録は `./.opencode/local-failure-logs/` にある。概要を知ることができるが、分析が間違っている型の失敗も存在する。
  - より実態に迫るにはセッションログを直接採掘する。
    - Claude Code: `~/.claude/projects/`
    - Codex: `~/.codex/sessions/`
    - OpenCode: `~/.local/share/opencode/opencode.db` または `opencode db --format json "SQLITE3 QUERY"`
    - Oh-My-Pi: `~/.omp/agent/sessions/`
    - Pi Coding Agent: `~/.pi/agent/sessions/`
  - 過去のセッションの採掘レポートの保存先は `./.opencode/local-failure-logs/session-mining/` である。
  - 蓄積事例のトリアージレポートの保存先は `./.opencode/local-failure-logs/triage/` である。
- 失敗記録の作成日時とこのリポジトリの git 履歴を照合し、当時存在しなかった規則が現在は存在しているかどうかを確認する。
- 試験や検証の記録は実際の失敗事例ではないので別の検証記録として扱う。

## 関連資料

- 目的と問題の分析: `references/problem-analysis/fundamental-problem-map.md`
- 指示と規則の妥当性に関する判断軸: `references/quality-principles.md`

## 作業前の確認項目

- [ ] 追加ではなく、まずは言い換え・統合・移設、プロンプト編集以外の介入方法で対応できるか検討し、決定した対応方針とその理由を人間に合理的に説明した
- [ ] どの層（システムプロンプト / スキルの `description` / スキル本文）へ何をするかを決定し、なぜその層であるのかを説明し、人間の同意を得た
- [ ] 重要な条件文について、その時点で可視な情報だけで判定できるか確認した
- [ ] 条件分岐が別スキルや別工程の結果を要求していないか確認した
- [ ] 必須動作と保持すべき能力 / 制約を編集前に分けて洗い出し、説明した

## 作業後の確認項目

- [ ] 同じ規則について、複数の箇所が独立した正本として振る舞い、変更時に相互の同期を必要とする状態が残っていない
- [ ] 他の箇所と同じ内容を含む記述であっても、そのスキルを単独で理解・実行するために必要な入力、条件、判断、動作、停止、出力、責務は、重複だけを理由に削除または外部化していない
- [ ] ある確認項目を満たすために行った変更が、他の確認項目で要求される性質を損なっていない。特に、重複除去、共通化、簡潔化、責務移動によって、単独実行可能性、主体・条件・状態遷移の明記、責務境界を失わせていない
- [ ] 同じ指示を別表現で複数書いていないか
- [ ] 既存の用語、章名、見出しをそのまま使い、同じ概念や手順に新しい章や節を作っていない
- [ ] 同じ概念を指す表記が本文全体で一致している（表記揺れがない）
- [ ] 長い行動規範が常設プロンプトに残っていない
- [ ] 例外条件が本文に埋もれていない（本文の主要な流れから独立した長い例外条件は専用のスキルに移す）
- [ ] 未解決事項や受け入れ条件の不足を、実行不能な阻害要因と取り違えていない
- [ ] タスクや場面に固有の権限や禁止事項が適切な層に書かれているか
- [ ] 変更が失敗対応のためである場合、変更の理由と影響範囲を関連する失敗報告またはトリアージレポートに記録した
- [ ] 追跡対象のプロンプトファイルには確定済みの規則だけがある
- [ ] 未整理の証拠・長い会話断片・生ログ・到達不能なファイルパスがプロンプト本文に存在しない（到達不能なファイルパスとは、削除済みまたは未作成のまま実体を前提とするなど、実行環境から解決できないパスを指す。失敗記録などの実在する証拠置き場への参照はこれに当たらない）
- [ ] 抽象的な価値判断を、観測可能な代理条件や具体的な発火条件に分解した
- [ ] サブエージェント等の別主体が担うべき認可、レビュー、検証を、監督対象自身の判断、自己確認、自己申告で代替していない
- [ ] 挙動上意味のある指示を削除した場合、同層の言い換えまたは別層への明示的な移設で保存した。または、その挙動を削除することこそが介入であることを示した
- [ ] 目的 / 発火条件 / 必須出力 / 禁止行動 / 検証対象が、該当能力の階層全体から抜け落ちていない
- [ ] コマンド名、引き渡し先、スラッシュコマンド表記が一貫している
- [ ] 本文に、このリポジトリのテンプレート実体化のために使われるファイルパス（`.chezmoitemplates/`、`dot_agents/`、`dot_config/` などの実体化前のパスおよびそれを前提とする相対ファイルパス）を含めていない
- [ ] 規則や手順をファイル名で参照していない（スキルのフォルダに配置した関連ファイルを概念名に添えて示す相対パスを除く）
- [ ] 規則や手順の参照は概念名またはプロンプト本文中に記載のある章や節の名前で書かれている
- [ ] スキルのフォルダに配置した関連ファイルへの参照はスキル名のフォルダを基点とした相対パスで書かれている
- [ ] `scripts/check_vocabulary.py` の結果、`unaccounted` / `file-ref` がすべて 0 である
- [ ] `scripts/check_vocabulary.py` の検査対象は、バックティック内の未登録語彙と規則・手順のファイル名参照に限られている
- [ ] 義務語彙の棚卸し（`references/obligation-vocabulary.md`）に記載の曖昧語彙がプロンプト本文に存在しない
- [ ] スキルはそれ単独で理解可能な本文になっている
- [ ] スキルとサブエージェントの `description` はそれ単独で他の統治規則や他のハーネス拡張機能、このリポジトリのローカル規則、他のスキルの存在と理解を前提とせずに説明されている
- [ ] スキルとサブエージェントの `description` で使うべき条件、使わざるべき条件を示している
- [ ] スキルとサブエージェントの `description` で示された条件が他のどのスキルとも重複していない
- [ ] 共通システムプロンプトでスキルやサブエージェントへの誘導をしていない。確実な状態遷移のためにやむを得ずスキルへの誘導を書く場合でも、そのスキルやサブエージェントの `description` に書いてあることを改めて説明していない
- [ ] 共通システムプロンプトの構成に使用するテンプレート断片で、複数のファイルで同じ説明が書かれていない
- [ ] AI委任統治系の評価基準（`references/quality-principles.md`）に記載の設計原則に違反するプロンプト本文が存在しない

### 規範文と制御フロー

- [ ] 義務、禁止、許可、判断、状態遷移を表す各文について、その動作を実行する主体が本文に明記されている
- [ ] 親エージェント、サブエージェント、専用エージェントなど、異なる主体の責務を主語の省略によって混同していない
- [ ] スキル名、文書名、成果物名など、実行主体ではないものを「判断する」「実行する」「返す」「受け取る」などの動作主体として扱っていない
- [ ] スキルは実行主体ではなく、実行主体が読む手順・判断基準として記述されている
- [ ] 「渡す」「返す」「戻す」「接続する」「委譲する」など複数主体を前提とする動詞について、動作主体、相手または接続先、対象が本文にそれぞれ明記されている
- [ ] 作業を別主体へ委譲できるか否かが結果を変える箇所では、委譲の可否が本文に明記されている
- [ ] 別ファイルまたは別スキルへ手順を移した場合、手順の所有者、実行主体、委譲可否、開始条件、終了後の接続先が移設後の本文にも明記されている
- [ ] 節や箇条書きの配置、一般的な役割分担、前後の文脈、常識的な推測だけを根拠に、実行主体、実行順序、開始条件、終了条件、状態遷移を補完させていない
- [ ] 条件付きの動作について、条件を判定する主体と、条件成立後の動作を行う主体が本文に明記されている
- [ ] ある主体の出力を別主体が利用する場合、出力を生成する主体、利用する主体、利用方法が本文に明記されている
- [ ] 「結果」「分類」「候補」「対象」「それ」「これ」などの参照語が、本文中の明示的な参照先なしに解釈を要求していない
- [ ] 規範上異なる意味を持つ概念を、簡潔化や言い換えによって同じ語へ統合していない
- [ ] 編集前に存在した主体、責務、委譲禁止、開始条件、終了条件、状態遷移のいずれかを削除した場合、その意味を意図して削除したか、移設後の本文のどこに保存したかを差分から確認した
- [ ] 「文脈から明らか」「通常はそうする」「常識的に一意」「他の規則から推測できる」ことを、規範上必要な主体、条件、禁止、状態遷移の明記の代わりにしていない
- [ ] 編集後の本文だけから、実行者が新しい主体、手順、委譲関係、条件、状態遷移を補完することなく実行できる
