# レビュー手続きの運営

複数の独立した検査単位を持つレビューを、固定した初回レビューと条件付きの独立監査からなる有限な手続きとして運営する。初回指摘が0件なら独立監査を行わず、`要調査` があれば `判定不能` で終了する。状態、裁定、修正候補、監査結果、採否は親エージェントが所有する。

## 発動

レビューに複数の独立した検査単位があり、その結果を親エージェントがまとめて裁定する必要があるとき、最初のレビュー単位を起動する前に使用する。単一実行者が対象と観点を一度検査すれば閉じるレビューには使わない。

一回の手続きは、一つの検査対象版を扱い、次の上限を守る。

- 初回レビューの並列展開: 一回
- 親エージェントによる全指摘の裁定: 一回
- 完成修正候補の作成: 最大一回
- 独立監査: 最大一回

同じ手続きの中で修正候補を作り直したり、独立監査を再実行したりしてはならない。

## 1. 入力の固定

最初のレビュー単位を起動する前に、次の入力と条件を確認する。

- 手続きID
- 監査者が直接読める検査対象版と差分元の版の参照
- レビュー判定根拠版
- 観点集合と有限な検査集合
- 検査単位ごとの担当、`読取可能`、観測出力、確認方法
- 作業契約の条件集合
- レビュー種別ごとの修正後確認
- 使用する各レビュースキルの `## 入力` 節への参照。要件レビューでは `requirement-reviewer` が必要とする情報依存関係

最初のレビュー単位を起動する前に、親エージェントは次の各項目を照合しなければならない。

- 要件レビューの担当単位は、レビュー対象を起点に、担当する条項または検査が依存し、かつその条項または検査が宣言した参照先だけをたどって直接読むこと
- 候補レビューで、候補自身に必要な `依頼引用`、作業段階、未決事項、各義務の認可元・根拠への到達情報がない場合は、候補が入力契約を満たしていないと扱う。親エージェントは既存の情報所有先から補える範囲だけを補って候補を再固定し、意味を推測して補ってはならない。補えない場合は不足の所有先と再開条件を呼び出し側へ返すこと。
- 候補をレビューへ渡す前に、候補が宣言した参照先の資料が欠落または読取不能である場合は、レビュー単位を起動せず、不足の所有先と再開条件を呼び出し側へ返すこと。
- 候補自身の入力欠落と、候補が宣言した参照先の資料の欠落または読取不能を同じ `判定不能` として扱ってはならない。前者は候補の補正または候補作成元への戻り、後者は `判定不能` として扱うこと。

要件レビューでは、候補レビューの場合は要件契約候補を、派生レビューの場合は固定済み要件契約とそこから派生した仕様または作業契約を検査対象版として扱う。候補レビューでは候補自身をレビュー判定根拠版へ含めてはならない。全 `RR-OBL-<連番>` と `RR-CONTRACT-1` を全検査とする。

固定後に検査、観点、指摘候補、判定基準を追加してはならない。

## 2. 初回レビュー

固定した検査集合だけを、親エージェントのレビュー並列展開規則に従って観点別に展開する。各実行者は `読み取り専用` とし、割り当てられた単位だけを検査する。先行結果を他のレビュアーへ渡してはならない。

各実行者は対象レビュースキルが定める能力固有の結果を返す。対象レビュースキルへ固定状態値、固定ID、表、JSONのいずれかを含む結果形式を要求してはならない。親エージェントは、固定した確認方法と実際の結果を照合し、検査単位ごとに次の三値へ正規化する。

- 指定した確認方法で再現可能な破綻を観測した場合は `破綻確認` とする。
- 指定した確認方法を完了し、破綻を観測しなかった場合は `反例未確認` とする。
- 情報、環境、権限、または結果の根拠が不足して判定できない場合は `判定不能` とする。

結果から三値を根拠付きで決められない場合は `判定不能` とし、成功や無欠陥へ丸めてはならない。初回指摘集合は `破綻確認` からだけ作成し、`判定不能` を指摘へ変換しない。

全検査単位が結果または実行不能の理由と再開条件を返した時点で、初回指摘集合を固定する。

### いずれかの条件を満たしたら終了

- 全検査の未完了または `判定不能` が一件以上 → `判定不能`
- 指摘が0件（全検査完了、判定不能0件）→ `合格`（修正候補と独立監査は作らない）

### 入力欠落による判定不能からの再開

`判定不能` の原因が候補が宣言した参照先の資料の欠落または読取不能である場合に限り、入力を補修して再固定し、初回レビューを新規手続きとして再実行できる。

- 再固定では手続きID を連番更新する。
- 検査集合、観点、`読取可能`、条件を変えてはならない。
- これは候補の再編集や同一手続き内の再監査には該当しない。

## 3. 親エージェントによる裁定

親エージェントは、固定した全指摘を `review-response` の基準へ直接照合し、各一回だけ次のいずれかへ分類する。

- `採用`
- `却下`
- `要調査`
- `対象外`

分類用のサブエージェントを起動してはならない。全指摘に分類、契約条件、確認方法、修正前の観測、根拠または不足、再開条件を記録する。途中で指摘を追加してはならない。

`採用` には、レビュー種別に対応する修正契約を固定する。

- 全レビュー共通: 修正前の観測失敗、侵害する条件、修正範囲、非対象範囲、保つ条件、修正後に使う同じ確認方法
- 要件レビュー: 削除する意味、保持する意味、追加する意味、各意味の認可元または対象条件

`却下` と `対象外` を修正理由へ入れてはならない。

### この条件で終了

- `要調査` が一件以上 → `判定不能` で終了し、不足と再開条件を記録する。

## 4. 完成修正候補

完成修正候補の作成は、共通規則の「レビュー」段階から「レビュー対応」段階への遷移である。遷移の前に、依頼が修正適用までを含むことを、文脈に紐づいた根拠（依頼文言、作業契約、ユーザー回答など）で提示できることを確認する。根拠を提示できない場合、または依頼が指摘報告までを求めている場合は、候補を作成せず、ユーザーへ確認する。

`採用` が一件以上なら、親エージェントは修正契約だけに基づく完成修正候補を一回作成する。候補は、監査後に内容判断を伴う再編集なしで採用できる状態とし、現在採用中の成果物と区別して隔離する。

候補には次を記録する。

- 監査者が直接読める完成修正候補の参照
- 差分元の版
- 変更対象
- 実際の差分
- 各変更が処理する `採用` と修正契約
- 非対象範囲と保つ条件
- 修正後確認の結果

修正方針、疑似コード、編集指示、未適用の差分案を完成修正候補としてはならない。`採用` 以外の便乗修正、固定範囲を越える変更、認可元のない意味、無関係な整理を含めてはならない。

初回指摘が一件以上あり、`採用` が0件なら、完成修正候補を作成せず、裁定だけを独立監査へ渡す。

### この条件で終了

- 作成中または修正後確認が失敗した場合 → 候補を不採用として `不合格` で終了する。同じ手続き内で候補を縮小、巻き戻し、手直し、再作成したり、別の差分を提示したりしてはならない。

## 5. 独立監査

手続きに関わっていない新規のエージェントを一回だけ起動する。監査者は `読み取り専用` とする。

監査入力は `review-audit` が要求する資料に従って、一つの入力ファイルへ書き出す。

`採用` が0件なら、監査の対象は全分類だけとする。

監査者へ、親エージェントの調査経緯、感想、採用理由、理想設計、レビュー作業記録を渡してはならない。

監査者の確認手順（直接参照、実差分の照合、裁定・修正内容・修正結果の確認）と結果の解釈は `review-audit` の契約に従う。監査の対象は固定した指摘集合の処理だけであり、完成修正候補全体からの新しい問題の探索や新しい指摘の追加は対象外とする。

## 6. 監査結果

独立監査は次のいずれかを終端結果として返す。

- `合格`: 裁定、該当する修正内容、該当する修正結果をすべて確認した。監査対象を確定状態とし、監査後の内容変更を許可しない
- `不合格`: 入力から観測可能な不一致を確認した。候補を不採用とし、同じ手続き内の手直しと再監査を許可しない
- `判定不能`: 情報、環境、権限の不足により判定できない。候補を不採用とし、同じ手続き内の入力差し替え、手直し、再監査を許可しない

`不合格` の結果には対象、観測した不一致、根拠、確認方法が含まれる。`判定不能` の結果には不足、試みた確認、再開条件が含まれる。結果を別の値へ丸めてはならない。`判定不能` の不足分類、能力選択、戻り先はこの手続きで決めず、呼び出し側が決める。

## 7. 採否と終了

独立監査が `合格` の場合に限り、次を行う。

- `採用` が0件なら、修正前の検査対象版をそのまま合格とする
- `採用` が一件以上なら、監査対象となった完成修正候補そのものを採用する

監査結果を参考に再編集したり、同じ内容を書き直したりしてはならない。

独立監査が `不合格` または `判定不能` の場合は完成修正候補を採用しない。現在採用中の成果物を変更してはならない。同じ手続き内で別候補の作成、修正候補の手直し、独立監査の再実行をしてはならない。

要件契約候補は、手続き結果が `合格` の場合に限り要件契約として固定する。呼び出し側は `不合格` または `判定不能` を自身の準備完了判定へ反映し、手続きが返した不一致または再開条件に応じて戻り先を決める。`context-clarification` から呼び出した場合の不足分類と戻り先は、同スキルが担当する。

手続き終了後にレビュー対象または完成修正候補の内容を変更した場合、変更後の版に終了した手続きの `合格`、`不合格`、`判定不能` を適用してはならない。

## 完了チェック

- 手続き結果（`合格` / `不合格` / `判定不能`）を確定し、結果と戻り先を記録した。
- 採用する場合は、監査対象と同一の対象を採用した。
- 同じ手続き内で再編集、候補再作成、監査再実行をしていない。
