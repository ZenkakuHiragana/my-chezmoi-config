# レビュー周回の運営

`broad-or-unclear` のレビュー周回を、固定入力と順序付きチェックリストによる有限な 1 周として運営する。終端状態と根拠をレビュー周回台帳へ記録する。

## 入力

- レビュー対象版: 検査対象となる成果物の版と基準版
- レビュー判定根拠版: 検査対象の正否を判定する根拠集合の版
  - `code-review`: 作業契約、仕様、不変条件、テスト
  - `japanese-doc-review`: 想定読者、読者が行う作業、選択した観点の参照本文
  - `requirement-review`: 依頼引用、後続訂正、確認済みの技術制約、安全上の不変条件、条項が参照するリポジトリ根拠と外部一次資料、テストとコマンド、情報所有先、対象自然言語の正本と保つ意味と利用経路
- `work_class`
- 開始前に固定する観点集合と検査集合
- レビュー単位ごとの担当、`read_set`、観測出力、確認方法
- レビュー単位ごとの終了判定への扱い: `必須` または `残存記録`
- 親エージェントの並列展開規則
- `review-response`
- 修正前処分案: `requirement-review` の `accepted` と、従来から独立確認の対象である親裁定の修正前処分
- 修正後確認一式: レビュー種別ごとの一括修正後検証
  - `code-review`: 指摘の確認方法と作業契約の実行可能なテスト
  - `japanese-doc-review`: 指摘の確認方法と読者利用経路の確認
  - `requirement-review`: `accepted` 指摘の確認方法と、影響を受けた `RR-*` 検査項目の再実行。実装後の受け入れテストは実行しない

## 発動

レビューの `work_class` が `broad-or-unclear` のとき、最初のレビュー単位を起動する前に必ず使用する。固定前に並列展開してはならない。

1 周の上限を次のように固定する。

- 初回並列展開: 1 回
- `review-response`: 1 回
- 修正前の新規独立確認: 1 回
- `accepted` 一括修正: 最大 1 回
- 対応後監査: 1 回

次の周を自動開始してはならない。

## 1. 周の固定

最初のレビュー単位を起動する前に、レビュー周回台帳へ次を記録する。

- 周回ID
- レビュー対象版: 検査対象となる成果物の版
- レビュー判定根拠版: 検査対象の正否を判定する根拠集合の版
  - `code-review`: 作業契約、仕様、不変条件、テスト
  - `japanese-doc-review`: 想定読者、読者が行う作業、選択した観点の参照本文
  - `requirement-review`: 依頼引用、後続訂正、確認済みの技術制約、安全上の不変条件、条項が参照するリポジトリ根拠と外部一次資料、テストとコマンド、情報所有先、対象自然言語の正本と保つ意味と利用経路
- `work_class`
- 観点集合
- 有限な検査集合
- レビュー単位ごとの担当、`read_set`、観測出力、確認方法
- レビュー単位ごとの `必須` または `残存記録`

`requirement-review` では、`要件契約候補` をレビュー対象版として扱う。検査対象となる契約候補を、それ自身のレビュー判定根拠版に含めてはならない。

`requirement-review` の有限な検査集合は、依頼と確認済み制約から固定した各意味上の義務と、契約全体の整合確認とする。契約候補の表や記載欄を別の検査単位へ分解してはならない。

要件契約候補の全 `RR-OBL-*` と `RR-CONTRACT-1` は `必須` とする。これらに `残存記録` を指定してはならない。指定がある場合は入力不正として、最初のレビュー単位を起動しない。

固定後に検査を追加してはならない。

## 2. 並列展開と受付閉鎖

固定した検査集合だけを、親エージェント用のレビュー並列展開規則に従って観点別に展開する。先行結果を他のレビュアーへ見せない。

全レビュー単位が結果を返すか、実行不能の理由と再開条件を返した時点で候補受付を閉鎖する。

- `必須` 単位が完了不能または `判定不能` なら `blocked` とする。
- `残存記録` 単位の `判定不能` は理由と再開条件を台帳へ記録する。それだけで `blocked` にしない。
- `判定不能`（検査被覆の欠損）を指摘へ変換してはならない。
- 受付閉鎖後に候補が現れた場合は現周へ追加せず、次の周の候補へ記録して `reset_required` とする。

## 3. 指摘分類

受付閉鎖時点の指摘集合について、`review-response` の 1 パス分類を実行する。

- `needs-investigation` が 1 件以上なら、不足と再開条件を記録して `blocked` とする。
- `accepted` だけを一括修正の対象とする。
- `rejected` と `out-of-scope` は分類根拠を台帳へ保持する。
- 分類後に指摘を追加してはならない。

`needs-investigation` がなく、`accepted`、`rejected`、`out-of-scope`、契約解釈の変更、または `判定不能` の受容がある場合は、親は修正前処分案を外部化する。`requirement-review` の `accepted` には次を必ず記録する。

- 修正前の観測失敗と対応する契約条件
- `削除する意味`
- `保持する意味`
- `追加する意味`
- 各意味の認可元または対象条件
- 修正後に同じ確認方法で確認する内容

`code-review` と `japanese-doc-review` の `accepted` には、今回の変更による意味上の差分の記載義務を追加せず、既存の修正契約を使う。親の採用理由、調査経緯、全体設計、コード差分、修正後成果物を修正前処分案へ含めてはならない。該当する親の裁定がない場合は、修正前処分案と新規独立確認に「該当なし」と記録する。

修正前の新規独立確認の新しい対象は `requirement-review` の `accepted` とする。`code-review` と `japanese-doc-review` の `accepted` は今回の新しい対象に含めず、既存の修正契約と対応後監査で処理する。

修正前処分案を外部化した後、4節の新規独立確認を一度だけ行う。確認を通過しない限り一括修正へ進んではならない。

`accepted` が 0 件で、独立確認の対象となる親の裁定もない場合は一括修正を作らず、対応後監査の修正後確認一式へ進む。

## 4. 修正前処分案と新規独立確認

修正前処分案を外部化した後、5節の一括修正前に、新規の別主体が一度だけ独立確認を行う。確認対象は `requirement-review` の `accepted` と、従来から対象である `rejected`、`out-of-scope`、契約解釈の変更、`判定不能` の受容とする。`code-review` と `japanese-doc-review` の `accepted` は今回の確認対象に含めない。レビュー周回の並列展開で起動したレビュアーを再利用してはならない。

全レビュー種別に共通する確認入力は、親の分類、該当する根拠、同じ入力から裁定を再現するために必要な固定入力とする。`requirement-review` の `accepted` 特別確認へ渡す入力は、次に限る。

- 依頼と後続訂正
- 確認済み技術制約
- 該当する契約条項
- 要件レビューの指摘と修正前の再現根拠
- `review-response` の分類
- 親が外部化した意味上の差分（`削除する意味`、`保持する意味`、`追加する意味` と各認可元または対象条件）

確認者へ親の採用理由、調査経緯、全体設計、レビュー作業記録、コード差分、修正後成果物を渡してはならない。新規独立確認は元の成果物を再レビューする作業ではなく、親の分類と修正前処分案を監査する作業である。`code-review` と `japanese-doc-review` では、既存の確認入力を使い、ここで追加した要件レビュー用の意味差分入力を要求してはならない。

確認者は、別の設計の良さ、完全性、一般的な品質、将来用途を評価してはならない。`requirement-review` の `accepted` について、次だけを同じ入力から確認する。

- `accepted` の観測された契約条件違反が、提示された再現根拠と同じ入力で成立しているか。
- 指摘が無認可の意味上の義務の追加を含む場合、`削除する意味` がその義務を消しているか。
- 同じ義務を別の表現、別の欄、別の根拠、別の受け入れ条件として保持していないか。
- `追加する意味` がある場合、依頼、後続訂正、確認済み制約、または既存契約条件へ追跡できるか。新しい無認可義務を追加していないか。
- 独立に認可された義務を削除または変更していないか。

全レビュー種別の `rejected`、`out-of-scope`、契約解釈の変更、または `判定不能` の受容については、従来の同じ裁定へ到達できるかを確認する。

処遇は次のとおりとする。

- 全ての確認対象が妥当なら、一括修正へ進む。
- `requirement-review` の `accepted` の分類を再現できない場合、確認できないときは `blocked`、反証できるときは固定入力を保てないため `reset_required` とする。修正案を実行してはならない。
- `requirement-review` の `accepted` の処分案に無認可の意味が残る場合は親の修正案を破棄する。無認可の意味が認可済みの意味から分離可能で、削除対象を一意に特定できると確認したときは、その無認可の意味の単純削除を唯一の修正として採用しなければならない。分離不能または削除対象を特定できないときは `reset_required` とし、分離可能性を確認できないときは `blocked` とする。
- `requirement-review` の `accepted` の処分案が認可済みの義務を削除または変更する場合は、修正案を破棄して `reset_required` とする。
- 判定不能は `blocked` とする。
- 親へ別の修正案を再提案させてはならない。
- `rejected` または `out-of-scope` について同じ分類へ到達できない場合は、親の分類を取り消し、該当する指摘を `accepted` または `needs-investigation` へ戻す。
- 契約解釈の変更について同じ裁定へ到達できない場合は、親の変更を取り消して `reset_required` とする。
- `判定不能` の受容について同じ裁定へ到達できない場合は、親の受容を取り消し、当該検査単位を未解消として `blocked` とする。指摘へ変換してはならない。

確認者、入力、除外した入力、実行時点、判定結果、不一致時の処遇をレビュー周回台帳へ記録する。対象となる親判断がない場合は、台帳へ「該当なし」と記録する。

## 5. 一括修正と失効判定

親は修正契約にある `accepted` 指摘だけを最大 1 回の一括修正で修正する。`review-orchestration` 自身は成果物を編集しない。

4節の新規独立確認で、親の裁定と、該当する `requirement-review` の `accepted` の修正前処分案が確認済みであることを前提とする。独立確認で修正案が破棄された場合、親へ別案の再提案を求めてはならない。`requirement-review` の `accepted` に含まれる無認可の意味が分離可能で、削除対象を一意に特定できると確認されたときは、確認で特定された意味の単純削除へ縮小して一括修正へ進めなければならない。分離不能または削除対象を特定できないときは `reset_required` とし、分離可能性を確認できないときは `blocked` として現周を終える。

修正後、`write_set` を各レビュー単位の `read_set` と観測出力へ照合する。

- 交差する単位だけを、同じ検査と同じ確認方法で 1 回再実行する。
- 交差しない単位の検査被覆は有効のままとする。
- 交差を判定できない場合は `blocked` とし、不足と再開条件を記録する。
- 再実行で失敗した場合は `rollback_required` とする。再実行中に現れた新しい候補は現周へ追加せず、次の周の候補として台帳へ記録する。

`requirement-review` の修正で、固定済みの意味上の義務に欠けていた契約記載を追加した場合は、その義務の既存検査を再実行する。新しい意味上の義務が必要になった場合は検査追加ではなくレビュー判定根拠版の変更として扱い、`reset_required` とする。

修正後に修正後確認一式を実行する。失敗した場合は `rollback_required` とする。`requirement-review` では実装後の受け入れテストは実行しない。

## 6. 判定基準の変更

周の中でレビュー判定根拠版が変わった場合は、旧根拠に基づく検査、候補、分類、対応後監査を全て失効し、`reset_required` とする。新しい周を自動開始してはならない。

レビュー対象版の変更（`accepted` 修正による）は判定基準の変更として扱わず、5節の対応後監査として処理する。

レビュー判定根拠版の変更となるのは次に該当するときに限る。

- ユーザー要求または後続訂正の変更
- 確認済みの技術制約の変更
- 安全上の不変条件の変更
- 情報所有先または正本の変更
- レビューの範囲または判定基準の変更

`要件契約候補` 内の範囲条項を `accepted` 指摘に基づいて修正することは、レビュー対象版の変更であり、レビュー判定根拠版の変更ではない。

## 7. 終端

次のいずれかをレビュー周回の終端状態として台帳に記録する。

- `ready_for_exit_check`: 全ての `必須` 単位が完了し、その `判定不能` が 0 件であり、指摘分類、修正前処分案、修正前の新規独立確認、必要な再実行、修正後確認一式が完了した。
- `blocked`: 必須単位、必須の判定不能領域、`needs-investigation`、修正前の独立確認の判定不能、または失効範囲のいずれかを解消できない。
- `reset_required`: レビュー判定根拠版の変更、受付閉鎖後の候補、固定入力を保てない変更、分類を反証する修正前確認、または認可済み義務を壊す修正前処分案がある。
- `rollback_required`: `accepted` 修正後の同じ確認方法または修正後確認一式が失敗した。

複数の終端条件が同時に成立した場合は、`rollback_required` > `reset_required` > `blocked` の優先順位で 1 つだけを記録する。採用しなかった成立条件と根拠は台帳の「結果」へ記録する。

## 禁止事項

- 開始後に検査または候補を追加してはならない。
- レビュー指摘の内容を代替検査してはならない。
- `review-response` の 4 値分類を上書きしてはならない。
- `accepted` 以外を一括修正へ入れてはならない。
- 修正前の独立確認を一般的な品質審査や別案の設計に使ってはならない。
- 親の採用理由、調査経緯、全体設計、コード差分、修正後成果物を独立確認の入力へ含めてはならない。
- 独立確認の失敗後に親へ別の修正案を再提案させてはならない。

## 完了チェック

- 最初のレビュー単位を起動する前に固定入力を台帳へ記録した。
- 要件契約候補の全 `RR-OBL-*` と `RR-CONTRACT-1` を `必須` とし、`残存記録` にしていない。
- 初回並列展開、`review-response`、修正前の新規独立確認、一括修正、対応後監査が上限内である。
- 候補受付を閉鎖した。
- 判定不能（検査被覆の欠損）を指摘へ変換していない。
- `accepted` だけを一括修正の対象にした。
- 修正前処分案を外部化し、`requirement-review` の `accepted` の削除・保持・追加の意味と認可元を記録した。その他のレビュー種別では既存の修正契約を記録した。
- 一括修正前に新規独立確認を行い、確認者、許可入力、除外入力、判定、不一致時の処遇を記録した。
- 変更と交差する単位だけを同じ検査で再実行した。
- 修正後確認一式を確認した。
- 残存領域と再開条件を記録した。
- 修正前の独立確認を一括修正後に再実行していない。
