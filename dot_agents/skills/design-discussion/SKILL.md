# 設計相談

設計相談の目的は、提示された案を完成させることではない。
対象の現実に対して、より妥当な問題像と設計判断を得ることである。

問題像と候補案はどちらも更新可能な仮説として扱う。
候補案は問題を解く手段であると同時に、問題の捉え方を検査するための
プローブでもある。案を考えた結果、元の問題設定、責務配置、前提が
間違っていると分かったなら、案を守らず問題像を更新する。

候補案を受けたら、詳細化する前に、その案が必要になるためには
何がどこで問題でなければならないかを逆算する。
その問題構造を、依頼、対象の実態、制約、実行経路と照合する。
照合して問題がなければ、反対意見を作る必要はない。
矛盾があるなら、案の精緻化より先にその矛盾を扱う。

以下は設計を考えるための原則であり、チェックリストではない。
現在の論点を実際に左右するものだけを使う。
全項目を回答に列挙したり、使ったことを自己申告したりしてはならない。

## 問題の捉え方

### 症状と原因

問題が観測された場所と、問題を生んでいる責務は一致するとは限らない。

局所的な異常へその場で補正を加える前に、同じ原因から生じる兄弟事例が
ないかを見る。複数の経路に同じ補正が必要になるなら、補正を置く場所より
上流に原因や責務がある可能性が高い。

最小変更とは、変更行数や変更ファイル数だけを最小にすることではない。
誤った責務に小さな修正を置くより、原因を所有する場所を一度直す方が
システム全体では小さいことがある。

### 適用域

一つの失敗を、必要以上に広い問題へ一般化しない。

ある方法が特定の層、入力、環境では成立しないことと、
その方式全体が成立しないことは別である。
逆に、局所的に成功する経路があることだけで全体の問題を否定してもならない。

障害や制約がどの範囲に実際に作用するかを考え、
生き残る部分と成立しない部分を混同しない。

### 層と独立した軸

一見矛盾する観測は、異なる層や独立した軸について述べていることがある。

一つの説明へ無理に統合する前に、責務、時間、実行環境、入力の種類などが
異なっていないかを見る。独立した問題を一つの仕組みで同時に解こうとすると、
不要な結合を生みやすい。

### 答えられる問い

観測できない内部状態や、証明手段のない完全性を直接要求する問いは、
設計によって答えられる問いとは限らない。

その場合は、実際の判断に必要な情報を保ったまま、
観測可能な証拠や検証可能な結果へ問いを置き換える。
置き換えても残る不確実性は、解決したことにしない。

### 現実との残差

設計上の説明で現実をすべて説明できないなら、説明ではなく問題像の方を疑う。

実行、実機、利用者の反応など、現実との衝突でしか解消できない不確実性はある。
それを推論で消したことにせず、必要なら安価に確認できる形や、
失敗しても影響を限定できる形を選ぶ。

## 責務と知識

### 責務の位置

判断は、その判断に必要な知識を所有する場所へ置く。

下位層だけが知っている事実を caller が解釈しなければならない、
複数の caller が同じ判断を再実装している、
同じ条件分岐が各所へ散っている、といった状態は、
責務が外へ漏れている兆候である。

責務を移すときは、コードの位置だけではなく、
誰が事実を知り、誰が判断し、誰が結果を保証するかを見る。

### 変更理由

同じ理由で変わるものは一緒に置き、
異なる理由で変わるものは不必要に結合しない。

現在存在する複数の変更軸を一つの抽象へ押し込むと、
片方の変更が他方へ波及する。
一方、まだ存在しない将来の変更理由を想像して抽象を作ると、
仮想的な柔軟性のために現在の複雑性を支払うことになる。

実在する変更理由と、推測上の将来変更を区別する。

### 情報隠蔽と局所性

設計判断に必要な知識は、それを所有する場所へ閉じ込める。

caller が内部形式、保存方式、処理順序、回復手順などを知る必要があるほど、
その知識はシステム全体へ拡散する。
一つの設計判断を変更するときに多くの場所を同時に修正する必要があるなら、
隠すべき知識が interface の外へ漏れている可能性がある。

情報隠蔽の目的はコードを隠すことではなく、
変更の影響と理解に必要な知識を局所化することである。

## 状態

状態を一つ増やすたびに、その状態の所有、更新、初期化、失敗、
他の状態との整合性という義務が生まれる。

既存の事実から導出できる値を独立した状態として保持すると、
同じ事実を二つの場所で表現することになり、同期問題が生まれる。
導出で十分なら状態を増やさない。

複製が必要な場合は、どれが事実の正本で、他がキャッシュ、ミラー、
導出結果のどれなのかを区別する。
二つの表現を同時に正本として扱わない。

状態を保持する場所と、その状態を変更する判断の所有者が離れすぎると、
不変条件を守る責務も分散する。

## 構造と interface

interface は caller が目的を達成するために必要な知識を公開し、
それ以外の設計判断を内部へ隠す。

小さい interface そのものが目的ではない。
情報を隠しすぎた結果、caller が内部事情を推測したり、
複数の低水準操作を正しい順序で組み立てなければならないなら、
複雑性を隠せていない。

新しい層、wrapper、adapter、interface は中立ではない。
それぞれ新しい名前、契約、失敗経路、変更点を増やす。
その境界が実際の変更理由や複数の実装を分離していないなら、
単なる中継層になっている可能性がある。

module、interface、seam、depth、locality が設計判断の中心になる場合は、
`codebase-design` の原則を使う。
その定義をこの技能で複製しない。

## 複雑性

新しい状態、抽象、層、設定、ツール、依存関係を導入する側に
立証責任がある。

新しい仕組みを作る前に、問題そのものをなくせないか、
既存の責務配置を直せば済まないか、
既存のコード、言語、基盤、標準機能、既存依存関係で解けないかを考える。

それでも新しい仕組みが必要なら、
どの具体的な問題を引き受け、何を単純にするために存在するのかが説明できるべきである。

ただし、削減そのものを目的にしない。
正しさ、安全性、必要な検証、必要な回復能力まで削るのは単純化ではない。

## 失敗の意味

失敗を処理する層は、その失敗について意味のある判断または回復ができなければならない。

回復できない失敗を成功、空値、欠損、既定値へ変換すると、
上位層から判断材料を奪い、壊れた状態を正常系へ混ぜることになる。

一方、下位層が完全に回復できる内部事情まで無条件に上位へ漏らす必要もない。

失敗を変換するなら、その層が実際に回復を所有しているか、
または上位層にとって有意味な失敗へ変換していることが必要である。

可観測性と回復可能性は別である。
回復できなくても、何が失敗したかを利用者や上位層が判断できる必要がある場合がある。

## 対象の現実

一般的な設計原則、パターン、慣習は、対象システムの事実より強い根拠ではない。

実行時、プロトコル、ライブラリ、基盤、ハードウェア、
既存コードの契約によって設計判断が変わるなら、その事実を優先する。

案を成立させる重要な仮定が未確認なら、
一般論で穴を埋めず、設計判断を左右する範囲で確認する。
確認そのものが目的になって設計作業を置き換えてはならない。

## 候補案と比較

最初の案を守る必要はない。
案を考えることで問題像が変わったなら、新しい問題像から案を考え直してよい。

実質的に異なる問題設定や設計構造が成立するときは比較する。
比較のためだけに、採用可能性のない架空の代替案を作らない。

候補は抽象的な「良さ」で順位付けせず、
対象の制約、変更理由、所有する責務、追加する複雑性、
失敗時の挙動と結びつけて比較する。

元の案が最も妥当なら、そのまま採用してよい。
別案を出すこと自体は成果ではない。

## 応答

原則をチェックリストとして消化した結果を返さない。
「各観点を確認しました」といった自己申告も不要である。

現在の設計判断を実際に左右する論点だけを自然に議論する。
不確実性も、判断に影響するものだけを表に出す。

問題像が不安定なら、その状態で詳細設計を完成させない。
一方、十分に理解できている部分を、形式上の手順のために議論し直さない。

定型の設計書、比較表、質問票は、依頼された場合または
その形式自体が現在の判断に必要な場合だけ作る。
