# 文体の方針

文体の観点では、文章の表現と体裁に関する方針を示す。
誤字、脱字、余字、固有名詞や用語の明らかな誤記は誤記の観点で扱う。

## 太字・斜体構文の境界

太字（`**`）と斜体（`*`）の構文は、前後の文字が ASCII 文字でない場合、構文の外側に ASCII 空白を置く。日本語文字や全角記号に隣接した構文が、表示環境でそのまま表示される問題を避けるためである。

文末の句点などの全角記号を強調範囲に含める場合は、記号の後ろに不自然な空白を置かず、構文の終了後と次の文の間に空白を置く。

```markdown
悪い例は**こうだ**。
良い例は **こうだ。**
```

## 表記揺れの検出

同じ概念、同じ作業、同じ資料、同じシステム、同じ組織を指す表現は、文書内で同じ表記に統一すること。
本文に表記ルール、用語集、正式名称、略称の指定がある場合は、それを正として扱う。

表記揺れとして扱うもの:

- 表記ルールと本文中の表記が一致していないもの。
- 同じ概念を指す固有名詞、略称、和名、英名、および英単語とその日本語訳が混在しているもの。
- 同じ資料や項目を指す可能性が高い日本語名と略称が混在し、本文だけでは別物として区別できないもの。

表記揺れを指摘する場合は、揺れている複数の表記と、それぞれの出現位置を `対象箇所` に示す。
本文中に表記ルールがある場合は、その表記ルールを `根拠` に接続する。
同じ概念かどうかが本文だけで確定できない場合は、表記揺れとして指摘せず `判定不能` とする。

正式名称や禁止表記に含まれる語が、指標名、画面名、ログ名、資料名などの複合名詞の一部として出ている場合は、
同じ役割、作業、資料、システム、組織を指すと本文から判断できるときだけ表記揺れとして指摘する。
別概念の名称要素である可能性が残る場合は、問題を断定しない。
その語を表記ルールの対象に含めるかどうかが本文だけで決まらない場合は、表記揺れとして断定しない。

## 本文の言語に合わない語の混入

日本語本文では、読者向け説明、見出し、項目名、注意文を日本語表記で書くこと。
日本語表記には、日本語で定着した漢字、ひらがな、カタカナによる表記を含む。外国語由来であることだけを理由に、定着したカタカナ表記を問題としてはならない。
アルファベット表記、略称、内部呼称を使う場合は、その出現箇所で原表記そのものを必要とする用途を確認する。

残してよいもの:

- 原表記の正確な文字列が、読者の操作、検索、照合、または概念の識別に必要なもの。
- 日本語の対象読者が通常その表記で識別する頭字語。

指摘候補にするもの:

- 読者向けの説明や名称として使われているアルファベット表記に、正確な文字列を必要とする用途がない箇所。
- 内部識別子だけを読者向けの役割説明や名称として使っている箇所。
- 略称や内部呼称が定義されず、読者が指す概念を特定できない箇所。
- 技術用語、略称、内部呼称の意味、役割、参照先を、想定読者が本文から特定できない箇所。
- アルファベット表記と日本語を継ぎはぎした結果、主語、述語、修飾先、語同士の関係を本文から読み取れない箇所。
- 本文で使われている日本語表記から、概念の種類、対象範囲、操作、責務、工程または状態上の位置を読み取れない箇所。
- 同じ概念に複数の表記を使っている箇所、または区別が必要な異なる概念を同じ表記へまとめた箇所。

対象本文の主語、述語、修飾関係、参照関係、用語の定義と用法から直接確認できる読者上の破綻を指摘する。

表記の適否は書き手やレビュアーの違和感ではなく、原表記が担う用途と、対象本文中の定義、用法、概念関係に照らして判断する。
根拠が不足して表記の適否を決められない場合は、推測した置換案を指摘にせず `判定不能` として残す。

## 冗長な語句の削除

以下の語句が含まれている場合、削除して文意が通るかを確認する。

- 「としては」
- 「においては」
- 「に対しては」
- 「については」

削除しても文意が通るものを、冗長な語句として指摘候補にする。
削除すると文意が通らない場合は、冗長語句ではなく文構造の問題として扱う。
ただし「構文としては正しいが仕様としては誤りである」のように明示的な対比構文で使う場合は残してよい。

## 書き手都合の前置きの削除

「この文書では簡潔にまとめる」「以下では詳細な経緯は扱わない」のような前置きが、読者に必要な対象説明ではなく、執筆上の都合や指示への応答を述べているだけなら削除する。
残す場合は、その文が本文の対象範囲、判断条件、読者の誤解防止に本当に必要かを確認する。
執筆方針ではなく主題を直接書けるなら、主題の説明へ書き換える。

## 曖昧な範囲表現の回避

範囲を説明する際に、以下の語句を用いて範囲を曖昧にしないこと。

- 「など」
- 「等」

範囲を説明する際に「設定やログなど」と書いた場合、読み手は「など」に何が含まれるかを判断できない。
「など」「等」を使う場合は例を示す際に限定的に使うこと。
列挙が網羅的であれば「など」を外す。
網羅できない場合は、列挙した項目の上位概念で範囲を示すか、条件を明記して範囲を限定する。

## 曖昧な推量表現の回避

以下の推量表現は避けること。

- 「思われる」
- 「考えられる」
- 「可能性がある」

事実であれば断定し、不確かであれば根拠や条件を明示する。

条件下で発生する事象を記述する場合は、推量ではなく条件を明示した表現を使う。

- 避けるべき表現: 「障害が発生する可能性がある」（根拠が不明）
- 許容する表現: 「メモリが不足した場合、障害が発生する」（条件を明示）
- 許容する表現: 「設定値が閾値を超えると、処理が中断される」（条件を明示）

「〜する場合がある」は、発生条件が前文または同文中に明示されている限り許容する。
条件が示されていない「〜する場合がある」は推量表現と同様に扱い、条件を追記するか断定に書き換えること。

## 文体の統一

同一の文書内で文体を混在させないこと。
同じ主体の同じ動作を説明するときは、同じ述語を使うこと。
たとえば「確認します」と「確認いたします」が同じ動作を指す場合は、どちらか一方に統一する。
ユーザーが文体を指定していない場合は、本文中で多く使われている文体、または読み手に余計な敬語関係を生まない簡潔な文体に寄せる。

## 日本語文中の不自然な空白

日本語の文中で、英単語、数値、記号との境界ではない部分に空白がある場合、読者は不自然に感じる。
日本語の語と語の間に空白があると、読者はそこに意味があるかと迷う。

英単語との境界（例: 「AI を使う」）は自然だが、日本語の語と語の間の空白（例: 「却下 や 対象外」「要対応 の修正」）は不自然である。
意図的な区切りでない限り、空白を削除して一語に繋ぐことを検討する。
