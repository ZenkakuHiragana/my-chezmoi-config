# レビュー対応

既に固定された指摘だけを、変更前の対象で再現して分類する。指摘を修正したり、新しい指摘を探したり、レビュー全体の終了や変更の実施判断を決めたりしない。

## 入力

次を開始前に確認する。

- 変更前の検査対象。依頼に比較基準が含まれるときは、その基準も確認する
- 依頼で認められた目的、範囲、受け入れ結果、保つ条件、確認方法
- 開始前に固定された指摘の集合
- 各指摘の対象箇所、破綻、根拠、確認方法、侵害するとされる条件
- 再現に使う引用、操作、テスト、ログ、生成物、必要な権限

指摘に対象箇所、破綻、根拠、確認方法、条件との関係がない場合は、正しい指摘として分類せず、入力不足として分離する。レビューの別の出力形式や別の実行者を前提にしてはならない。

## 一回の処理

入力された指摘、対象、条件、確認方法を開始前に固定し、各指摘を一度だけ次の順で処理する。

1. 指摘の対象と、侵害するとされる条件を依頼の目的、範囲、受け入れ結果、保つ条件へ直接照合する。
2. 指摘に条件との関係がない場合は入力不足として分離し、分類しない。条件との関係を確認でき、現在の作業の対象外である場合だけ `対象外` とする。対象外の範囲を新しい要求へ変えてはならない。
3. 指摘に示された同じ確認方法を、変更前の対象へ適用する。
4. 情報、環境、権限が不足して結果を決められない場合は `要調査` とする。不足を `採用` または `却下` へ丸めてはならない。
5. 受け入れ結果または保つ条件の観測可能な失敗を再現した場合は `採用` とする。
6. 確認方法を完了し、指摘された失敗が存在しない、または根拠が対象と一致しない場合は `却下` とする。

途中で指摘を追加してはならない。同じ指摘を複数の分類へ入れてはならない。確認の被覆が欠けているという記録は、個別指摘として分類せず、入力不足として返す。

## 分類条件

### `採用`

確認方法のどの手順が、対象のどの観測値で失敗したかを記録する。条件との関連、一般論、将来危険の推測だけで `採用` にしてはならない。

### `却下`

同じ確認方法を完了した結果、指摘された失敗を確認しなかった根拠、または指摘の根拠が対象と一致しない箇所を記録する。感想や好みだけで `却下` にしてはならない。

### `要調査`

試みた確認方法、不足する情報・環境・権限、不足によって確定できない理由、再開に必要な条件を記録する。

### `対象外`

指摘の対象と条件を、現在の目的、範囲、受け入れ結果、保つ条件へ照合した結果を記録する。対象外であるという結論を、新しい要求や修正理由へ変えてはならない。

## 返す内容

各指摘について、分類、対象箇所、対応する条件、実行した確認方法、変更前の観測、根拠または不足、再開条件を返す。`要調査` には不足と再開条件、`却下` には反証根拠、`対象外` には条件との照合、`採用` には再現した失敗を必ず含める。固定の表、識別子、外部化形式は要求しない。

最後に、`採用` となった指摘だけを修正対象として列挙し、対象外の範囲、保つ条件、修正後に再実行する同じ確認方法を示す。`採用` がなければ、その事実を返す。

## 禁止事項

- 対象成果物を編集してはならない。
- 新しい指摘を探索または生成してはならない。
- 指摘の確認方法を、都合のよい別の確認へ置き換えてはならない。
- `要調査` または `対象外` を黙って解消してはならない。
- 分類結果から修正の実施や手続き終了を決めてはならない。

## 完了条件

- 入力された対象、条件、指摘、確認方法を開始前に確認した。
- 分類対象の指摘を各一回だけ分類し、入力不足の指摘を分類せず分離した。
- `採用` の全件で変更前の失敗を再現した。
- `却下` の全件に反証根拠がある。
- `要調査` の全件に不足と再開条件がある。
- `対象外` の全件に条件との照合がある。
- `採用` だけを修正対象として返した。
- 対象を編集せず、指摘追加、修正の実施、手続き終了を行っていない。
