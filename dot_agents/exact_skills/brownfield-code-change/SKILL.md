# 既存のコード・スキルの変更

既存の利用者と設計を持つソフトウェアやスキルへ変更を加え、依頼された結果が実際に成立したところまで仕上げる。
スキルはエージェントが読む指示として扱い、本文、参照資料、補助プログラムと、それを読み込んで実行する経路を対象にする。

## 変更する対象を確定する

編集を始める前に依頼が実際のどのコード・指示と利用経路に対応するかを確認する。
対象だけでは挙動が分からない場合は参照先や利用側までたどり、適用される仕様や既存の検証も確認する。

この確認で得た事実に合わせて対象理解を直す。
現在のコードや指示にそう書かれているという理由だけで、その状態を保持すべき仕様とはみなさない。

依頼された結果や守るべき条件を、現在有効なユーザー発言と確認した対象から確定できない場合は、一般知識や慣例で不足を補って実装へ進まない。
確認できたことと、何が決まらないため変更できないかをユーザーへ返す。

## 依頼を後続へ保持する

現在有効なユーザー発言を、後続の作業者が直接参照できる `要件契約` として固定する。

ユーザー発言とその参照先だけで依頼を確認できるなら、それ以上の意味を追加しない。
探索によって後続の行動を拘束する内容が新たに確定した場合だけ `requirement-contract` に従って候補を作り、
その追加部分を `requirement-reviewer` と `review-orchestration` で独立に確認してから採用する。

作業中にユーザーが依頼を訂正または変更した場合は、すでに作成した `要件契約` を書き直し、以後の判断も現在有効な内容へ合わせる。

## 実装前に設計する

新しい機能の実装、既存機能の拡張、または入出力・データの表現・状態の所有・処理の責務を新設もしくは変更する仕事では、
本体のコード、スキルの本文・参照資料・補助プログラムを編集する前に `software-design` に従って設計を作り、独立した確認を終える。
スキルでは、入力と成果物の約束、情報や記録の表現と管理、判断・操作を担う主体、開始・終了・委譲・受け渡しの条件を、
上記の入出力・データの表現・状態の所有・処理の責務へ対応させる。この対応は、実装中やレビュー後に設計へ戻る判断にも使う。

設計工程では、今回の変更とその接続先を扱う。既存の設計から決まっている部分を新しく決め直さない。
確認した設計、利用例、変更例、確認結果をそのまま実装へ使い、別の実装計画や要件へ書き写さない。

設計上の選択はユーザーの依頼や既存の仕様ではないので新しい要求として `要件契約` へ追加しない。

実装中またはレビュー後の修正で、確認した入出力の約束、データの表現、状態の所有、処理の責務を変更する場合は、変更後の設計に依存する確認を `software-design` に従って行う。

## 変更を作る

依頼された結果に必要な変更を、既存の責務分担と利用経路に沿って行う。

変更によって既存の対応関係が崩れる場合は、認可された変更を成立させるために必要な追従も揃える。
依頼とは独立した問題の修正、根拠のない互換動作や代替経路、ついでの再設計は持ち込まない。

実装方法の選択によって利用者が受け取る結果や既存の契約が変わる場合、その選択が依頼・仕様・既存設計から決まらなければ勝手に確定しない。

変更前から存在する利用者の編集を、自分の変更と混同して上書きしたり取り消したりしない。
編集する対象の作業開始時の内容を、後から参照できることを編集前に確かめる。履歴から復元できない未コミット・未追跡の内容は、編集前に作業記録へ残す。
作業記録は対象の規則に従い、既存のものを使うか、なければ用意する。依頼を保持する `要件契約` とは分けて扱う。

## 実際の結果を確認する

変更後は対象に用意されているビルド等の検証方法を使い、依頼された結果を判定できる方法で確認する。
スキルでは、適用される指示の品質基準へ照合し、実際の読み込み経路と実行者が使える情報から、判断・操作・受け渡しと結果を確認する。
指示どおりに経路をたどった確認と、エージェントが実際に実行した結果を区別し、前者を後者の証拠にはしない。
構文検査やコマンドの正常終了だけで、求められた動作まで成立したことにはしない。

不具合を修正した場合は、問題の成立を確認した条件を変更後にも適用する。
同じ対象と条件ですでに得た有効な結果は再利用し、同じ確認を繰り返すためだけに実行しない。

検証結果が想定と違った場合は、その結果に合わせて対象理解と実装を見直す。
実装を正しいことにするために、期待結果や検査条件を変更しない。

## レビューして完了する

実装とその検証を終えたら、変更後のコードやスキル本文とその参照先を `artifact-review` と `review-orchestration` でレビューする。
レビューでは今回の依頼を示す `要件契約` と、対象の要求を定める既存の正本をそれぞれ直接参照させる。

親エージェントは、指摘の成立を確認した後、この節に従って今回の対応を決める。
成立したことだけで修正義務が生じるわけではなく、指摘に添えられた改善案も変更の認可にはならない。
その回の全指摘について、以下の依頼との照合と原因確認を終えてから、今回の扱いと、解消する問題をまとめて直す範囲を決める。それまでは修正を始めない。
指摘、確認した根拠、対応を選んだ理由、修正前後の差分を、後の編集で失われない形で作業記録に残す。履歴から再取得できるものは参照でよい。後の回ではこの経過を使う。

### 今回の依頼との関係を確かめる

成立した指摘ごとに、失われる動作や性質、発生条件、その条件へ到達する利用経路を確認する。
保守上の問題では、実際の定義や更新処理をたどり、一つの変更に対して誰がどこを揃えなければならないかを示す。
現在の誤動作と、変更時に発生する作業や漏れの危険を区別し、仮想の機能追加から対応義務を作らない。

その影響を、今回求められた結果、適用仕様、既存の利用側が依存する約束、成果物に適用される品質基準へ照合する。
何が成立しなくなるかと、その約束の出どころを対応付ける。設計者が選んだ実現方法を要求として固定しない。

ユーザーが明示した非対応・非保証は、元の発言を読み、対象の条件と許容された結果の範囲を確かめる。
その範囲に収まる影響は、欠陥が成立していても、その指定を覆して修正しない。
同じ条件で別の性質まで失われる場合は、それも許容されたとはみなさない。例えば、狭い画面で全文を表示しない指定は、アプリケーションの停止まで許す指定ではない。
指定を守ったまま、今回保つべき性質を回復できるなら解消する。指定や外部仕様を変えなければ解消できない場合は、その変更を実行せず、元の指定、判明した影響、選択によって変わる結果をユーザーへ返す。

設計者だけが選んだ非保証は、ユーザーの指定と同じ権威を持たない。
その判断が前提にした入力、利用経路、影響を指摘の事実と比べ、前提が崩れた箇所と失われる性質を設計の検討へ戻す。
設計に書かれていることだけを免除の根拠にせず、指摘が成立したことだけを撤回の根拠にもしない。

以上の指定と認可を守り、今回の変更で持ち込んだ欠陥と、依頼された結果や守るべき約束の成立を妨げる欠陥は、この作業で解消する。
修正の費用が大きいことだけを理由に、必要な品質を満たさないまま完了にしない。
変更前からある独立した欠陥で、今回の依頼の成立に関わらないものは、修正範囲に加えず、成立条件と影響を報告する。
この扱いにするには、作業開始時の内容と今回の変更の影響先を確認し、同じ問題が変更前にもあり、今回の要求を妨げないことを確かめる。
「高品質に」のような一般的な望みだけを、既存の独立した問題をすべて直す根拠にしない。

判断に必要な事実を確認できなければ、取得できる資料や実物を調べる。未確認のことを「以前からある」「影響が小さい」「対象外」として処理しない。
ユーザーの選択が必要なものと、自分で調べられる不足を分け、判断待ちの事項に依存しない作業を進める。

### 修正の経過から原因を確かめる

成立した指摘全体について、今回の成果物、作業開始時の内容、前の回までの修正前後を、指摘が成立する同じ条件で比べる。
作業開始時にあった利用者の未コミット変更も比較の基準に含める。現在のコードや指示だけから発生時期を推測しない。
既存の記録や差分で確認できる事実は再利用し、因果関係が決まらない箇所をコードや指示の追跡、実行で確かめる。

各問題について、結果を変える値、その値の所有者と更新元、依存する処理をたどる。
スキルでは、判断に使う情報や記録、その取得・更新を担う主体、依存する指示と受け渡しをたどる。
複数の指摘が同じデータ表現、更新規則、責務分担に由来するか、前の修正で加えた状態、同期、分岐、呼び出し順が今回の問題を生んだかを確かめる。
同じファイルにあることや、修正後に指摘されたことだけを共通原因や因果関係の根拠にしない。
以前からある独立した欠陥を新しく発見した場合は、修正方法が次の欠陥を生んだ場合と分ける。

前の修正が新しい問題を生んだ場合は、前に解消しようとした問題と今回の問題を並べ、両方を生む値の持ち方や処理の約束を検討対象にする。
前の修正を維持することを前提に補正を足さない。複数の問題が同じ判断に由来する場合も、その判断を一緒に扱う。
一方、既存の約束に従って誤記や計算を正せば解消する独立した問題まで、一括して再設計しない。
レビューの回数、指摘数、変更行数から、設計へ戻るかどうかを決めない。

### 直し方を比べて変更する

直し方は、指摘された箇所へ手を加える案を既定路線にせず、確認した原因と守る条件から選ぶ。
候補について、問題を解消する仕組みと、増減する状態、分岐、同期、呼び出し順、変更時の追従箇所を、修正前と同じ利用・変更の場面で比べる。
追加または残す負担には、それを除くと失われる動作や約束を対応付ける。分岐が増えること自体を品質低下とはしない。
一件の指摘を消しても、別の約束を破る案は採らない。

同じ要求と既存の約束を保ち、同期や追従の仕事を減らせる案は、その比較結果を根拠に選ぶ。
負担の交換がある場合は、何が減り何が増えるかを示し、今回の目的と既存の方針に照らして選ぶ。別の場所へ同じ手動同期を移しただけなら、同期を減らしたことにはしない。
利用者が受け取る結果や認可範囲を変える選択が残る場合は、「変更を作る」に従ってユーザーへ返す。

選んだ案がデータ表現、状態の所有、入出力の約束、処理の責務を変える場合は、「実装前に設計する」に従って `software-design` に戻り、その変更に依存する確認を行う。
その際は、ここまでに確認した原因と影響を、利用例・変更例で確かめる条件へ加える。関係しない設計工程までやり直さない。
これらを変えず、確認済みの約束に従って原因となる実装の誤りを正す案では、局所修正する。
修正案を採れなかったことを、元の欠陥が解消したことにしない。

### 修正後の確認と完了

修正が入った場合は、元の問題が成立した条件と、修正の影響を受ける利用経路・既存の約束について、検証と独立レビューを行う。
`artifact-review` と `review-orchestration` による再レビューの対象には、修正の差分だけでなく、変更した定義の利用側と、入出力や状態の変化が伝わる先も含める。
前の回から対象・条件が変わらず、修正の影響も受けない検証・レビュー結果は再利用する。
影響先を確認せずに差分の行だけへ絞ったり、影響しない部分の全面レビューを繰り返したりしない。

新しく得た指摘にも、この節の手順を適用する。
今回の依頼の成立に関わらず、修正の影響も受けない箇所から、さらに改善候補を探し続けることは必須工程にしない。

最後に現在有効な依頼へ戻り、求められた結果と守るべき性質が成立し、必要な追従・検証・レビューが終わり、今回解消すべき問題が残っていないことを確認して完了とする。
すべての指摘を消すことを終了条件にせず、未解消の指摘がある場合は、成立条件と影響、今回修正しない根拠となった指定や要求との関係を最終報告に示す。
ユーザーの指定を見直す材料となる影響も、指定に従ったという理由で報告から落とさない。

必要な確認が `要調査`・`判定不能` のまま、または依頼の成立に必要なユーザーの選択が残る場合は、完了としない。
依頼された結果を確認できないまま作業を終える場合は、現在成立している状態、未解決の問題、続行できない理由と必要な判断を返す。
