# 既存コードの変更

既存の利用者と設計を持つソフトウェアへ変更を加え、依頼された結果が実際に成立したところまで仕上げる。

## 変更する対象を確定する

編集を始める前に依頼が実際のどのコードと利用経路に対応するかを確認する。
対象だけでは挙動が分からない場合は参照先や利用側までたどり、適用される仕様や既存の検証も確認する。

この確認で得た事実に合わせて対象理解を直す。
現在のコードにそう書かれているという理由だけで、その状態を保持すべき仕様とはみなさない。

依頼された結果や守るべき条件を、現在有効なユーザー発言と確認した対象から確定できない場合は、一般知識や慣例で不足を補って実装へ進まない。
確認できたことと、何が決まらないため変更できないかをユーザーへ返す。

## 依頼を後続へ保持する

現在有効なユーザー発言を、後続の作業者が直接参照できる `要件契約` として固定する。

ユーザー発言とその参照先だけで依頼を確認できるなら、それ以上の意味を追加しない。
探索によって後続の行動を拘束する内容が新たに確定した場合だけ `requirement-contract` に従って候補を作り、
その追加部分を `requirement-reviewer` と `review-orchestration` で独立に確認してから採用する。

作業中にユーザーが依頼を訂正または変更した場合は、すでに作成した `要件契約` を書き直し、以後の判断も現在有効な内容へ合わせる。

## 実装前に設計する

新しい機能の実装、既存機能の拡張、または入出力・データの表現・状態の所有・処理の責務を新設もしくは変更する仕事では、
本体のコードを編集する前に `software-design` に従って設計を作り、独立した確認を終える。

設計工程では、今回の変更とその接続先を扱う。既存の設計から決まっている部分を新しく決め直さない。
確認した設計、利用例、変更例、確認結果をそのまま実装へ使い、別の実装計画や要件へ書き写さない。

設計上の選択はユーザーの依頼や既存の仕様ではないので新しい要求として `要件契約` へ追加しない。

実装中またはレビュー後の修正で、確認した入出力の約束、データの表現、状態の所有、処理の責務を変更する場合は、変更後の設計に依存する確認を `software-design` に従って行う。

## 変更を作る

依頼された結果に必要な変更を、既存の責務分担と利用経路に沿って行う。

変更によって既存の対応関係が崩れる場合は、認可された変更を成立させるために必要な追従も揃える。
依頼とは独立した問題の修正、根拠のない互換動作や代替経路、ついでの再設計は持ち込まない。

実装方法の選択によって利用者が受け取る結果や既存の契約が変わる場合、その選択が依頼・仕様・既存設計から決まらなければ勝手に確定しない。

変更前から存在する利用者の編集を、自分の変更と混同して上書きしたり取り消したりしない。
最初にコードを編集する前に、作業前の対象（今回の作業で変更を加える前のコード）を後で比べられる形で残す。未コミットの変更がある場合は、その差分も作業記録に保存する。「レビューして完了する」で、指摘が作業前からある問題かを確かめるために使うからである。

## 実際の結果を確認する

変更後は対象に用意されているビルド等の検証方法を使い、依頼された結果を判定できる方法で確認する。
構文検査やコマンドの正常終了だけで、求められた動作まで成立したことにはしない。

不具合を修正した場合は、問題の成立を確認した条件を変更後にも適用する。
同じ対象と条件ですでに得た有効な結果は再利用し、同じ確認を繰り返すためだけに実行しない。

検証結果が想定と違った場合は、その結果に合わせて対象理解と実装を見直す。
実装を正しいことにするために、期待結果や検査条件を変更しない。

## レビューして完了する

実装とその検証を終えたら、変更後のコードを `artifact-review` と `review-orchestration` でレビューする。
レビューでは今回の依頼を示す `要件契約` と、対象の要求を定める既存の正本をそれぞれ直接参照させる。

`review-orchestration` の手順で確かめるのは、指摘された問題が検査対象で成立するかどうかまでである。
成立した指摘をこの作業でどう扱うかは、この節の手順で決める。
指摘が成立したことだけを理由に修正を始めない。指摘に書かれた改善案も、そのまま変更の指示として使わない。
個々の指摘が正しいことと、指摘を一件ずつ直していく進め方が正しいことは、別の事柄だからである。

その回のレビューで成立したすべての指摘について、扱いと直し方を決めるまで、コードを編集しない。
一件を先に直すと、その直し方が残りの指摘を読むときの前提になり、複数の指摘が同じ原因から出ていることを見落とすからである。
回ごとに、成立した指摘、それぞれの扱いと直し方、その回の修正の差分を作業記録に残す。

### 指摘と今回の変更の関係を確かめる

成立した指摘ごとに、作業前の対象へ同じ条件を当てる。
作業前の対象は、「変更を作る」で残したものを使う。

- **作業前からある問題：** 作業前の対象でも、同じ条件で同じ問題が起きる。
- **今回の変更が生んだ問題：** 作業前の対象では、同じ条件で問題が起きない。指摘された箇所が作業前の対象に存在しない場合も、これに当たる。

指摘の条件が今回変更したコードを通ることだけを理由に、今回の変更が生んだ問題にしない。作業前の対象でも同じ問題が起きるなら、作業前からある問題である。
作業前からある問題とするのは、作業前の対象を実行するか、該当箇所の作業前の内容を読んで、同じ問題が起きることを確かめた場合だけである。
確かめられない指摘は、今回の変更が生んだ問題として扱う。

二回目以降のレビューでは、今回の変更が生んだ問題について、前の回の修正との関係も確かめる。比べる相手は、前の回の修正を加える前のコードである。

- **前の回の修正が生んだ問題：** 前の回の修正を加える前のコードでは、同じ条件で問題が起きない。
- **前の回の修正で解消していない問題：** 前の回に解消すると決めて直した指摘と同じ成立条件で、また成立した。

### 依頼と定めに照らして扱いを決める

成立した指摘ごとに、次の項目を上から順に当てはめ、扱いが決まった項目で止める。

**ユーザーが明示的に定めた条件の問題。**
`要件契約` やユーザーの発言が、指摘の条件について「サポートしない」「保証しない」「対応しなくてよい」のように明示的に定めている場合は、その定めを変えない。
設計の記録が、そのような定めをユーザーの決定として書いている場合も、発言の引用が見つからなくても同じに扱う。
定めの文面が許していることと、指摘の影響を比べる。

- 影響が定めの文面の範囲に収まる場合は、修正しない。例えば「極端に狭い画面では内容を全部表示しなくてよい」という定めに対して、狭い画面で内容の一部が表示されないことは、この場合に当たる。
- 影響が定めの文面の範囲に収まらない場合は、定めの文面を守ったまま解消できる修正があるかを確かめる。停止する、応答しなくなる、状態や保存内容が壊れる、資源を失う、定めが名指ししていない機能や条件にまで影響が及ぶ、などは範囲に収まらない影響である。機能を提供しないと定めることは、これらを許すことではない。
  解消できる修正があれば、次の項目へ進んで解消するかどうかを決める。そのときの修正は、定めの文面を守るものに限る。
  定めを変えなければ解消できない場合は、修正しない。

定めと `要件契約` の求める結果が同じ条件について食い違う場合は、どちらかに合わせて実装せず、その食い違いをユーザーへ返す。

**設計の記録だけが定めた条件の問題。**
設計の記録（今回の作業で作った設計や、既存の設計メモ）が指摘の条件を保証しないと定めていて、その定めをユーザーの決定として書いていない場合、その定めは設計を作った側の判断である。
設計を作った側の判断は、レビューで見つかった事実によって見直す対象である。

定めの記録と指摘を比べ、次のどれかに当たる場合は、定めの前提が事実と合っていない。定めがないものとして次の項目へ進む。

- 定めは、その条件が起きないことを前提にしていた。しかし指摘は、`要件契約` が求める利用の経路でその条件が起きることを示している。
- 指摘の影響が、定めの記録に書かれた結果と違う。
- 指摘の影響に、停止する、応答しなくなる、状態や保存内容が壊れる、資源を失う、のどれかが含まれる。記録にその影響が書かれていても当たる。機能を提供しないと定めることは、これらを許すことではない。
- その定めのために、`要件契約` から引用できる結果や条件、適用される既存の仕様、呼び出し側が依存している約束のどれかが成り立たない。

どれにも当たらず、指摘の条件と影響が定めの記録に書かれたとおりである場合は、設計で考慮して選んだことを指摘が述べ直している。修正しない。
記録が指摘の条件に触れていない場合は、設計で考慮されていなかった条件である。定めがないものとして次の項目へ進む。

**依頼された結果を妨げる問題。**
指摘の現象によって成り立たなくなる結果や条件を `要件契約` から引用できる場合は、作業前からある問題であっても、この作業で解消する。
この扱いにするのは、引用した文が述べる結果を、指摘の条件のもとで実行またはコードの追跡によって確かめ、成り立たないことを確認した場合だけである。
「高品質に」「保守しやすく」のような一般的な望みを、作業前からある問題をこの作業へ取り込む根拠にしない。

**今回の変更が生んだ問題。**
ここまでの項目で扱いが決まらない、今回の変更が生んだ問題は、この作業の成果物の欠陥である。この作業で解消する。
直す手間が大きいことは、解消しない理由にならない。

**作業前からある問題。**
ここまでの項目で扱いが決まらない、作業前からある問題は、「変更を作る」のとおり依頼とは独立した問題であり、この作業では修正しない。
依頼と独立した問題を直すと、利用者が確かめていない変更が差分に混ざり、差分全体を確かめる手間が増えるからである。
ただし、ユーザーが今回の依頼でそのような問題の修正を求めている場合（例えば「既存の機能の漏れも直す」と述べている場合）は、今回の変更が生んだ問題と同じく解消する。

### 直し方を選ぶ

解消すると決めた指摘をすべて並べてから、直し方を決める。

**前の回の修正の上に修正を重ねない。**
前の回の修正が生んだ問題と、前の回の修正で解消していない問題は、ほかの指摘より先に、次の順に扱う。

1. 前の回の修正のコードが、その修正で従わせるはずだった規則（確認済みの設計を含む）に従っていない場合は、実装の誤りとして、以下の「成り立つ理由を分ける」から扱う。
2. 前の回の修正が設計へ戻して作ったもので、コードが確認済みの設計に従っているのに問題が起きる場合は、その設計に問題がある。
   前の回の修正が生んだ問題であれば、この指摘の成立条件を確認の場面と保つ条件に加えて、「設計へ戻す」をもう一度行う。
   前の回の修正で解消していない問題であれば、設計をやり直さず、確認に使った条件と、回ごとの指摘と修正の経過をユーザーへ返す。その成立条件は前の回の設計の確認ですでに当てていたので、同じ確認を繰り返しても新しい情報が加わらないからである。
3. それ以外は、前の回の修正を取り消した状態を出発点にして、前の回の指摘と今回の指摘をまとめ、以下の「成り立つ理由を分ける」から直し方を選び直す。
   前の回の修正の上に局所修正を重ねると、同じ箇所へ手を加え続けることになるからである。

**成り立つ理由を分ける。**
既存の規則が指摘の条件での振る舞いをすでに決めていて、コードがそれに従っていない場合は、実装の誤りである。
ここでいう既存の規則は、`要件契約`、適用される仕様、確認済みの設計、呼び出し側が依存している約束である。従う規則の所在を作業記録に書く。
コメントや文書がコードの実際の動作と食い違っている場合も、実装の誤りに含める。
指摘の条件での振る舞いを決める規則がなく、解消するには新しい振る舞いを決めることになる場合は、設計の考慮漏れである。設計へ戻す。
「設計の記録だけが定めた条件の問題」で定めの前提が事実と合わなかった指摘も、設計へ戻す。

**局所修正の案を作り、足すものを書き出す。**
実装の誤りとした指摘ごとに、指摘された箇所を規則に従わせる案を作り、その案が足すものを差分から作業記録に書き出す。
従わせる規則が定めていない次のものを一つでも足す案は、局所修正として採らず、設計へ戻す。

- 呼び出しをまたいで残る状態（変数、フィールド、キャッシュ、フラグ）
- 別の場所にある値や定義と、手作業で一致させ続けなければならない値や定義
- 呼び出し側が守らなければならない呼び出し順
- タイマー、定期的な確認、常駐する処理、再試行、代替の経路
- 設定項目、公開する操作や型、新しいモジュール
- 振る舞いを分ける分岐
- 入出力の約束、データの表現、状態の所有、処理の責務の変更

これらを足さない案を局所修正と呼び、そのまま採る。
例えば、関数の約束が拒むと定めている入力を検査する分岐を足す案は、規則が定める条件で振る舞いを分けるだけなので局所修正である。
規則が定めていないものを一覧から足すと、依頼にも確認済みの設計にもない新しい決定が、確認を経ないまま入る。新しい決定は、設計と同じ確認を経てから採る。

**共通の原因をまとめる。**
解消する指摘のうち二つ以上が次のどちらかに当たる場合は、それらを一つの問題としてまとめて設計へ戻す。

- 同じ手作業の対応関係（別々の場所にある値や定義を手作業で一致させている関係）の一致漏れである。
- 解消のために、同じ状態、同じ分岐の並び、同じ更新処理へ、一覧にあるものを足す。

同じ対応関係で一致漏れが二つ以上見つかった場合、値を一件ずつ直しても、漏れを許した手作業の持ち方は残る。
同じものへ一覧にあるものを指摘ごとに足すと、それを保守する仕事が指摘の数だけ同じ場所に積み重なる。
指摘が同じファイル、同じ関数、同じ状態にあるだけで、上のどちらにも当たらなければまとめない。

**設計へ戻す。**
設計へ戻すと決めた指摘は、直す前に `software-design` に従って、その解消に関わるデータの表現、状態の所有、処理の区切り、例外で保つものを設計し、独立した確認を終える。
実装前に設計した部分であれば、「実装前に設計する」のとおり変更後の設計に依存する確認を行い、設計工程の全体を繰り返さない。
設計へ戻す理由になった事実（指摘の成立条件、局所修正の案が足すことになったもの、共通に変更する対象、前の回の修正との関係）を、確認で当てる場面と保つ条件に加える。
案を比べた結果、どの案も別の約束を破るか、除いた仕事と同じ仕事を別の場所に増やす場合は、`software-design` の採否の区別に従って選ぶ。
どの修正案も採らなかった場合は、その指摘を解消したことにしない。

**ユーザーへ返す。**
直し方の選択によって、利用者が受け取る結果、既存の入出力の約束、永続状態の扱い、正本や責務の所有が変わり、その選択が依頼・仕様・既存設計から決まらない場合は、「変更を作る」のとおり勝手に確定しない。選択肢と、それぞれを選んだときに利用者が受け取る結果をユーザーへ返す。
ここまでの手順でユーザーへ返すと決めたもの（食い違う定めと依頼、設計へ戻しても解消していない問題、直し方の選択）は、ユーザーの判断に依存しない指摘の修正と検証を終えてから返す。

### 直した後に確かめ直す

修正が入った場合は、その修正後のコードについて必要な検証をもう一度行う。

検証の後、その回の修正の差分を検査対象として、もう一度 `artifact-review` と `review-orchestration` でレビューする。
検査対象には、修正の差分のほか、修正した定義を使う箇所と、修正によって入出力や状態が変わる利用経路を含める。
前の回のレビューで判定できた部分のうち、前の回から変わらず修正の影響も受けない部分は、検査対象に含めない。その部分には前の回のレビュー結果がそのまま当てはまるからである。
前の回に `判定不能` になった範囲は、原因を解消してから検査し直す。

再レビューで成立した指摘も、この節の手順で扱う。
再レビューの検査対象の外にある箇所について指摘が成立した場合も同じ手順で扱うが、それを理由に次の回の検査対象を広げない。

成立した指摘がなくなった時点、または残る指摘がすべて、修正しないと決めたもの、ユーザーへ返すと決めたもの、`要調査` のもののいずれかになった時点で、レビューを終える。
指摘が出なくなるまでレビューを繰り返すことを、完了の条件にしない。
レビューを繰り返せば、今回の変更と関係の薄い改善点も見つかり続ける。それを探し続けることは、依頼を完了させる仕事ではない。

### 完了する

最後に現在有効な依頼へ戻り、求められた変更が実際に成立し、必要な追従と検証が終わっていることを確認してから完了とする。

完了の報告では、成立した指摘のうち解消しなかったものを、扱いごとに分けて示す。
どの指摘にも、成立条件と、起きる現象と影響を書く。そのうえで、扱いごとに次の事実を添え、修正しないと決めた判断と今回の依頼との関係をたどれるようにする。
修正しないと決めた判断が誤っていた場合に、ユーザーが報告から、その判断に使った事実を確かめられるようにするためである。

- 作業前からある問題として修正しなかったもの：作業前の対象で同じ問題が起きることを確かめた方法と結果、`要件契約` から引用できる結果を妨げないこと
- ユーザーの定めに従って修正しなかったもの：定めの引用と、影響が定めの文面の範囲に収まるのか、範囲を超えるが定めを変えなければ解消できないのか
- 設計の記録の定めどおりとして修正しなかったもの：定めの所在と、記録に書かれた条件と影響が指摘の現象と一致したこと
- 設計で案を比べて修正しなかったもの：比べた案と、それぞれが除くものと増やすもの
- ユーザーへ返す選択：選択肢と、それぞれを選んだときに利用者が受け取る結果、または確認に使った条件と回ごとの経過

依頼された結果を確認できない場合と、`要調査` の指摘やレビューで `判定不能` になった範囲が残る場合は、完了したことにしない。
現在成立している状態と、確かめられなかった事柄とその理由を返す。
