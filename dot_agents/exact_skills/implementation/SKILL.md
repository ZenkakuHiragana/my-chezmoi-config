# 実装

依頼された変更を作り、変更後の内容と動作を確かめて仕上げる。

## 実装前の確認

現在有効な依頼と、対象に適用される仕様から、変更する内容と保つべき内容を区別する。
変更前の対象を直接読み、既にある利用者の変更と、これから行う自分の変更を区別できるようにする。
対象だけでは意味や動作が決まらない箇所は、呼び出し元や参照先をたどり、実際の利用され方まで確かめる。
関連するテストや文書も、対象の挙動を定める根拠として照合する。
生成物や実行時の設定が動作を左右する場合は、どの原本と処理から作られるかも確認する。

依頼された結果を確認する方法が対象と仕様から定まらない場合は、編集を始める前に不足を確認する。
依頼と仕様が定めていない選択のうち、どれを選ぶかによって利用者が受け取る結果や既存の契約が変わるものは、自分で決めない。

不具合や指摘の修正では、変更前の対象と根拠を照合し、問題が成立する条件と確認方法を確かめる。
同じ対象・条件について既に得られた確認結果は利用し、同じ確認をやり直すためだけの実行はしない。
問題の成立を確認できなければ、それを理由とする変更は行わない。

## 編集原則

依頼された結果を満たすために必要な変更を、一つのまとまりとして作る。
変更によって利用側が使えなくなったり、関連するテストや説明が実態と食い違ったりする場合は、許された変更範囲内でそれらも揃える。既存の構成や責務分担を、ついでに作り直さない。
互換動作や障害時の代替処理など、別の動作経路を設ける場合は、依頼または既存の契約に根拠があることを確認する。

既存の処理や記述を置き換えるときは、依頼と仕様から保つべきと確認した条件を、置き換え後も満たす。
置き換え後に不要になった処理や記述は、保持を求める契約がなければ取り除く。

修正する指摘が限定されている場合は、その指摘の解消に必要な変更だけを行う。
その変更で新たに生じた不具合は取り除くが、依頼に含まれない既存の問題へ修正を広げない。
編集できる範囲や時点が指定されている場合は、その指定を守る。

## 確認

変更後の対象と、その変更が影響する利用側を読み直す。
書こうとした内容ではなく、実際に書かれた内容から意味や動作を読み取り、依頼と変更前の対象に照らす。
必要な変更の抜け、不要な追加、保つべき内容の欠落がないかを確かめる。

確認方法は、依頼された結果が得られたかを判断できるものを選ぶ。
適用される規則に必須の検査があれば、それも行う。
コードや設定では、利用できる診断やテストを使い、変更した動作を確認する。
構文検査の成功だけで、依頼された動作まで確認したことにはしない。
指示文では、実行者に渡る情報と手順を静的に照合し、必要な判断と動作が成立するかを確認する。
ただし指示文の確認を理由としてその指示が要求する副作用を新たな認可なく実行してはならない。
不具合や指摘の修正では、変更前に問題を確認した方法を変更後にも適用し、同じ条件で問題が解消したことを確かめる。

照合や検査で自分の変更の誤りが分かった場合は、依頼と既に決まった設計の範囲内で修正する。
修正した箇所とその影響先を再確認し、誤りの解消を確かめる。
検査の期待結果は依頼と仕様に従い、実装の出力に合わせて変更しない。
失敗を隠すために、必要な検査や警告を無効にしない。

## 失敗時の扱い

資料の取得やツールの実行に失敗した場合は、その操作が成功したものとして後続へ進めない。
原因を確認し、入力の誤りなど自分で解消できる問題を、許された操作で直して続ける。
操作が拒否された場合は、別の方法で同じ副作用を実現しない。

必要な情報や権限を得られない場合、または修正に依頼の範囲外の変更や未確定の設計判断が必要な場合は、推測で補って変更を続けない。
変更を途中まで適用している場合は、定められた復旧方法に従う。復旧方法が定まっていなければ、既存の利用者変更を保ったまま今回の変更だけを取り消せる場合に限り、変更前の状態へ戻す。
取り消す範囲を区別できない場合は、変更を残したまま、残っている内容と続行できない理由を依頼元へ返す。

## 返す内容

変更した対象について、依頼された結果に対して何ができ、どの確認結果がそれを裏付けるかを説明する。
確認できていない内容は、確認できた内容と分けて示す。
続行に必要な情報・権限・判断が不足していない限り、残る作業を返答へ回さず実装を続ける。
それでも依頼された結果を確認できない場合は未完了として、残る作業と、続行に必要な情報または判断を返す。
成果物の採用や外部への提供に別の手続きが定められている場合は、それに従う。自己確認だけでその手続きを省略しない。
