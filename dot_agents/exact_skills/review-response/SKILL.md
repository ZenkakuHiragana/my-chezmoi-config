# レビュー対応

開始前に固定された指摘だけを、変更前の対象で一度ずつ検証して分類する。この手順は、レビューへの対応を所有する実行主体が自ら実行し、分類を別主体へ委譲してはならない。指摘の説明を欠陥の権威として扱わず、観測した現象を、今回適用する独立した根拠へ戻して判定する。対象を修正したり、新しい指摘を探したり、レビュー全体の終了や変更の実施を決めたりしない。

## 入力

次を開始前に確認する。

- 変更前の検査対象と、比較基準
- 開始前に固定された指摘の集合
- 各指摘の対象箇所、主張された現象、根拠候補、確認方法
- 今回の判断に使う根拠の正本
  - 依頼本文と後続の訂正・追加・選択の逐語引用
  - 認可済みの拘束と、その認可元・根拠へ到達できる資料
  - 今回適用するレビュー基準と、その適用範囲
  - 対象の役割または既に固定された意味を示す正本、接続先、既存の利用契約
- 再現に使う引用、操作、テスト、ログ、生成物、必要な権限

各指摘に対象箇所、主張された現象、確認方法がない場合は、入力不足として分離する。指摘に書かれた「なぜ悪いか」や「侵害する条件」だけを、欠陥の根拠として補ってはならない。根拠の正本またはその到達経路が不足している場合は、確認できない入力として記録し、推測で補ってはならない。

## 一回の処理

入力された指摘、対象、確認方法、根拠の集合を開始前に固定し、各指摘を一度だけ次の順で処理する。

1. 指摘の対象箇所を変更前の対象へ戻し、指摘が主張する現象そのものを、指摘に示された確認方法で再現する。確認方法を実行する環境、権限、道具が不足する場合は `要調査` とする。確認方法を完了して対象箇所が存在しない、または主張された現象を観測できない場合は、その観測を記録して `却下` とする。
2. 現象を観測できた場合は、指摘の説明をいったん保留し、依頼引用、認可済みの拘束と認可元、今回適用するレビュー基準、対象の役割または既に固定された意味を示す正本をそれぞれ直接確認する。
3. 確認した根拠について、対象、根拠の所有先、該当する逐語引用または観測値、今回の対象へ適用される理由を記録する。指摘の説明、一般論、モデルのもっともらしさを根拠の代わりにしてはならない。
4. 観測した現象が、確認した根拠のどの記載と食い違うかを、対象箇所の引用、再現値、読解結果、または実行結果へ戻して確認する。根拠が現象を欠陥として扱うことを示していない場合は `却下` とする。根拠が適用されるかを確認できない場合は `要調査` とする。
5. 根拠に反する観測可能な失敗と、その失敗が今回のレビュー対象で修正対象になる理由を確認できた場合は `採用` とする。
6. 現象と根拠を確認できるが、今回のレビューの対象または適用範囲に含まれない場合は `対象外` とする。ユーザーの依頼に逐語でないことだけを理由に `対象外` としてはならない。今回適用するレビュー基準が対象へ適用される場合は、その基準を独立した根拠として確認する。
7. 情報、環境、権限、根拠への到達性が不足して確認方法または根拠との照合を完了できない場合は `要調査` とする。不足を `採用`、`却下`、`対象外` へ丸めてはならない。

途中で指摘を追加してはならない。同じ指摘を複数の分類へ入れてはならない。固定した根拠の集合にない資料、条件、問題を、検査中に新たに採用してはならない。

## 分類条件

### `採用`

次の全てを確認した指摘を `採用` とする。

- 変更前の対象で、指摘された現象を同じ確認方法により観測した
- 欠陥の根拠を、依頼引用、認可済みの拘束と認可元、今回適用するレビュー基準、または既に固定された役割・意味を示す正本へ直接戻せる
- 根拠が今回の対象へ適用される理由を確認した
- 観測した現象が根拠のどの記載に反するかを確認した
- その反し方が、今回のレビューで修正対象となる観測可能な失敗であることを確認した

条件との関連、一般論、将来危険の推測、指摘の説明との意味上の整合だけで `採用` にしてはならない。

### `却下`

次のいずれかを確認した指摘を `却下` とする。

- 同じ確認方法で、指摘された現象を観測しなかった
- 指摘の根拠候補が対象の事実と一致しなかった
- 独立した根拠を確認したが、その根拠は観測した現象を欠陥として扱うことを示していなかった

感想、好み、指摘の説明への反論だけで `却下` にしてはならない。

### `要調査`

確認方法、根拠、環境、権限、または根拠への到達性の不足により、現象の再現または根拠との照合を完了できない指摘を `要調査` とする。不足しているもの、確認できない理由、再開に必要な条件を記録する。

### `対象外`

現象と適用される根拠を確認できるが、その根拠が定める対象または適用範囲に今回の指摘が含まれない指摘を `対象外` とする。依頼に明示されていないという事実だけで `対象外` にしてはならない。対象外であるという結論を、新しい要求や修正理由へ変えてはならない。

## 分類結果

各指摘について、次のように分類する。

- 分類
- 対象箇所
- 変更前に観測した現象、または観測しなかった反証
- 実行した確認方法
- 独立した根拠の所有先と、該当する逐語引用または観測値
- その根拠が今回の対象へ適用される理由
- 観測した現象と根拠の一致または不一致
- `侵害する条件`: 独立した根拠へ照合した結果として対応する条件、または `該当なし`。指摘に書かれた同名の説明を転記してはならない
- `要調査` の不足と再開条件、`却下` の反証、`対象外` の範囲、`採用` の再現した失敗

入力不足として分離した指摘には、不足している入力と、確認を開始できない理由を返す。根拠を確認できなかったことを、根拠が存在しないという結論へ変えてはならない。

最後に、`採用` となった指摘だけを修正対象として列挙し、各指摘で再現した失敗と、修正後に再実行する同じ確認方法を示す。この列挙を修正契約と呼ぶ。`採用` がなければ、その事実を返す。修正の実施、修正内容の決定、レビュー手続きの終了判断は返さない。

## 禁止事項

- 対象成果物を編集してはならない。
- 新しい指摘を探索または生成してはならない。
- 指摘に書かれた「侵害する条件」、分類、重要度、説明を、独立した根拠なしに採用してはならない。
- 指摘の確認方法を、都合のよい別の確認へ置き換えてはならない。
- 依頼引用を要約、言い換え、分類欄へ再作文してはならない。
- 認可済みの拘束、レビュー基準、対象の役割または意味を、根拠のない推測で補ってはならない。
- `要調査` または `対象外` を黙って解消してはならない。
- 分類結果から修正の実施、指摘の追加、手続きの終了を決めてはならない。

## 完了条件

- 入力された対象、指摘、根拠、確認方法を開始前に確認した。
- 根拠の正本と到達経路を、指摘の説明から独立して確認した。
- 固定された指摘を各一回だけ処理し、入力不足を分類せず分離した。
- 全ての `採用` で、変更前の現象、独立した根拠、根拠との不一致、修正対象となる失敗を記録した。
- 全ての `却下` に、現象がないことまたは根拠との不一致を示す反証がある。
- 全ての `要調査` に、不足、確認できない理由、再開条件がある。
- 全ての `対象外` に、適用される根拠と対象範囲との照合がある。
- `採用` だけを修正対象として返した。
- 対象を編集せず、指摘追加、修正の実施、手続き終了を行っていない。
