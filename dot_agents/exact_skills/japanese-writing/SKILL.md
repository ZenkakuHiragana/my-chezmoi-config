# 日本語で情報を伝える

文章表現は情報伝達の一形態である。書き手は、必要な意味を保ったまま、読者が情報を受け取るための認知負荷を最小化する表現を選ぶ。読者が目的を果たすまでの負担を小さくすることを目指す。

## 追加資料の読み込み

この本文を通常の執筆に使う。次の条件に該当する資料は、その内容を書き始める前に読む。複数の条件に該当する場合は、それぞれを読む。

- 操作手順、依頼、規則など、実行者の行動を指示する文章を書く場合は、[指示を文章にする](references/instructions.md) を読む。
- Markdown で文章を書く場合は、チャット応答を含め、[Markdown の強調境界](references/markdown.md) を読む。
- PDF またはスライドを作る場合は、[ページ構成](references/pages.md) を読む。

[根拠資料の案内](references/sources.md) に、既知の資料の所在と適用範囲を示す。日本語の語義・用法・表記に関する主張または問いを資料へ照合する仕事では、情報源を選ぶ段階でこの案内を読む。この案内は資料の所在と適用範囲を示すものであり、調査手順を定めるものではない。

以下の例は使い分けを示すためのものであり、資料からの引用ではない。例中の設定は説明用であり、実際の作業への追加要求ではない。同じ形式でも、使う理由が変われば残す場合と直す場合がある。

## 読者に何を渡すか

依頼と対象から、誰が何のために読む文章なのかを捉える。仕組みを理解したい読者には関係の説明が要り、項目を調べたい読者には探せる構造が要る。同じ情報でも、利用の仕方によって配置と形式を変える。

読者の出発点は、その文章を受け取る時点で持つ知識と、そこから通常の経路で得られる情報である。書き手が知る会話や編集の経緯を、そのまま読者の前提にしない。会話への返答では会話の文脈を使い、独立した文書では文書の読者に必要な前提を本文に置く。

伝える内容が決まったら、その中の主題を定める。理解に必要な前提から新しい情報へ進み、主張には理由を、操作には必要な条件を結び付ける。読者が必要とする位置に短い説明を置くことで読み戻りを減らせるなら、文字数だけを理由に省かない。

### 編集の経緯と読者の文脈を分ける

書き手が「API 一覧を置くな」と指示され、本文の理解にも一覧が不要なら、一覧を置かなければよい。「API 一覧は別資料を参照する」という案内を本文へ残す理由はない。

読者が実装に使う操作を選ぶために一覧が必要なら、何を調べるための一覧かを伝え、実在する参照先を示す。参照の有無は、削除した事実ではなく読者の作業から決まる。

## 伝えるべき内容に合う表現を選ぶ

出力先で利用できる文章表現から、読者の目的と伝えるべき内容に合うものを選ぶ。
適切な表現の選択はそれだけで項目同士の関係を伝える効果がある。

| 読者が得る情報             | 表現の選び方                                     |
| -------------------------- | ------------------------------------------------ |
| 理由や因果をたどる説明     | 文で関係を明示し、一つの主題を段落としてまとめる |
| 必要な節を探す長い説明     | 内容が分かる見出しで区切り、包含関係を階層で示す |
| 個別に拾う同格の項目       | 箇条書きにする                                   |
| 順番に行う操作             | 番号付きの手順にし、前後関係を見せる             |
| 共通の軸で比べる対象       | 軸を見出しにした表で、値と対象を対応付ける       |
| 文章だけでは追いにくい関係 | 図で関係を示し、読み取る要点を本文で説明する     |
| 正確な文字列を使う操作     | コード表記やコードブロックで説明文と区別する     |

文章中で項目を列挙する表現は原則として多用しない。
項目の列挙は、列挙した各項目を後で別々に扱う必要がある場合に限って行う。
集合として扱えば足りる場合は、個々の項目を並べず上位の概念でまとめる。
因果や役割の違いが重要なら、関連する名詞を並べる代わりに、その関係を述べる。
箇条書きへ置き換えても、そこで伝えたい関係は伝わらない。

表は同じ比較軸を繰り返し読む負担を減らせるが、長文をセルに押し込むと読みにくくなる。短い説明は文のままでよい。見出しは節の主題を示すために使い、各文を見出し付きの断片にしない。

### 項目を拾うか、関係を理解するか

読者が持ち物を一つずつ確かめる案内なら、箇条書きが適する。

> 当日は次のものを持参する。
>
> - 受講票
> - 筆記用具
> - 本人確認書類

短い文中列挙も、共通の役割が明らかなら使える。

> 氏名と連絡先を入力する。

一方、伝えたいのが依頼と資料の関係なら、関係を書く。

> 利用者の依頼から確認対象を定め、その対象について資料を調べる。

これを「資料、発言、引用、正本、関連文献、外部情報源、応答内容を確認する」とすると、何が対象を決め、何が根拠になるかが消える。名詞を改行しても関係は回復しない。ただし、本当に各項目を照合する依頼なら、その対象を省いてはならない。

### 比較を表にする

二つの保存方式について、読者が同じ観点で選ぶ場面を考える。

| 方式 | 既存の内容 | 新しい内容 |
| --- | --- | --- |
| 上書き | 置き換える | 保存する |
| 追記 | 残す | 末尾へ加える |

各方式を同じ軸で照合できるため、表に意味がある。「保存先は指定フォルダである」とだけ伝えるなら、一文で足りる。短い説明を表へ移すために、新しい比較軸を作らない。

### 手順と条件を対応付ける

保存してから終了する順序が必要なら、番号を付ける。

> 1. ファイルを保存する。
> 2. 保存が完了したら、画面を閉じる。

順序を示す番号と、次へ進む条件の両方に意味がある。二つ目の項目が条件を含むことを理由に、散文へ戻す必要はない。

## 用途から中心を決める

以下は文書の用途に応じた選択肢であり、すべての文書に同じ章立てを要求するものではない。

| 用途 | 読者が得るもの | 情報の配置 |
| --- | --- | --- |
| 仕様 | どの条件で、どの結果が成立するか | 適用対象を示し、条件と結果を対応付ける。例外は該当する条件に結び付ける |
| 手順 | 目的の状態へ進む方法 | 開始に必要な条件を置き、操作を実行順に示す。分岐と結果の見分け方を対応付ける |
| 説明 | 仕組みとその理由 | 必要な概念を導入し、中心の関係を説明してから詳細へ進む |
| 設計 | 確定した判断と、それを支える構造 | 目的に対して責務と関係がどう働くかを述べ、判断の理由と制約を結ぶ |
| 参照資料 | 名前から引ける定義や値 | 調べる名前を入口にし、共通項目をそろえて探しやすくする |
| 報告 | 観測結果から言えること | 結果と根拠をつなぎ、条件と限界を添える |

説明では中心となる仕組みから入ると、詳細の位置付けが分かりやすい。一方、操作前の注意が結果を左右するなら、その操作より先に置く。「例外は後に書く」という順序を安全条件にまで適用しない。

## 文の組み立てで意味を表す

正しい日本語文法で文章を組み立てる。文法的に成立すること、意図した意味になること、場面にふさわしいことは別の判断である。

### 述語から文を組み立てる

助詞は、名詞が述語に対して担う役割を示す。

> 担当者が利用者に結果をメールで知らせる。

この文では「担当者」が知らせる主体、「利用者」が相手、「結果」が内容、「メール」が手段である。述語が変われば、名詞との結び付きも変わる。「資料に基づく」と「資料を基にする」の助詞は、名詞が同じだからといって統一できない。

文の主題と動作主は一致するとは限らない。「この資料は担当者が更新する」では、話題にしているのは資料であり、更新する主体は担当者である。「は」が付いた語を必ず動作主として読むと、この違いを失う。

後ろの語に合う活用形を使う。「静かな部屋」では名詞を、「静かに話す」では動作を修飾する。長い名詞句も、助詞を使って関係を表せる。「新規顧客対応手順変更案」が新規顧客への対応を意味するなら、「新規顧客への対応手順を変更する案」と書く。

修飾語は修飾先が分かる位置に置く。「担当者が昨日提出した報告書」なら、昨日提出されたのが報告書だと分かる。読点は係り受けや語の切れ目を示せるが、文の構造が定まらないまま読点だけを増やしても解決しない。

### 話題と焦点をつなぐ

「は」は話題を設定し、対比にも用いる。「が」は述語に対する主語を示すほか、誰が行ったのかという焦点を表すことがある。

> 担当者は確認した。管理者はまだ確認していない。

> 誰が確認したのか。担当者が確認した。

同じ人物と動作でも、前者は人物を対比し、後者は問いの答えを示している。助詞を表記の揺れとして統一しない。

主題や主体が文脈から明らかな場合は省略できる。「担当者は資料を受け取り、内容を確認した」は、同じ担当者の動作として読める。途中で管理者へ動作が移るなら、その主体を示す。

「この結果」「それ」は、読者が指す対象を定められるところで使う。複数の結果が並んだ後では、必要な名詞を繰り返す方が短い指示語より負担が小さい。段落を変えるだけで、前段の条件や対象が解除されるわけではない。

### 出来事のどこを中心にするか

能動は動作主を、受身は動作を受ける側を中心に述べる。

> 委員会が申請を承認した。

> 申請は委員会に承認された。

前者は委員会の行為を説明し、後者は申請の扱いを説明している。判断の責任を伝えるなら動作主を明らかにする。対象の状態を続けて説明するなら、受身が適する場合がある。受身には「雨に降られた」のように影響を受けた側を述べる用法もあり、すべてが能動文の単純な置換ではない。

使役は、他者に動作をさせる関係を表す。「管理者が担当者に再実行させる」では、働き掛ける人と実行する人が異なる。使役には強制にも許容にも読めるものがある。権限や責任の違いを伝える場合は、「再実行を命じる」「再実行を許可する」のように必要な関係を直接表す。

### 時間と状態を表す

時制は出来事を時間上に位置付ける。アスペクトは、出来事を進行中や完了後の状態などとして捉える働きである。

| 表現 | この文脈で伝えること |
| --- | --- |
| 今、担当者がファイルを更新している | 更新作業が進行中である |
| ファイルは更新済みである | 更新が完了している |
| 扉が開いている | 開いた後の状態が続いている |

「ている」は進行だけを表すとは限らない。「た」も過去のほか、「こんな所にあった」のように発見を表すことがある。形だけで状態を決めず、動詞と文脈に合う表現を選ぶ。

報告では時間の基準を示す。「現在」が観測時点なのか読者が読む時点なのかで、成立する内容が変わることがある。また、「確認してから送る」と「送ってから確認する」は別の手順である。語順の整理で出来事の順序を変えない。

### 否定と限定の範囲を保つ

否定は、何が成立しないかを表す。数量や条件と組み合わさると、否定する範囲が重要になる。

> すべての申請を承認したわけではない。

> どの申請も承認しなかった。

前者は全件承認を否定しており、一部を承認した場合を含む。後者は承認が一件もないことを述べる。「必ず成功するわけではない」も、「必ず失敗する」とは異なる。

「だけ」「しか」は対象を限定する。標準的な「しか」は否定形と組み合わせる。「管理者しか変更できない」は、管理者以外では変更できないことを表す。限定語の位置にも意味がある。「管理者だけが設定を変える」は主体を限定し、「管理者が設定だけを変える」は対象を限定する。

「も」は同類の追加に使い、数量に付くと「百人も来た」のように多さを表すこともある。形式を付けるだけで、追加や意外さの基準が読者に伝わるわけではない。必要な比較の文脈と結び付ける。

二重否定は解釈の手間を増やす一方、留保や限定を表す場合がある。「対応できないわけではない」を「対応できる」とすると、その含みを失い得る。単純な肯定で同じ意味になる場合に言い換える。

### 確かさと働き掛けを区別する

モダリティは、内容に対する書き手の判断や、読者への働き掛けを表す。内容が何かに加え、どの確かさや拘束力で述べるのかを選ぶ。

| 伝える意味 | 表現例 |
| --- | --- |
| 発生を確言として述べる | 接続が切れた |
| 発生の可能性を述べる | 接続が切れたかもしれない |
| 行為を義務付ける | 提出しなければならない |
| 行為を許可する | 提出してよい |
| 行為を禁止する | 提出してはならない |
| 義務がないと述べる | 提出する必要はない |

確言の形で書いたことは、内容が真である証拠にはならない。分かっていることに合わせて確かさを表す。条件が分かったことと、その条件下で必ず起こることも別である。推量を削って断定したり、根拠のない慎重さを加えたりしない。

「できる」は能力や実現可能性にも使われるため、許可を伝える場面では「してよい」などで区別する。「べきだ」は規範的判断や推奨として使われるが、文書で義務表現が定義されていればその定義に従う。一般語の印象で要求の強さを変えない。

接続失敗だけを観測し、原因を特定できていない場面では、停止は仮説として扱う。

> 接続先が停止した可能性がある。停止したかどうかは未確認である。

「可能性がある」を削って「接続先が停止した」とすれば、未確認の原因を事実へ変えてしまう。

提出が任意なら「提出する必要はない」と書ける。「提出してはならない」へ変えると、義務の否定を禁止へ変えてしまう。語尾が整っても、伝える規則が変われば推敲にはならない。

### 節と文の関係を表す

接続は、二つの内容がどのようにつながるかを示す。原因なら「ので」「から」、目的なら「ために」、譲歩なら「ても」など、必要な関係を表す形式を使う。「再試行しても失敗する」と「再試行したので失敗する」では、再試行と失敗の関係が異なる。

条件の「と」「ば」「たら」「なら」は、意味が重なる場面もあるが、常に交換できるわけではない。

> 参加するなら、連絡してほしい。

> 参加したら、連絡してほしい。

前者は参加を前提に連絡を求める。後者は参加後の連絡と読まれ得る。前件が仮定か既成の事実か、後件が依頼か結果の説明かによっても適する形式が変わる。

並列では項目の共通の受け先を示す。「AとBを提出する」と「AまたはBを提出する」では、両方が必要か選択できるかが違う。両方を選べるかが判断に関わる場合は、その扱いを明示する。単なる出来事の連続を「だから」で結び、因果関係を作らない。

## 語を選ぶ

伝えたい意味に合い、読者が直接理解できる語を選ぶ。同義に見える語でも、指す対象や要求の強さが変わるなら置き換えない。同じ概念には一貫した呼び方を使い、別の概念を同じ語へまとめない。

平易で定着した日本語表記がある一般語は、日本語で書く。「ファイル」のように定着したカタカナも日本語表記である。操作や照合に必要な識別子、正式名称、引用は原表記を保つ。専門語を言い換えると精度が落ちる場合は、その語を残し、読者に必要な説明を添える。

未知の用語は、この位置で何を指すか分かるように導入する。仕組みの説明では役割から入ると理解を助けられる。名前を調べる参照資料では、名前から説明へ進む方が探しやすい。どちらの順序も、読者が概念の意味を保留したまま進まずに済むように使う。

なじみのなさだけで誤用と決めず、表す意味と使われる場面を分けて考える。資料を利用できない場合や、資料から語義・用法・定着度を確認できない場合は、確認済みとして断定せず、未確認であることを区別して書く。

資料へ接触する際は、利用できる権限の範囲で扱う。外部検索には公開できる一般的な表現を使い、非公開の本文をそのまま送らない。

### 日本語表記と識別子を分ける

一般的な説明の「readability を改善する」は、「読みやすさを改善する」で意味を伝えられる。

設定名が正確に `readability` と定義されているなら、次のように役割と固定文字列を区別する。

> 読みやすさの評価値を `readability` に設定する。

「ファイル」や「アルファベット」は、外国語由来であっても定着した日本語表記である。

### 説明順は読者の入口から選ぶ

初めて仕組みを学ぶ読者には、役割から名前へ進められる。

> 一度得た結果を保存し、再利用する仕組みをキャッシュと呼ぶ。

「キャッシュ」を調べる辞書形式の資料なら、名前を入口にする。

> キャッシュ: 一度得た結果を保存し、再利用する仕組み。

名称を先に置くこと自体は誤りではない。読者が探すものと、その位置で必要な説明が対応しているかによって選ぶ。

## 補足と対比を置く

本文には主題を理解するための情報を置く。括弧や注記には、その位置で解釈を助ける補足を置く。判断に不可欠な条件は本文へ組み込み、本文を言い直すだけの補足は加えない。例は抽象的な内容を具体化するために添え、例示と対象の全範囲を区別する。

否定は不成立や禁止そのものを伝えられる。対比は、候補の違いが読者の理解や選択を変えるときに使う。書き手だけが知る却下案を持ち出す必要はない。編集指示への応答を本文へ混ぜず、読者が今回知るべき内容を述べる。

参照は、読者が必要な情報へ進む道として置く。リンク先で何が分かるかを示し、現在の説明に必要な接続まで参照先へ追いやらない。強調は、読み落とされると理解や行動が変わる箇所を目立たせるために使う。

### 補足が情報を加えるか

保存形式の名称と略称を対応付ける場合は、括弧が補足として働く。

> Portable Document Format（PDF）で保存する。

一方、見出し「情報源の確認（正しい資料を使う）」の括弧が、確認の条件も内容も増やさないなら、「情報源の確認」で足りる。発行元を照合する説明が実際にあるなら、「発行元の照合」という具体的な見出しも選べる。見出しを詳しくするために、本文にない作業を作らない。

### 否定そのものが必要な場合

> 再試行しても復旧しなかった。

復旧しなかったことが報告の内容なので、否定を残す。

> この部屋では撮影してはならない。

禁止を初めて知らせる文も成立する。否定の対象が前の文に出ていないことだけでは、不要な否定とは言えない。

保存方式を比較した読者に「上書きではなく追記で保存する」と伝えるなら、対比が選択を助ける。読者が知らない却下案を否定するためだけに「これは同期でも複製でもなく、保存である」と書く必要はない。保存動作が主題なら、その動作を直接説明する。

## 説明と参照をつなぐ

一つの文書では、その文書の役割を果たす範囲を説明する。複数の文書に分ける場合は既存の責務に従い、定義や一覧を管理する正本を増やさない。読者がその場で必要とする短い説明は本文に置き、詳しい定義へ進める参照を添える。

参照の粒度は、読者が調べる対象と媒体の安定性に合わせる。節を特定できるリンクが維持されているなら、文書全体を指すだけにしない。リンクの文字列または周辺の文で、参照先から何を得られるかを伝える。関連しているという理由だけで、読者の作業に要らない参照を増やさない。

仕組みの説明では、処理順とデータの関係を区別する。複雑な関係は図で示せるが、図の記号が本文のどの概念に対応するかも示す。

## 文体と媒体に合わせる

説明の正確さを保ちながら、読者との関係と場面に合う文体を選ぶ。丁寧さを増すことと、敬語が正しく成立することは別である。本文の文体は一貫させ、引用や画面上の固定文言は原文を保つ。

### 相手と場面に合う言葉遣い

敬語は、誰の行為を述べ、誰に向けて話すかに関わる。「おっしゃる」は行為者を立てる尊敬語である。「申し上げる」は自分側の発言が向かう先を立てる謙譲語であり、単に文末を丁寧にする働きとは異なる。

相手との親疎や場面の改まりに合わせて、丁寧さを選ぶ。文体の選択と敬語の誤用を混同しない。「です・ます」と「だ・である」のどちらかが文法的に優れるわけではない。体言止めも見出しや要約に使えるが、説明文で判断や動作まで省くと、読者に述語を補わせることになる。

### 構造を記法へ写す

文書を生成するときは、読者が利用する形式で意味の伝わる記法と配置を選ぶ。同じ内容でも、画面幅やページ分割、利用できる文書構造によって適する表現は変わる。

見出しには、対象の形式で見出しを表す記法を使う。太字にするだけでは、目次や見出し移動に使える構造にならない場合がある。見出しの階層は内容の包含関係に合わせる。

箇条書きには項目の区切りを、手順には順序を表す記法を使う。項目内の補足は、その項目に属することが分かるように配置する。番号そのものを参照する文書では、読者が番号と対象を対応付けられる表現を選ぶ。

表では、各セルがどの行・列の見出しに対応するかを明らかにする。狭い画面で長文の列が並ぶなら、表を分けるか、項目ごとの説明にする。表は比較のために使い、文字を左右へ置くためだけの枠にしない。

### 図と補足を読む順に置く

図は、本文だけでは把握しにくい関係を示す場所に置く。表題と本文で図の主題を示し、線や記号の意味が必要なら説明する。色や形だけに重要な違いを負わせず、文字でも区別を伝える。数値を示す図では軸や単位を明示する。

例や注記は、説明対象との関係が分かる位置に置く。操作前に必要な条件を、離れた脚注へ追いやらない。短い補足は括弧に収められるが、主題の理解に必要な長い説明は本文として扱う。

リンクには目的が伝わる文字列を使う。現在の文の理解に必要な説明は本文に残し、詳しい情報へ進むために参照を使う。

### 固定文字列を示す

操作や照合に使う名前は、原表記を保って説明文と区別する。コード、設定値、テンプレートを日本語へ翻訳しない。説明には日本語を使い、文字列が指す役割を示す。

例の値と、そのまま入力すべき値を区別する。空白や記号を整えるだけでも動作が変わることがあるため、実行用の文字列に装飾のための変更を加えない。コードブロックの外に、その例の用途と読み取り方を書く。

長いパスやコードは、読者が全文を取得できる配置にする。意味を変える空白や改行を文字列へ加えるのではなく、表示幅やブロックの配置で扱う。本文から文字列をコピーする用途があるなら、説明や行番号と混ざらない形にする。
