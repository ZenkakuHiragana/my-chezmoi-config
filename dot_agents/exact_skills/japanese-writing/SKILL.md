# 日本語文章の執筆

文章表現は情報伝達の一形態である。必要な意味を保ち、読者が目的を果たすまでの認知負荷を小さくすべきである。
このスキルは情報の探索や関係の復元にかかる余計な負担を減らし、伝わりやすい日本語文章を執筆するためのものである。

この指示における例文は使い分けを示すためのものである。例示の内容は実際の作業に対する要求としては扱わない。

## 追加資料

構成する文章の目的に合わせて追加で以下の資料を読み、記載内容に従う。

- `references/artifacts.md`: 文書ファイルとして保存したり、外部サービスにコメントを投稿したりする時に読む。
- `references/instructions.md`: モデルの行動を指示するプロンプトやスキル本文を構成する時に読む。

## 読者に渡すもの

依頼と対象から、誰が何のために読む文章なのかを捉える。
読者の目的と既知の内容に合わせて、今回伝える情報の範囲と深さを選ぶ。
調査で把握する範囲と、読者へ報告する範囲は同じではない。把握した情報をすべて提示する必要はない。

求められた情報と、理解や判断に必要な関係を残す。
事実・推測・未確定の区別を保ち、文章を整えるために新しい事実や要求、結論を作らない。
作業経緯も、その説明を求められた場合は内容となる。
情報の種類だけでなく、読者の目的に対応する範囲を選び、伝えるべき内容を決定する。

読者の前提にできるのは、受け取る時点で持つ知識と、本文または通常の利用経路から得られる説明である。
会話への返答では会話の文脈を使い、独立した文書にはその読者に必要な前提を置く。
今回の読者の目的に関係しない編集経緯や却下案を混ぜない。
例えば、一覧を削除する指示を受けたことだけを理由に、本文へ「この文書には一覧を記載しない」と残す必要はない。

選んだ内容の主題を定め、理解に必要な前提から新しい情報へ進む。
主張には理由を、操作には条件を結び付ける。
その位置に短い説明を置けば読み戻りを減らせるなら、文字数だけを理由に省かない。

## 伝えるべき内容と適した表現の選択

出力先で使える表現から、伝えるべき内容を最もよく伝えるものを選ぶ。

| 読者が得る情報             | 表現の選び方                                   |
| -------------------------- | ---------------------------------------------- |
| 理由や因果をたどる説明     | 文で関係を示し、一つの主題を段落にまとめる     |
| 必要な節を探す長い説明     | 内容が分かる見出しを付け、包含関係を階層で示す |
| 個別に拾う同格の項目       | 箇条書きにする                                 |
| 順番に行う操作             | 番号付きの手順にし、前後関係を示す             |
| 共通の軸で比べる対象       | 軸を見出しにした表で、値と対象を対応付ける     |
| 文章だけでは追いにくい関係 | 図で示し、読み取る要点を本文で説明する         |
| 正確な文字列を使う操作     | コード表記やコードブロックで説明文と区別する   |

### 文章中の列挙表現

文章中で項目を列挙する表現は原則として多用しない。
並列表現は同格の項目が共通の役割を持っていて、かつ各項目を個別に示すこと自体が伝えるべき内容である場合に有効である。
概念を表す語彙を選ぶ労力を回避するために使うものではない。
集合として扱えば足りる場合は、上位の概念でまとめるか、代表的な1項目をだけを挙げる。

- 悪い例: 「ユーザーが理解、調査、判断するために」
  - なぜ悪いか: ユーザーの行動という共通項があるが、殊更にそれぞれを区別して扱う必要がない。並べて書くのは純粋に情報の無駄である
  - 行動ごとに異なる情報を伝える場合は「理解にはAが、調査にはBが、判断にはCが必要」など関係を述べるか、箇条書きで個別に説明する
- 良い例: 「住所、氏名、電話番号を応募フォームに入力する」
  - なぜ良いか: 入力すべき項目という共通項であり、なおかつ具体的に各項目を区別して扱うことこそが伝えるべき内容である
  - 入力項目そのものを伝える必要がない場合は「必要事項を入力する」で足りる

因果や役割の違いは、関連する名詞の列挙ではなく関係として述べる。
「依頼から確認対象を定め、その対象について資料を調べる」と「依頼、対象、資料を確認する」では伝わる因果が異なる。

### 表組み

表は共通の軸を繰り返し読む負担を減らすために使う。
セルの中に配置してよいのは単語、値、短い文章である。
長文、複数の段落、箇条書きなどセル内部を独立した説明領域として使う表現は入れない。

## 文の組み立て

文法的に成立すること、意図した意味になること、場面にふさわしいことを分けて扱う。

本文中の長い名詞句は名詞の連結で関係を省略せず、助詞や述語で関係を示す。

同じ主体を指す箇所では主語を省略できる。途中で別の主体の動作へ移るなら主体を示す。

### 能動と受動

「課長が申請を承認した」は動作主を、「申請は課長に承認された」は対象を中心に述べる。
責任を伝えるなら動作主を示し、対象の状態を説明するなら受身も使う。

### 否定と限定

「すべて承認したわけではない」は全件承認の否定であり、「どれも承認しなかった」とは異なる。
「必ず成功するわけではない」も「必ず失敗する」とは異なる。

「管理者だけが設定を変える」は主体、「管理者が設定だけを変える」は対象を限定する。
標準的な「しか」は否定形と組み合わせ、「管理者しか変更できない」は管理者以外では変更できないことを表す。

二重否定は留保を表す場合がある。「対応できないわけではない」を単純な肯定へ変えるのは、その含みも保てる場合に限る。

### 確かさと働き掛け

内容の確かさと、読者への拘束力を選び分ける。
「接続先が停止した可能性がある」を、原因未確認のまま「停止した」へ変えない。
推量を削ったり、根拠のない慎重さを加えたりしない。

次は一般的な用法である。他に定義がある場合はそれに従う。
複数の解釈を持つ表現は誤読に注意する。

- しなければならない: 義務
- してよい / してもよい: 許可
- してはならない: 禁止
- しなくてもよい / する必要はない: 義務の否定
- できる: 許可、能力の主張、実現可能性
- すべき: 規範的判断、推奨

### 条件表現

「再試行しても失敗する」と「再試行したら失敗する」は前後の関係が異なる。
「参加するなら連絡して」は参加する意思があることが条件で、「参加したら連絡して」は参加したことが条件である。
「たら」「なら」「ても」などは前後の関係に合わせて選ぶ。

## 語彙選択

意味に合い、読者が直接理解できる語を選ぶ。
同義に見えても、対象や要求の強さが変わる語へ置き換えない。
同じ概念には一貫した呼び方を使い、異なる概念を同じ語へまとめない。

平易で定着した日本語表記がある一般語は日本語で書く。
識別子や引用は元の表記で書く。
専門用語を言い換えると意味を保持できない場合は想定読者に合わせて必要な説明を添える。

例:

- 「readability を改善する」ではなく「読みやすさを改善する」
- 「accessibility に配慮する」ではなく「アクセシビリティに配慮する」
- 「変数 `readability` を宣言する」

### 用語の導入

文書内で概念に名前を付ける場合は、後の説明でその概念を繰り返し指す必要がある場合に限る。
最初に使う位置または用語定義の節で名前と意味の対応を示し、その後は同じ名前で指す。
既存の語で十分に表せる概念へ新しい用語を作らない。

## 補足と対比

括弧や注記には、その位置で解釈を助ける短い補足を置く。判断に必要な条件や長い説明は本文に置く。言い直すだけの補足は加えない。

- 良い例: 「Portable Document Format（PDF）」 ... 名称と略称を結ぶ
- 悪い例: 「情報源の確認（正しい資料を使う）」 ... 同じ主張の言い換え

対比は対象の違いが読者の理解や判断に必要な場合に使う。
対比の対象はその時点の文章展開や想定読者の知識から読者が持つと合理的に見込めるものに限る。
読者のメンタルモデルに存在しない前提を持ち出したり否定したりしない。

## Markdown の強調

強調は、読み落とされると理解や行動が変わる箇所に使う。
強調が多すぎると重要度の差が伝わらず、強調していないのと同じになる。

日本語文章においては Markdown レンダラーの都合により強調にはいくつかの制約がある。

斜体構文を使っても日本語フォントの斜体表示が機能しない場合がある。
想定するレンダラーで日本語の斜体表示が機能することを確認できない場合は日本語の文字に斜体を適用しない。

日本語の文字が強調構文の外側に隣接すると強調の境界の検出に失敗する場合がある。
強調構文の外側に日本語の文字が隣接する場合は、構文の外側を半角スペースで区切る。
また、強調の外側に日本語の句読点を置かない。

例:

- 設定を **保存する** と反映される。
- これは **重要な条件。** 次の操作より前に満たす。
- 英単語 _emphasize_ は強調するという意味。
