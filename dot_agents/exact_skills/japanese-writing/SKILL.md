# 日本語文章の執筆

文章表現は情報伝達の一形態である。必要な意味を保ち、読者が目的を果たすまでの認知負荷を小さくすべきである。
このスキルは情報の探索や関係の復元にかかる余計な負担を減らし、伝わりやすい日本語文章を執筆するためのものである。

このスキルにある例文は使い分けを示すためのものである。例示の内容は実際の作業に対する要求としては扱わない。

## 読者に渡すもの

依頼と対象から、誰が何のために読む文章なのかを捉える。
読者の目的と既知の内容に合わせて、今回伝える情報の範囲と深さを選ぶ。
調査で把握する範囲と、読者へ報告する範囲は同じではない。把握した情報をすべて提示する必要はない。

求められた情報と、理解や判断に必要な関係を残す。
事実・推測・未確定の区別を保ち、文章を整えるために新しい事実や要求、結論を作らない。
作業経緯も、その説明を求められた場合は内容となる。
情報の種類だけでなく、読者の目的に対応する範囲を選び、伝えるべき内容を決定する。

読者の前提にできるのは、受け取る時点で持つ知識と、本文または通常の利用経路から得られる説明である。
会話への返答では会話の文脈を使い、独立した文書にはその読者に必要な前提を置く。
今回の読者の目的に関係しない編集経緯や却下案を混ぜない。
例えば、一覧を削除する指示を受けたことだけを理由に、本文へ「この文書には一覧を記載しない」と残す必要はない。

選んだ内容の主題を定め、理解に必要な前提から新しい情報へ進む。
主張には理由を、操作には条件を結び付ける。
その位置に短い説明を置けば読み戻りを減らせるなら、文字数だけを理由に省かない。

## 段落と論証の構成

パラグラフライティングを基本とする。段落は論証の一歩であり、読者は段落単位で論理を追えなければならない。

- 一つの段落には一つのトピックだけを置く。場面の進行（調査、報告、検証、評価）が複数混ざった長い段落は分割する。
- 段落同士の関係が順序や表現から分かるようにする。主張・根拠・対比・条件を、読者が関係を補わなくても追える形で配置する。
- 段落の最初の文を読めば、その段落が何の話かわかるようにする。
- 何かを否定・限定するときは、否定する命題そのものを正確に書き出す。漠然とした否定で済ませない。
  悪い例: 何もかもが解決するわけではない
  良い例: 明文化されていればすべてを任せられることを意味しない

## 論証の厳密さ

文章の論理にツッコミどころを残さない。書き上げたら、読み手の反論を先回りして次の点を点検する。

- 推量・可能性・読者の疑念・反実仮想として書かれている文を、機械的に断定へ変えない。
  「かもしれない」「だろう」「ようだ」「らしい」は、根拠なく主張を弱めている場合だけ削る。
  事実未確認の可能性、作中人物の認識、ログからの推定、読者が抱きそうな疑念、反実仮想を表す場合は、その不確実性を保つ。
  断定に直せるのは、本文内の根拠によって命題が確定している場合に限る。
  悪い例：「提示し続けているかもしれない」を「提示し続けている」に変える。
  良い例：「提示し続けている可能性がある」のように、不確実性を残して文を整える。
- 異なるものを「同じ」とまとめない。区別すべき対象（別々の決定、別々の原因、種類の違う問題）を一括りの言葉でくくらない。
  悪い例：相互依存する三つの未決事項を「同じ決定を別々に下していた」と書く。
  良い例：「どれも別々の決定であり、しかも互いに依存している」と腑分けする。
- 複数の要因がある事象を、単一の原因に還元しない。例が複数種類の問題を含むなら、それぞれを切り分け、どの道具がどれを説明するのかを対応づける。
  悪い例：契約の不在と情報隠蔽の失敗が混ざった事故を、丸ごと「情報隠蔽の問題」と説明する。
- 章・節をまたいで、同じ概念の扱いを一致させる。ある節で「人間が決める」と分類したものを、別の節で「チームで合意する」と書かない。分類・定義・用語の地位は全体で揃える。
- 因果を主張するときは、その機構（なぜそうなるのか）を一文で示す。「AだとBになる」とだけ書いて理由を省略しない。
  悪い例：「手順で分けると変更が全体に波及する」。
  良い例：「各工程がデータを受け渡すための表現を共有してしまい、その表現を変えると全体に波及する」。
- 主張は、挙げた例が実際にその全体を支えているかを確認する。例が主張の一部しか支えないなら、主張の範囲を例に合わせて狭める。
- 譲歩や限定（「ただし」「とはいえ」）を置いたら、その後で必ず論を進める。逆接で終えて宙吊りにしない。
- 複数の概念を一つの上位語にまとめるときは、命名の直前に、それらが同じものに帰着すると一文で述べる。

## 読み手の負荷の管理

読者の記憶と注意は有限の資源として扱う。

- 後で参照する必要のない固有名（ファイル名、関数名、識別子）を出さない。「仕様書」「金額計算のユーティリティ」のような一般的な言い方で済ませる。
- 抽象的な言い回しの指す内容が文脈から一意に決まらないときは、適切にその場で補足する。できるだけ読者に前を読み返させない。
- 概念を初めて示す文では、読者が順に読んだだけで、まずその概念が何であるか（データ構造、手順、制約などの種類や地位）を読み取れる順序にする。
  その概念を既に知っている読者にだけ自然な性質・仕組み・制約を、種類の同定より前に置かない。
  前置すると、未習の読者は文を読み終えた時点で逆戻りしなければ核となる情報を見逃すか、理解が滞る。
- 同一節内に図、表、コードなど複数の提示があるとき、各媒体が担う説明（配置の見え方、数値、手順など）を分けて書く。
  媒体間で型やデータを揃える必要はなく、別例として並べてよい。
  指示語（「この2つ」「上記の例」）は、どの媒体のどの例を指すか文脈だけで一意に決まるように置く。
  一つの媒体で確認した性質を、別の媒体の例にもそのまま当てはめない。
  二方式を「Aの代わりにB」と対比するときも、やめる側と採る側の語順を置換関係と一致させ、後に書く側が採用される方式であることを順読みで読み取れるようにする。
- 章冒頭や節の導入では、これから例で扱う内容に関係しない過剰な詳細を詰め込まない。
- その節の主張・帰結を理解するのに直接関係しない過剰な詳細を書かない。議論に必要な具体性は残す。
  省略すべきものの典型は、エージェント報告の装飾的精度（時刻、HTTP ステータス、カバレッジ率、ハッシュ値など）や、後で参照しない固有名詞。
- 詳細を示す前に、その詳細によって読者の理解や判断が何から何へ変わるのかを考える。
  何も変わらないか、その節の主張を補強するのに十分な情報を持たないなら書かない。
  複数の詳細が同じ結論を支えるだけなら、読者が個々を区別する必要がない限りそれらの共通する意味を本文に書く。

## 演出の抑制

過剰な演出は読みにくい文章を生む。以下は演出の節度に関する規範である。修辞は、それが効果を生む箇所でのみ使う。

- 溜め（「ここには〜が潜んでいる」）や修辞疑問で導出を演出するのは、緊張が議論に効く要所に限る。説明で足りる箇所では、そのまま述べる。
- 帰結の列挙によって事故や危険を煽らない。
- 「重要なのは〜である」のような前置きで主張を予告しない。主張をそのまま書く。
  ただし、主張の様式を宣言する前置き（「標語として言い換えれば」など）は使ってよい。
- 慣用表現をひねった言い回しや、指す内容が一意に決まらない比喩を使わない。平易な語彙でそのまま書く。
  例: 知識を体に入れる → 身につく、報告の外側に世界が広がっている → 気づく機会が減る

## 冗長の排除

無駄な文章をなるべく残さない。

- 同じ主張を言い換えて繰り返さない。一つの主張は一度だけ書く。題材が直前と同じでも、その文が加えている命題が違えば繰り返しではない。
  列挙の各項が同じ論理的地位であることを示す枠語の反復や、定義の直後に適用条件や限定を足す文も、主張の繰り返しではない。
- 隣接する節が同じことを別の角度で述べているなら、役割が重複している。片方に吸収して一つの節にまとめる。
- 場面を描写した直後に、その内容を要約し直さない。意味づけの一文（「このような作業は、ほぼ完全に任せられる」など）だけを置く。
- 冗長さは文字数や文数で判定しない。短文化と一文化は、動機、対象、操作、その同一性、因果、条件が順読みで明示されたまま保てる場合に限る。
  これらを読者の推論に委ねる圧縮はせず、必要な反復と長さを残す。
- 接続や評価のためだけの文（「それ自体はよいことである」など）を置かない。
- 想像上の読者との問答（問いを立てて一語で答える形など）を修辞として使わない。主張はそのまま述べる。
- 読者が抱きそうな発想を、メタな枠取り（「ここまでの話には自然な続きがある」「〜という発想である」）で紹介しない。
  その発想自体を直接書く。読者の疑問なら疑問文のまま書いてよい（「その保守も任せればよいのではないだろうか」）。
- 「本書もそれを否定しない」のような、著者の立場の弁明や断りを書かない。事実の記述（「〜に書かせる場合が多い」）だけを置く。
- 文脈を最短で読み手と共有できる文章にする。導出を一歩ずつ展開しなくても伝わるなら、構造に名前を与えて言い切る。
- 本文でまだ導入していない概念や文書名を、先回りして持ち出さない。
- ためらいのある弱い述語（「有効な対策であり」など）で済ませない。本文内の根拠で確定していることは強く具体的に言い切る（「活用において必須であり」など）。
  ただし、不確実性・可能性・仮定・読者の疑念を表すための弱い述語は保持する。語調を整えるための意図的な緩和（「必須だと言ってもいい」など）は許す。
- 文章のリズムを作るための接続表現（「しかし一方で」など）は、冗長と見なさない。

## 伝えるべき内容と適した表現の選択

出力先で使える表現から、伝えるべき内容を最もよく伝えるものを選ぶ。

| 読者が得る情報             | 表現の選び方                                   |
| -------------------------- | ---------------------------------------------- |
| 理由や因果をたどる説明     | 文で関係を示し、一つの主題を段落にまとめる     |
| 必要な節を探す長い説明     | 内容が分かる見出しを付け、包含関係を階層で示す |
| 個別に拾う同格の項目       | 箇条書きにする                                 |
| 順番に行う操作             | 番号付きの手順にし、前後関係を示す             |
| 共通の軸で比べる対象       | 軸を見出しにした表で、値と対象を対応付ける     |
| 文章だけでは追いにくい関係 | 図で示し、読み取る要点を本文で説明する         |
| 正確な文字列を使う操作     | コード表記やコードブロックで説明文と区別する   |

### 文章中の列挙表現

文章中で項目を列挙する表現は原則として多用しない。
並列表現は同格の項目が共通の役割を持っていて、かつ各項目を個別に示すこと自体が伝えるべき内容である場合に有効である。
概念を表す語彙を選ぶ労力を回避するために使うものではない。
集合として扱えば足りる場合は、上位の概念でまとめるか、代表的な1項目を挙げる。

- 悪い例: 「ユーザーが理解、調査、判断するために」
  - なぜ悪いか: ユーザーの行動という共通項があるが、殊更にそれぞれを区別して扱う必要がない。並べて書くのは純粋に情報の無駄である
  - 行動ごとに異なる情報を伝える場合は「理解にはAが、調査にはBが、判断にはCが必要」など関係を述べるか、箇条書きで個別に説明する
- 良い例: 「住所、氏名、電話番号を応募フォームに入力する」
  - なぜ良いか: 入力すべき項目という共通項であり、なおかつ具体的に各項目を区別して扱うことこそが伝えるべき内容である
  - 入力項目そのものを伝える必要がない場合は「必要事項を入力する」で足りる

因果や役割の違いは、関連する名詞の列挙ではなく関係として述べる。
「依頼から確認対象を定め、その対象について資料を調べる」と「依頼、対象、資料を確認する」では伝わる因果が異なる。

### 表組み

表は共通の軸を繰り返し読む負担を減らすために使う。
セルの中に配置してよいのは単語、値、短い文章である。
長文、複数の段落、箇条書きなどセル内部を独立した説明領域として使う表現は入れない。

## 文の組み立て

文法的に成立すること、意図した意味になること、場面にふさわしいことを分けて扱う。

本文中の長い名詞句は名詞の連結で関係を省略せず、助詞や述語で関係を示す。

文は、誰が何をするのか、どの条件で成り立つのか、何を否定・限定するのかが伝わる形に組み立てる。
語句を省略・置換するときは、その語句だけを処理せず、前後とのつながりを含めて文を書き直す。
元の意味を保ったまま、修飾先、主語と述語の対応、助詞のつながりが成立する形に整える。

### 能動と受動

「課長が申請を承認した」は動作主を、「申請は課長に承認された」は対象を中心に述べる。
責任を伝えるなら動作主を示し、対象の状態を説明するなら受身も使う。

### 否定と限定

「すべて承認したわけではない」は全件承認の否定であり、「どれも承認しなかった」とは異なる。
「必ず成功するわけではない」も「必ず失敗する」とは異なる。

「管理者だけが設定を変える」は主体、「管理者が設定だけを変える」は対象を限定する。
標準的な「しか」は否定形と組み合わせ、「管理者しか変更できない」は管理者以外では変更できないことを表す。

二重否定は留保を表す場合がある。「対応できないわけではない」を単純な肯定へ変えるのは、その含みも保てる場合に限る。

### 確かさと働き掛け

内容の確かさと、読者への拘束力を選び分ける。
「接続先が停止した可能性がある」を、原因未確認のまま「停止した」へ変えない。
推量を削ったり、根拠のない慎重さを加えたりしない。

次は一般的な用法である。他に定義がある場合はそれに従う。
複数の解釈を持つ表現は誤読に注意する。

- しなければならない: 義務
- してよい / してもよい: 許可
- してはならない: 禁止
- しなくてもよい / する必要はない: 義務の否定
- できる: 許可、能力の主張、実現可能性
- すべき: 規範的判断、推奨

### 条件表現

「再試行しても失敗する」と「再試行したら失敗する」は前後の関係が異なる。
「参加するなら連絡して」は参加する意思があることが条件で、「参加したら連絡して」は参加したことが条件である。
「たら」「なら」「ても」などは前後の関係に合わせて選ぶ。

## 語彙選択

意味に合い、読者が直接理解できる語を選ぶ。
同義に見えても、対象や要求の強さが変わる語へ置き換えない。
同じ概念には一貫した呼び方を使い、異なる概念を同じ語へまとめない。

平易で定着した日本語表記がある一般語は日本語で書く。
識別子や引用は元の表記で書く。
専門用語を言い換えると意味を保持できない場合は想定読者に合わせて必要な説明を添える。
術語・訳語は、その分野で慣用されている語を選ぶ（プッシュ通知は「配送」ではなく「配信」、など）。意味の近い漢語を一般語の感覚で充てない。
術語の響きを持つ語を、術語でない場面に流用しない（システムから人間までの連なりを「経路」と呼ぶ、など）。「届くまでの流れ」「間に何があるか」のように普通の言い方で書く。

例:

- 「readability を改善する」ではなく「読みやすさを改善する」
- 「accessibility に配慮する」ではなく「アクセシビリティに配慮する」
- 「変数 `readability` を宣言する」

### 用語の導入

文書内で概念に名前を付ける場合は、後の説明でその概念を繰り返し指す必要がある場合に限る。
最初に使う位置または用語定義の節で名前と意味の対応を示し、その後は同じ名前で指す。
既存の語で十分に表せる概念へ新しい用語を作らない。

## 補足と対比

括弧や注記には、その位置で解釈を助ける短い補足を置く。判断に必要な条件や長い説明は本文に置く。言い直すだけの補足は加えない。

- 良い例: 「Portable Document Format（PDF）」 ... 名称と略称を結ぶ
- 悪い例: 「情報源の確認（正しい資料を使う）」 ... 同じ主張の言い換え

対比は対象の違いが読者の理解や判断に必要な場合に使う。
対比の対象はその時点の文章展開や想定読者の知識から読者が持つと合理的に見込めるものに限る。
読者のメンタルモデルに存在しない前提を持ち出したり否定したりしない。

## 見出しの付け方

見出しは内容を特定できる具体的なものにする。その節が答える問い、または扱う対象を指す句にする。

- 内容を示す具体的な文の他、節で扱う対象を指す名詞句を見出しとしてもよい。
- 見出しは疑問形でも断定形でも良い。扱う対象や読者の持つ問いを指しているかを考えて見出しを付ける。
- 疑問形か、対象を指す名詞句かは、本文のトーンに合うほうを選ぶ。

## Markdown の強調

強調は、読み落とされると理解や行動が変わる箇所に使う。
強調が多すぎると重要度の差が伝わらず、強調していないのと同じになる。

日本語文章においては Markdown レンダラーの都合により強調にはいくつかの制約がある。

斜体構文を使っても日本語フォントの斜体表示が機能しない場合がある。
想定するレンダラーで日本語の斜体表示が機能することを確認できない場合は日本語の文字に斜体を適用しない。

日本語の文字が強調構文の外側に隣接すると強調の境界の検出に失敗する場合がある。
強調構文の外側に日本語の文字が隣接する場合は、構文の外側を半角スペースで区切る。
また、強調の外側に日本語の句読点を置かない。

例:

- 設定を **保存する** と反映される。
- これは **重要な条件。** 次の操作より前に満たす。
- 英単語 _emphasize_ は強調するという意味。
