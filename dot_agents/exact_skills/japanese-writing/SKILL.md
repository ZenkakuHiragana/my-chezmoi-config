# 日本語で情報を伝える

文章表現は情報伝達の一形態である。必要な意味を保ち、読者が目的を果たすまでの認知負荷を小さくする。短さそのものではなく、情報の探索や関係の復元にかかる余計な負担を減らす。

## 追加資料の読み込み

この本文を通常の執筆に使う。操作手順、依頼、規則など、実行者の行動を指示する文章を書く場合は、書き始める前に [指示を文章にする](references/instructions.md) を読む。

[根拠資料の案内](references/sources.md) は既知の資料の所在と適用範囲を示す。日本語の語義・用法・表記に関する主張または問いを資料へ照合する仕事では、情報源を選ぶ段階で読む。資料案内は調査手順を定めるものではない。

以下の例は使い分けを示すためのものである。例示の内容は実際の作業に対する要求としては扱わない。

## 読者に何を渡すか

依頼と対象から、誰が何のために読む文章なのかを捉える。読者の目的と既知の内容に合わせて、今回伝える情報の範囲と深さを選ぶ。調査で把握する範囲と、読者へ報告する範囲は同じではない。把握した情報をすべて提示する必要はない。

求められた情報と、理解や判断に必要な関係を残す。事実・推測・未確定の区別を保ち、文章を整えるために新しい事実や要求、結論を作らない。作業経緯も、その説明を求められた場合は内容となる。情報の種類だけで排除せず、今回の読者の目的に対応する範囲を選ぶ。

読者の前提にできるのは、受け取る時点で持つ知識と、本文または通常の利用経路から得られる説明である。会話への返答では会話の文脈を使い、独立した文書にはその読者に必要な前提を置く。今回の読者の目的に関係しない編集経緯や却下案を混ぜない。例えば、一覧を削除する指示を受けたことだけを理由に、本文へ「一覧は別資料を参照する」と残す必要はない。

選んだ内容の主題を定め、理解に必要な前提から新しい情報へ進む。主張には理由を、操作には条件を結び付ける。その位置に短い説明を置けば読み戻りを減らせるなら、文字数だけを理由に省かない。

## 伝えるべき内容に合う表現を選ぶ

出力先で使える形式から、情報の関係が伝わるものを選ぶ。

| 読者が得る情報             | 表現の選び方                                   |
| -------------------------- | ---------------------------------------------- |
| 理由や因果をたどる説明     | 文で関係を示し、一つの主題を段落にまとめる     |
| 必要な節を探す長い説明     | 内容が分かる見出しを付け、包含関係を階層で示す |
| 個別に拾う同格の項目       | 箇条書きにする                                 |
| 順番に行う操作             | 番号付きの手順にし、前後関係を示す             |
| 共通の軸で比べる対象       | 軸を見出しにした表で、値と対象を対応付ける     |
| 文章だけでは追いにくい関係 | 図で示し、読み取る要点を本文で説明する         |
| 正確な文字列を使う操作     | コード表記やコードブロックで説明文と区別する   |

文章中で項目を列挙する表現は原則として多用しない。項目の列挙は、各項目を後で別々に扱う必要がある場合に限る。集合として扱えば足りる場合は、上位の概念でまとめる。短い「氏名と連絡先を入力する」のように、共通の役割が明らかな列挙は使える。

因果や役割の違いは、関連する名詞の列挙ではなく関係として述べる。「依頼から確認対象を定め、その対象について資料を調べる」を「依頼、対象、資料を確認する」に変えると、何が何を決めるかが消える。箇条書きへ置き換えても関係は回復しない。ただし、実際に各項目を照合する依頼なら対象を省かない。

表は共通の軸を繰り返し読む負担を減らすために使う。「保存先は指定フォルダである」だけなら一文で足り、表にするための比較軸は作らない。見出しは節の主題を示し、各文を見出し付きの断片にしない。

## 用途から中心を決める

次は用途ごとの選択肢であり、すべての文章に同じ章立てを要求するものではない。

| 用途     | 読者が得るものと情報の配置                                               |
| -------- | ------------------------------------------------------------------------ |
| 仕様     | 適用対象を示し、条件と結果を対応付ける。例外は該当条件に結ぶ             |
| 手順     | 開始条件を置き、操作を実行順に示す。分岐と結果の見分け方を結ぶ           |
| 説明     | 必要な概念を導入し、仕組みの中心となる関係と理由から詳細へ進む           |
| 設計     | 確定した判断と、それを支える構造を示す。目的に対する責務と関係の働きを述べ、判断の理由と制約を結ぶ |
| 参照資料 | 名前から引ける定義や値を置き、共通項目をそろえる                         |
| 報告     | 観測結果と根拠をつなぎ、言えることの条件と限界を添える                   |

操作前の注意が結果を左右するなら、その操作より先に置く。「例外は後に書く」という順序を安全条件にまで適用しない。「保存し、保存完了後に閉じる」のような手順では、番号の順序だけでなく次へ進む条件も伝える。

## 文の組み立てで意味を表す

文法的に成立すること、意図した意味になること、場面にふさわしいことを分けて扱う。

### 述語から文を組み立てる

助詞は、名詞が述語に対してどのような役割を持つかを表す。例えば「担当者が利用者に結果をメールで知らせる」では、助詞によって次の関係を示している。

| 文中の表現 | この文で示す役割 |
| --- | --- |
| 担当者が | 知らせる人 |
| 利用者に | 知らせる相手 |
| 結果を | 知らせる内容 |
| メールで | 知らせる手段 |

「資料に基づく」と「資料を基にする」のように、述語が変われば適する助詞も変わる。名詞が同じことを理由に助詞を統一しない。

主題と動作主を区別する。「この資料は担当者が更新する」の主題は資料、動作主は担当者である。「は」が付く語を必ず動作主として扱わない。

後ろの語に合う活用を使う。「静かな部屋」は名詞を、「静かに話す」は動作を修飾する。長い名詞句も「新規顧客への対応手順を変更する案」のように助詞で関係を示す。修飾先が分かる位置へ修飾語を置き、読点は係り受けや語の切れ目を示すために使う。構造が定まらない文を、読点の追加だけで直そうとしない。

### 話題と焦点をつなぐ

「担当者は確認した。管理者はまだ確認していない」は対比、「誰が確認したのか。担当者が確認した」は問いへの焦点を示す。「は」と「が」を表記の揺れとして統一しない。

「担当者は資料を受け取り、確認した」のように同じ主体を回復できる箇所では省略できる。途中で管理者の動作へ移るなら主体を示す。「それ」「この結果」は対象を定められる位置で使い、複数の候補があるなら名詞を繰り返す。段落を変えても前段の条件や対象が解除されるわけではない。

### 出来事のどこを中心にするか

「委員会が申請を承認した」は動作主を、「申請は委員会に承認された」は対象の扱いを中心に述べる。責任を伝えるなら動作主を示し、対象の状態を続けて説明するなら受身も使う。「雨に降られた」のような受身は影響を受けた側を表し、すべてが能動文の単純な置換ではない。

使役では働き掛ける人と実行する人を区別する。「再実行させる」が強制か許容かで責任が変わるなら、「再実行を命じる」「再実行を許可する」と関係を表す。

### 時間と状態を表す

「今、担当者がファイルを更新している」は作業中、「更新済み」は完了、「扉が開いている」は開いた後の状態を表す。「ている」を進行、「た」を過去とだけ決め付けない。「こんな所にあった」は発見も表す。動詞と文脈に合う形を選ぶ。

報告では、観測時点と読者が読む時点を区別して時間の基準を示す。「確認してから送る」と「送ってから確認する」の順序は、語順を整える際にも保つ。

### 否定と限定の範囲を保つ

「すべて承認したわけではない」は全件承認の否定であり、「どれも承認しなかった」とは異なる。「必ず成功するわけではない」も「必ず失敗する」とは異なる。

「管理者だけが設定を変える」は主体、「管理者が設定だけを変える」は対象を限定する。標準的な「しか」は否定形と組み合わせ、「管理者しか変更できない」は管理者以外では変更できないことを表す。

「も」は同類の追加や、「百人も来た」のような多さを表す。追加や意外さの基準は文脈と結び付ける。二重否定は留保を表す場合がある。「対応できないわけではない」を単純な肯定へ変えるのは、その含みも保てる場合に限る。

### 確かさと働き掛けを区別する

内容の確かさと、読者への拘束力を選び分ける。「接続先が停止した可能性がある」を、原因未確認のまま「停止した」へ変えない。断定の形は根拠にならず、条件が分かることと、その条件下で必ず起こることも別である。推量を削ったり、根拠のない慎重さを加えたりしない。

「提出しなければならない」は義務、「提出してよい」は許可、「提出してはならない」は禁止、「提出する必要はない」は義務の否定である。「できる」は能力や実現可能性にも読めるため、許可は区別して伝える。「べきだ」は規範的判断や推奨にも使う。文書内で義務表現が定義されている場合は、その定義を保つ。

### 節と文の関係を表す

原因、目的、譲歩など、伝える関係に合う接続を選ぶ。「再試行しても失敗する」と「再試行したので失敗する」は別の関係である。単なる出来事の連続を「だから」で結び、因果を作らない。

「参加するなら連絡してほしい」は参加を前提とし、「参加したら連絡してほしい」は参加後とも読まれる。「と・ば・たら・なら」を無条件に交換せず、前件が仮定か事実か、後件が依頼か結果の説明かに合わせる。

並列では共通の受け先を示す。「AとBを提出する」は両方、「AまたはBを提出する」は選択を表す。両方を選べるかが判断に関わる場合は、その扱いも示す。

## 語を選ぶ

意味に合い、読者が直接理解できる語を選ぶ。同義に見えても、対象や要求の強さが変わる語へ置き換えない。同じ概念には一貫した呼び方を使い、異なる概念を同じ語へまとめない。

平易で定着した日本語がある一般語は日本語で書く。「readability を改善する」は「読みやすさを改善する」で足りる。一方、設定名が `readability` なら原表記を保つ。「ファイル」のように定着したカタカナも日本語表記である。識別子・正式名称・引用は保持し、専門語を言い換えると精度が落ちる場合は説明を添える。

初めて仕組みを学ぶ読者には「一度得た結果を保存し、再利用する仕組みをキャッシュと呼ぶ」のように役割から導入できる。名前を引く辞書では「キャッシュ: 一度得た結果を保存し、再利用する仕組み」と名前から入る。名前と説明の順序を一律に固定せず、その位置で何を指すか分かるようにする。

なじみのなさだけで誤用と決めず、意味と使用場面を分ける。資料を利用できない場合や、語義・用法・定着度を資料から確認できない場合は、確認済みとして断定せず未確認と区別して書く。

## 補足と対比を置く

括弧や注記には、その位置で解釈を助ける補足を置く。判断に不可欠な条件や、主題の理解に必要な長い説明は本文に置き、言い直すだけの補足は加えない。「Portable Document Format（PDF）」は名称と略称を結ぶが、「情報源の確認（正しい資料を使う）」が条件も内容も増やさないなら括弧は不要である。例示と全範囲を区別し、見出しを詳しくするために本文にない作業を作らない。

否定は不成立や禁止そのものも伝える。「復旧しなかった」「撮影してはならない」は、先に対立候補が出ていなくても成立する。対比は、候補の違いが読者の理解や選択を変える場合に使う。読者の知らない却下案を否定するためだけの説明は加えない。

## 説明と参照をつなぐ

文書の役割を果たす範囲を説明する。複数文書では既存の責務に従い、定義や一覧の正本を増やさない。その場の理解に必要な短い説明は本文に残し、詳細へ進める参照を添える。関連していることだけを理由に参照を増やさない。

読者がリンクを開く前に、参照先で何を確かめられるか分かるようにする。そのために、リンクの名前や直前の説明に参照の目的を書く。参照する説明が特定の節にあり、その節へのリンクを利用できる場合は、文書全体ではなく該当する節へ案内する。

## 文体と媒体に合わせる

読者との関係と場面に合う文体を選び、本文では一貫させる。引用や画面の固定文言は原文を保つ。

敬語は、敬意を向ける相手と行為の関係に合わせて選ぶ。例えば、尊敬語の「おっしゃる」は発言する人を立て、謙譲語の「申し上げる」は自分側の発言を受ける相手を立てる。敬語を正しく使い分けることと、丁寧さを増すことは別である。

「です・ます」と「だ・である」に文法上の優劣はない。体言止めは見出しや要約に使えるが、判断や動作まで省いて読者に補わせない。

### 構造を記法へ写す

出力先の画面幅、ページ分割、利用できる構造に合わせる。見出しの階層は包含関係に合わせる。見出し用の記法が使える形式では、それを使う。太字だけでは、目次や見出し移動に使える構造にならない場合がある。箇条書きの補足は所属を明らかにし、手順は順序を表す記法で書く。番号を参照する文書では番号と対象の対応を保つ。

表は行・列の見出しとセルを対応付ける。狭い画面に長文の列を押し込まず、表を分けるか項目ごとに説明する。比較ではなく文字を左右に置くためだけの枠にしない。

### 図と補足を読む順に置く

図は、その図が説明する内容を本文で取り上げる箇所の近くに置く。表題で図が何を示すかを伝え、本文では読み取るべき関係を説明する。

処理の実行順と、データの包含関係や対応関係は区別して説明する。図の要素には本文と同じ名前を使うなど、何を表すか分かるようにする。線や記号の意味を説明し、色や形だけで重要な違いを伝えない。数値の図には軸と単位を示す。

例や注記も説明対象の近くに置き、操作前の条件を離れた脚注へ追いやらない。

### 固定文字列を示す

コード、設定値、テンプレートは翻訳せず、説明文から区別する。

文章にコードや設定値の例を載せる場合は、その例を何に使うのかと、コードや設定のどこをどう読むのかを、コードブロックの前後に説明する。例示用の値なのか、そのまま入力してよい値なのかを読者が区別できるようにする。

コピーする文字列に説明や行番号を混ぜず、装飾のための空白や改行を加えない。長いパスやコードは文字列を変えず、表示幅やブロックの配置で全文を取得できるようにする。

### Markdown の強調境界

強調は、読み落とされると理解や行動が変わる箇所に使う。日本語の本文で `**` による太字や `*`・`_` による斜体を使い、前後の文字が ASCII 文字でない場合は、表示事故を避ける執筆上の方針として、構文の外側を ASCII 空白で区切る。行頭・行末には追加の空白は要らない。

```markdown
設定を **保存する** と反映される。
これは **重要な条件。** 次の操作より前に満たす。
用語を _強調する_ 場合も外側を区切る。
```

句点を強調範囲に含める場合も、句点と閉じる `**` の間へ空白を入れない。この方針は、日本語に隣接する強調が必ず不成立になるという意味ではない。CommonMark では区切りの内外にある空白や句読点の位置が成立に関わり、内側が括弧などで始まる場合も外側との境界が重要になる。詳細は [CommonMark 0.31.2 の強調規則](https://spec.commonmark.org/0.31.2/#emphasis-and-strong-emphasis) による。

### ページ構成

PDF やスライドでは、ページ内で必要な関係を読めるように置く。表の見出しだけが前のページに残る配置や、説明対象から離れた注記は避ける。内容を収めるために文字を小さくし続けるのではなく、主題に沿って分割する。表紙から各節へ進む順序と、見出し番号が示す構造を一致させる。
