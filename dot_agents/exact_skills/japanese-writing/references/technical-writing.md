# 技術文書の構成

技術文書では、読者が対象を理解し、必要な判断や操作へ進めるように情報を配置する。以下は文書の用途に応じた選択肢であり、すべての文書に同じ章立てを要求するものではない。

## 用途から中心を決める

| 用途 | 読者が得るもの | 情報の配置 |
| --- | --- | --- |
| 仕様 | どの条件で、どの結果が成立するか | 適用対象を示し、条件と結果を対応付ける。例外は該当する条件に結び付ける |
| 手順 | 目的の状態へ進む方法 | 開始に必要な条件を置き、操作を実行順に示す。分岐と結果の見分け方を対応付ける |
| 説明 | 仕組みとその理由 | 必要な概念を導入し、中心の関係を説明してから詳細へ進む |
| 設計 | 確定した判断と、それを支える構造 | 目的に対して責務と関係がどう働くかを述べ、判断の理由と制約を結ぶ |
| 参照資料 | 名前から引ける定義や値 | 調べる名前を入口にし、共通項目をそろえて探しやすくする |
| 報告 | 観測結果から言えること | 結果と根拠をつなぎ、条件と限界を添える |

説明では中心となる仕組みから入ると、詳細の位置付けが分かりやすい。一方、操作前の注意が結果を左右するなら、その操作より先に置く。「例外は後に書く」という順序を安全条件にまで適用しない。

## 説明と参照をつなぐ

一つの文書では、その文書の役割を果たす範囲を説明する。複数の文書に分ける場合は既存の責務に従い、定義や一覧を管理する正本を増やさない。読者がその場で必要とする短い説明は本文に置き、詳しい定義へ進める参照を添える。

参照の粒度は、読者が調べる対象と媒体の安定性に合わせる。節を特定できるリンクが維持されているなら、文書全体を指すだけにしない。リンクの文字列または周辺の文で、参照先から何を得られるかを伝える。関連しているという理由だけで、読者の作業に要らない参照を増やさない。

仕組みの説明では、処理順とデータの関係を区別する。複雑な関係は図で示せるが、図の記号が本文のどの概念に対応するかも示す。

## 指示を文章にする

指示では、実行者が判断する順に情報を置く。使用条件を示し、与えられる入力から動作と結果へつなぐ。禁止や停止条件は、それを判断する操作に結び付ける。説明用の文や背景まで命令の形にそろえない。

複数の実行者が関わる場合は、誰が決め、誰が動くかが分かるようにする。同じ実行者が続く箇所では主語を省略できる。スキル名や文書名を、意思決定や受け渡しを行う人の代わりに主語として使わない。

受け渡しでは、どこから何が届き、受け取った側がどう使うかをつなげて述べる。宛先や用途がすでに呼び出し関係から定まるなら、各文に同じ説明を繰り返さない。複数の読み方が生じる境界に、必要な主体と対象を示す。

確定した手順を文章化する際は、完了時に何が得られ、その成否をどう見分けるかも伝える。書式を埋めるために、元の手順にない入力や停止条件を作らない。

## 固定文字列を示す

操作や照合に使う名前は、原表記を保って説明文と区別する。コード、設定値、テンプレートを日本語へ翻訳しない。説明には日本語を使い、文字列が指す役割を示す。

例の値と、そのまま入力すべき値を区別する。空白や記号を整えるだけでも動作が変わることがあるため、実行用の文字列に装飾のための変更を加えない。コードブロックの外に、その例の用途と読み取り方を書く。
