# シェルスクリプトのレビュー用プロファイル

POSIX 系シェルや Bash のスクリプトについて、展開後の引数と終了状態を追い、意図した操作が実行されるかを確認する。
見た目のコマンド文字列だけでなく、シェルが解釈した後の値と実行環境を調べる。

## 呼び出す環境と処理の定義

shebang と実際の起動コマンドを確認し、どのシェルのどの版で動くかを確かめる。
Bash の配列を使う処理を `sh` で起動していないかなど、記述と呼び出し方の一致を調べる。
外部コマンドのオプションや出力形式も、対象 OS の実装で利用できるかを確認する。

関数や補助スクリプトの呼び出しは、定義と読み込みが実行前に済むかをたどる。
条件付きで読み込むファイルや動的に選ぶコマンドも、実際の入力で解決できるかを確かめる。
名前が似ていることだけを改名漏れの証拠にせず、定義と呼び出しの対応を確認する。

変更のレビューでは、変更した分岐から到達する共通の末尾処理と既存分岐も読む。
最初の未解決呼び出しを見つけても、残る呼び出しの確認を続ける。
抜粋外の定義や実行環境を確認できない場合は、未定義と断定せず、その不足を分けて返す。

## 引数と出力の境界

変数展開やコマンド置換を使う箇所では、展開後に何個の引数が渡るかを確認する。
空白やワイルドカードを含む値、空の引数が、意図せず分割・消失しないかを調べる。
引数を転送する `"$@"` や、Bash の配列を展開する形式も、要素の境界を保っているかを確かめる。

外部から得た値がオプションや命令として扱われる箇所を調べる。
クォートして一つの引数にしても、先頭の `-` をオプションとして解釈する問題は別に残る。
`--` の利用可否は呼び出すコマンドごとに確認する。
`eval` やシェルへの文字列渡しでは、再解釈する理由と、そのときにデータが命令へ変わらない条件を調べる。

標準出力をデータとして受け取る処理では、進捗や診断の文字列が混ざらないかを確認する。
コマンド置換によって末尾の改行が取り除かれることも、データの契約に照らす。
補助関数が一つのコマンド文字列を返す契約なら、複数行や余分な文字列を返していないかを確かめる。
他の用途の出力まで一行に制限しない。

コマンドの出力を解析する場合は、対象が提供する機械処理用の形式を確認する。
人間向け表示の桁や翻訳された文言へ依存し、環境や入力によって解釈が変わらないかを調べる。

## 失敗と状態の伝わり方

終了状態を判定する箇所では、どのコマンドの結果を見ているかを確かめる。
例えば `local value=$(command)` では、宣言コマンドの終了状態によって、内部で実行したコマンドの失敗を見落とさないかを調べる。
途中に別のコマンドを挟んで `$?` の意味が変わる場合も確認する。

`set -e` に任せた処理は、条件式や関数の呼び出され方によって、失敗時の扱いが変わる箇所を調べる。
パイプラインでは、どの終了状態が全体の結果になるかを、対象シェルと `pipefail` などの設定から確認する。
厳格な設定を追加すればすべて解決するとは判断しない。

サブシェルやパイプライン内の処理では、変数や作業ディレクトリの変更がどこまで残るかを確認する。
読み込んで実行するスクリプトと、別プロセスで起動するスクリプトも区別する。
バックグラウンド処理は、開始したことだけで成功とせず、必要な完了と終了状態を受け取れるかを確かめる。

## 後始末と検査

一時ファイルの作成と削除では、他の実行と衝突せず、第三者が先に用意した対象を操作しないかを調べる。
`trap` では、登録時と実行時のどちらで値が展開され、どの資源を後始末するかを確認する。
初期化前の失敗でも、空のパスや無関係なファイルを削除しないかを見る。

失敗後の代替処理や再試行は、元の失敗を隠したり、既に完了した操作を重複して実行したりしないかを確認する。
環境変数による切り替えと、その説明が実装で一致するかも調べる。

構文検査と既存の ShellCheck、テストを利用し、実行する場合は副作用を許可された範囲に収める。
構文が通ることは、関数や外部コマンドが実行時に解決できることの証拠にはならない。
起動や再試行など、対象の状態を変える利用方法を何で検査したかを確認し、未確認の動作を明示する。
