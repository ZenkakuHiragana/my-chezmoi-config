# C# + .NET レビュー用プロファイル

C# の型と非同期処理、.NET が管理する資源の寿命を、実際の呼び出し方へ照合する。
構文の新しさではなく、契約を読み取りやすく、誤った使い方を検出できる実装かを確認する。

## 型と実行条件

プロジェクトの対象フレームワークと、言語・アナライザーの設定を確認する。
複数の構成がある場合は、条件によって参照する実装や生成されるコードが変わる箇所を調べる。
検査には、対象に用意されたビルドとテストを使う。

null 許容の宣言を、値を作る側と受け取る側の両方から確認する。
警告抑制の `!` は実行時の検査を追加しないため、その位置で null にならない根拠を調べる。
外部データの読み込みやリフレクションを経る値も、型の宣言だけで有効と判断しない。

型名やプロパティー名を文字列で扱う箇所では、改名による影響を確認する。
コード内の名前を参照する場合と、外部形式で固定された名前を使う場合を区別する。
`nameof` へ置き換えたために、内部の改名が外部の契約まで変えてしまう構造を正しい共通化としない。
状態による処理の振り分けでは、種類を追加したときに必要な対応の抜けを検出できるかを調べる。
列挙型やパターンマッチを使ったことだけで、対応が揃ったとは判断しない。

文字列の比較では、識別子として一致を調べるのか、人が読む言語上の比較を行うのかを確かめる。
実行環境のカルチャーによって意図せず判定が変わらないかを見る。値型のコピーと参照型の共有も、更新する対象を取り違える箇所では区別する。

## 列挙と処理の費用

LINQ や `IEnumerable` を使う処理では、結果を定義した時点と、実際に列挙する時点を区別する。
同じ列を複数回たどることで、検索や変換、副作用が繰り返されないかを調べる。
列挙するまでに元のデータや利用する資源が変わる場合は、結果へ及ぼす影響も確認する。

`ToList` や `ToArray` は、割り当てがあるという理由だけで不要としない。
一度得た結果を固定するためか、再列挙を避けるためかを確かめ、保持する費用と作り直す費用を比較する。
反対に、全件を保持せずに使える結果を、繰り返し大きな中間配列へ変えていないかも調べる。

高頻度の処理では、ボックス化や文字列の生成、リフレクションなどの費用を、実際の回数と入力規模へ結び付ける。
正規表現や変換処理を再利用する場合も、設定や入力条件が変わるのに古い状態を使い続けないかを確かめる。

## 非同期処理と失敗

返されたタスクを誰が待ち、失敗を誰が受け取るかを、呼び出し側までたどる。
`async void` では呼び出し側がタスクとして完了を待てないため、イベントハンドラーのようにその形式が必要な場合と、完了や失敗を返す必要がある通常の処理を区別する。

非同期処理を同期的に待つ箇所では、継続を実行するためのスレッドや実行枠まで塞がないかを調べる。
待機の仕組みと呼び出される環境を確認し、同期的な待機があるという理由だけでデッドロックと断定しない。

キャンセルに対応する処理では、要求が必要な呼び出し先まで届き、途中で止まった状態を扱えるかを確かめる。
キャンセルを完了や成功へ読み替えたり、広い `catch` で原因を失ったまま既定値を返したりしていないかを見る。

## 資源と利用者の寿命

`IDisposable` や `IAsyncDisposable` を実装する資源は、所有する側と利用する側を区別する。
`using` の範囲を抜けた後にタスクや遅延列挙がその資源を使わないかを確認する。
必要な非同期の後始末が終わる前に、所有者が完了を報告していないかも調べる。

依存性注入を使う対象では、登録した寿命と実際に保持する期間を照合する。
長寿命のサービスが短寿命のサービスを保持していないか、コンテナーが管理する資源を利用側が先に破棄していないかを確認する。
イベント購読についても、購読先が生き続けることで不要な参照や通知が残らないかを見る。

公開 API の説明や XML 文書は、null、失敗、完了の扱いが実装と一致するかを確かめる。
診断結果を根拠にする場合は成立条件を確認し、警告を消したことを問題の解消と取り違えない。
実行できなかった検査は、そのために未確認となる挙動を示す。
