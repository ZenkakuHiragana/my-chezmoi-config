# Rust + Cargo レビュー用プロファイル

Rust の所有権や型による保証を活かしつつ、コンパイラーだけでは保証できない、対象の仕様が求める状態と失敗の扱いを確認する。
Cargo を使う対象では、利用者が選ぶ構成でも同じ契約が成立するかを調べる。

## 所有権と型の表現

対象の Rust の版、エディション、ビルド対象を確認する。
値を渡す箇所では、所有権を移すのか、借用するのか、複製して独立させるのかを利用側までたどる。
借用を通すために無関係な部品の寿命を結び付けたり、所有する主体を決めないまま共有を広げたりしていないかを調べる。

`clone` や `collect` は、作る値と利用回数から必要性を確認する。
`Arc` の複製は、中身を独立させるのではなく共有する所有者を増やす。
複製を削れば常に良いとはせず、更新の独立性や寿命を保つ目的と、その費用を比較する。

状態を表す型では、本来成立しない組み合わせを作りやすくしていないかを確認する。
`match` の残りを一括で扱う分岐は、新しい状態への必要な対応を隠さないかを調べる。
一方、未知の値を受け入れる契約や、外部の拡張を許す型では、そのための分岐と区別する。

## 失敗と安全性

`Result` と `Option` は、呼び出し側が区別すべき失敗や値の不在を保っているかを確認する。
エラーを変換する箇所では、回復に必要な種類や原因を失っていないかを見る。
`unwrap` や `expect` は、失敗しない条件を実装から確かめる。
外部入力で崩れる前提と、固定した値について証明できる前提を同じ扱いにしない。

`unsafe` では、その操作が必要とする型、寿命、アクセス範囲を確かめる。
コメントに安全と書かれていることではなく、実装が条件を維持する根拠を確認する。
安全な関数から内部状態を変えられる場合は、その変更によって後の `unsafe` の前提を壊せないかまで調べる。

公開する安全な API は、呼び出し側が許された使い方をしただけで未定義動作を起こせないかを確認する。
手動で実装する `Send` や `Sync` も、宣言の存在を保証として扱わず、共有と移動に関する条件を実装全体へ照合する。

## 非同期処理の進行と終了

Future を作ることと、完了まで実行することを区別する。
待機する処理やタスクを開始する処理から、結果と失敗を受け取る側までをたどる。
タスクのハンドルを破棄した場合の挙動は実行基盤の仕様で確認し、ハンドルが消えれば処理も停止するとは推測しない。

中断によって Future が破棄される場合は、途中まで変わった状態と残る資源を確認する。
待機中に保持するロックでは、他の処理の進行を妨げる条件を調べる。
非同期の実行枠で同期的な入出力を行う場合も、その間に他の仕事が進めるかを確かめる。

`Arc` は共有する値そのものの更新を自動で安全にするものではない。
内部可変性や同期の仕組みを含め、複数の処理が保つべき状態をどう維持するかを確認する。

## Cargo の構成と生成

依存関係をたどり、実際に有効になるフィーチャーを確認する。
同じ依存へ複数の経路からフィーチャーが追加される場合は、対象のリゾルバーの規則に照らす。
一箇所で `default-features = false` と書いたことだけで、全体でも既定のフィーチャーが無効とは判断しない。

検査する構成は、提供すると決めた機能と対応対象から選ぶ。
すべてを有効にしたビルドでは、最小構成の依存不足が隠れる場合がある。
テスト用の依存や設定だけで使える機能を、通常の利用でも使えるものとしていないかも調べる。
対応を約束していない組み合わせまで機械的に要求しない。

`build.rs` は、どの入力や環境変数で生成結果が変わるかを確認し、その変更で再実行されるかを調べる。
生成物の出力先と利用順を確かめ、開発環境のファイルへ依存していないかを見る。
クロスコンパイルでは、ビルド用のプログラムが動く環境と、生成する成果物が動く環境を区別する。

検査には、既存の `cargo check`、テスト、Clippy などを使う。
チェックの成功を、実際のリンクやテスト実行の成功と混同しない。
警告の抑制がある場合は理由を確認し、対象の構成と根拠を示して問題を返す。
