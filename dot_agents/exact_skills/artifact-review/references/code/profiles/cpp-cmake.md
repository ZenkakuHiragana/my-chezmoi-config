# C++ + CMake レビュー用プロファイル

C++ のコードについて、型と資源の扱いを実際の利用箇所へ照合する。
CMake を使う対象では、ビルドする部品と利用する部品の間で、必要な設定が伝わるかも確認する。

## 対象の構成を確認する

使用する C++ の規格とコンパイラー、実際に有効になるビルド設定を確認する。
新しい構文が使えることと、対象が対応する環境で使えることを区別する。
条件付きコンパイルでは、対象の構成でどの定義が選ばれるかを調べる。

検査には、プロジェクトに用意されたビルドやテスト、静的解析を優先する。
警告は、その箇所の型と利用条件を調べる手掛かりとして扱う。検査を通すために設定やコードを変更しない。

## 所有権と参照の寿命

ポインターや参照を渡す処理では、資源を所有する側と借りて使う側を区別する。
取得から解放までをたどり、途中の例外でも取得済みの資源が後始末されるかを確認する。
資源の解放をオブジェクトの破棄へ結び付ける RAII と、各呼び出し側が手動で守る約束を区別する。

返却する参照やビューは、利用が終わるまで参照先が有効かを調べる。
`std::string_view` や `std::span` 自体をコピーしても、参照先の寿命を延ばすことにはならない。
コンテナーの更新による参照やイテレーターの無効化も、その後の使用まで追って確認する。

ラムダが参照や `this` を捕捉する場合は、呼び出される時点まで対象が存在するかを確かめる。
共有所有を使う場合も、循環参照で解放されなくなる条件や、共有した値の更新が別の利用者へ影響する条件を調べる。
生ポインターという形だけで所有と判断せず、共有所有への変更も一律には求めない。

基底型を介してオブジェクトを破棄する処理では、実際の型に必要な破棄が行われるかを確認する。
基底型から破棄する設計と、その使い方を禁止する設計を区別し、すべての基底クラスへ仮想デストラクターを要求しない。
コピーやムーブを独自に定義する型では、操作後に資源を二重に解放する状態にならず、元と先がそれぞれ許された状態に保たれるかを確かめる。

## 型と処理の意味

暗黙変換やオーバーロードがある箇所では、選ばれる型と処理を確かめる。
符号や精度の違いで比較が変わったり、基底型への値渡しで必要な情報が失われたりしないかを、入力から結果まで調べる。
状態の種類が決まっている場合は、その区別を型と分岐から追えるかを確認し、手動の型タグと値の組み合わせが矛盾する状態を作れないかを見る。

低水準の操作は、メモリー上に領域があることだけで正しいとしない。
対象の型と寿命、アクセスする範囲が操作の前提を満たすかを確認する。
型を読み替えるキャストでは、その型でアクセスしてよい根拠も調べる。
手元で期待どおり動いた結果だけを、未定義動作がない証拠にしない。

複数の処理が同じ値へアクセスする場合は、同期が保護する範囲を確認する。
個々の操作がアトミックでも、複数の操作で保つ条件まで保証されるとは限らない。
ロック中の呼び出しもたどり、再入や別のロック取得によって処理が進まなくならないかを調べる。

繰り返す処理では、値渡しや一時コンテナーの作成によって、何を何回コピーしているかを確認する。
コピーが独立した値を保つために必要なのか、読み取るだけなのに作り直しているのかを区別する。
テンプレートやマクロによる共通化も、利用するために各呼び出し側が内部の条件を覚え直す構造になっていないかを見る。

## CMake の依存関係と生成処理

ターゲットごとの設定を読み、その部品だけに必要な条件と、利用側にも必要な条件を区別する。
`PRIVATE`、`PUBLIC`、`INTERFACE` の指定によって、公開ヘッダーを読む側へ必要な定義が届くか、逆に内部用の設定を無関係な部品へ広げていないかを確認する。
指定の形式ではなく、実際に伝わるコンパイル条件とリンク条件を調べる。

生成処理では、入力と出力がビルドの依存関係に表れているかを確認する。
入力を変更しても再生成されない、並列ビルドで生成前のファイルを使う、前回の出力がある場合だけ成功するといった経路を調べる。
副生成物も、後続の処理が利用するなら生成順と更新を追う。

ライブラリーを配布する場合は、利用側から公開ヘッダーとリンク対象を使えるかを確かめる。
開発用の探索パスや、たまたま先に読み込まれたヘッダーへ依存していないかを見る。
検査した構成と未確認の構成を分け、別の構成の成功をそのまま保証にしない。
