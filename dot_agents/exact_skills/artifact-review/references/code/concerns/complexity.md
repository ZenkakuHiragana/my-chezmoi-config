# 複雑さ

処理を理解し変更するために追う条件や状態が、対象の仕事に対して過剰でないかを確認する。
関数の長さや分割数ではなく、その表現によって何を余計に覚え、組み立て直す必要があるかを調べる。

## 処理の流れと状態

主要な処理を入口から読み、結果を決める条件と状態の更新を追う。
一つの関数に異なる仕事が混ざる場合は、それぞれの前提を同時に覚えなければならない箇所を確かめる。
長くても一つの処理を自然に追える場合と、短くても離れた状態に依存する場合を区別する。

分岐が増えている箇所では、対象が本当にそれだけの場合分けを持つかを調べる。
複数のフラグを組み合わせて一つの状態を表し、各所で有効な組み合わせを判定し直しているなら、その状態の表現が複雑さを生んでいないかを確認する。

汎用の振り分けや設定駆動の処理では、実際に何が実行されるかをたどる。
単純な操作を表すために、多数の登録先や解釈規則を読まなければならない構造を調べる。

## 分割と共通化

関数や部品を分けた箇所では、名前と契約から役割が分かり、呼び出し側が内部を展開し直さず使えるかを確認する。
細分化しただけで条件や一時状態が複数の場所へ散っている場合は、読者が何を行き来して復元するかを示す。

共通化では、同じ規則をまとめているのか、独立した規則がたまたま似ているのかを確かめる。
用途ごとの例外を共通処理へ足し続ける場合は、一方の理解や変更のために他方の条件まで追う必要がないかを見る。
反対に、同じ規則の複写によって、同じ内容を何度も照合する負担も確認する。

性能や外部仕様のために複雑な処理が必要な場合は、その理由と表現を照合する。
必要な複雑さまで削るのではなく、制約を保ったまま理解できる区切りや説明があるかを調べる。

指摘には、理解を妨げる依存や条件の具体例を示す。
既に読みにくさや変更の結合があるなら、障害の発生を待たず設計上の問題として扱う。
好みの設計パターンと違うことだけでは問題にしない。
