# 最小性と意図性

対象の目的に必要な処理が揃い、用途のない機能や保守負担を持ち込んでいないかを確認する。
変更のレビューでは、依頼された仕事を成立させる範囲で差分がまとまっているかを調べる。

## 目的と実装の対応

実装が提供する挙動を利用側へたどり、何の目的や契約に必要かを確認する。
呼ばれない処理や使われない設定がある場合は、起動や生成、外部からの利用も調べてから、その必要性を判断する。

依頼された変更では、直接編集した箇所だけでなく、利用側や説明への必要な反映も確認する。
差分を小さくするために必要な追従を省いたり、その場限りの条件分岐で問題を隠したりしていないかを調べる。

無関係な整形や改名、依存の更新が混ざる場合は、今回の結果との関係を確かめる。
削除する内容についても、不要になる処理と、引き続き利用される契約を区別する。
行数が少なくても、責務や保存方式を無断で変える変更は小さいと扱わない。

## 仕組みを増やした理由

機能を切り替える設定や代替経路には、それぞれを必要とする利用場面があるかを確認する。
実現方法を決めずに複数の経路を残したため、利用者が選び分けを負担する構造になっていないかを調べる。

互換処理は、実際に守る必要のある利用者やデータとの関係から判断する。
将来の不明な用途を理由に追加した抽象化では、現在の処理を理解し変更する負担が増えていないかを見る。
現在のコードを安全に変更するための設計やテストは、未要求の将来機能と区別する。

エラーを避けるための追加処理では、原因を解消しているか、成功に見せているだけかを確かめる。
通常とは異なる動作を増やす場合は、その条件と維持する責任が対象の用途に見合うかを調べる。

## 必要な品質を削らない

短さだけを求めて、必要な検査や説明、責務の分離を不要としない。
反対に、品質を理由に、使われない仕組みや更新を続けるだけの文書を追加させない。

指摘には、満たされていない目的か、用途に結び付かない処理とその負担を示す。
依頼された結果と必要な品質を満たす方法が複数ある場合は、レビュー担当者の好みで作り直させない。
