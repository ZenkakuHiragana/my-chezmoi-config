# 責務境界

対象のルールや状態を扱う仕事が適切な部品にまとまり、内部の変更が無関係な部品へ広がらないかを確認する。

## 判断と状態を管理する部品

各部品が何を知り、何を決め、外へ何を約束するかを、実装と利用側から確認する。
ディレクトリや層の名前だけで責務を推測しない。
対象分野のルールと、保存や表示の都合で行う変換を区別し、それぞれを変えたときにどこへ影響するかを調べる。

複数の処理が同じ内部形式や計算方法を知っている場合は、その判断を変更するときに、すべてを同時に直す必要があるかを確かめる。
処理の順序に沿って分割していても、内部の判断が分離されているとは限らない。

反対に、独立に変わるルールを一つの部品へ集めた場合も確認する。
一方の要求を変えるために他方の条件分岐やテストまで直す構造になっていないかを調べる。
処理が似ていることと、同じ責務であることを区別する。

状態を管理する部品では、値を正しく保つための判断と更新を引き受けているかを確認する。
外から内部状態を直接変更できるために、各呼び出し側が同じ条件を守らなければならない構造を調べる。
派生値を別に保持する場合も、元の値との対応を誰が保つかを確かめる。

## 利用側へ見せる契約

呼び出し側が、公開された契約だけで正しく使えるかを確認する。
内部の保存形式や処理順を知らなければ呼び出せない場合は、何が外へ漏れているかを調べる。
一方、利用に必要な副作用や寿命の条件まで隠していないかも確かめる。

既存の拡張点や抽象化がある場合は、そこを通して必要な挙動を実現しているかを読む。
迂回する経路が、複数の場所に同じルールを持たせたり、依存方向を変えたりしていないかを調べる。
特定の層構成や設計パターンへの一致は要求しない。

テストの準備に内部状態の直接操作や多数の差し替えが必要な場合は、その部品の仕事を外から使える形で表せているかを確かめる。
エラーを返す境界も読み、回復できる側へ必要な判断材料が届くかを確認する。

指摘では、どの判断や状態の扱いが部品をまたぎ、そのためにどの利用や変更が不必要に結び付いているかを示す。
責務を決める根拠が不足する場合は、その不足と判断できない点を返す。
