# 依存関係

外部の部品やサービスに任せる仕事が明確で、その利用によって生じる制約を対象の運用と保守で扱えるかを確認する。

## 依存が担う仕事

依存先を使う箇所から、必要な機能と得られる保証を確認する。
既存の部品や標準機能で同じ仕事が実現されていないかを調べ、利用によって減る実装と増える導入負担を比べる。
依存の数や大きさだけで採否を決めない。

どの段階でその依存が必要かを確かめる。
開発時にだけ使う道具を利用者にも要求していないか、任意の機能を使わなくても大きな実行環境が必要になっていないかを調べる。
対応環境や配布条件は、依存先が支える範囲と照合する。

独自実装で外部依存を避けている場合も、置き換えた機能を保守できるかを見る。
既存実装の再発明によって、仕様対応や不具合修正を新たに抱えていないかを確認する。

## 取得されるものと更新時の影響

依存の宣言から、実際に取得される版と追加の依存をたどる。
ビルド時と実行時で異なるものを使ったり、取得するたびに意図せず内容が変わったりしないかを調べる。
固定や整合性確認の方法は、配布方式と再現性の要求に照らす。

取得元の信頼性と、利用する版の保守状況を確認する。
脆弱性の情報は、影響する版と成立条件を対象の使い方へ対応付ける。
警告が出たことだけで侵害を断定せず、確認していない呼び出し経路を「使っていない」とも判断しない。

ライセンスや配布上の義務は、対象の利用形態に関係する条件を確認する。
条件を確定できなければ、その不足を報告し、推測した許可で問題なしとしない。

依存先の更新に必要な修正箇所をたどり、内部形式や非公開の挙動への依存が無関係な部品へ広がっていないかを調べる。
包み直す層があっても、同じ内部知識が漏れていれば分離できているとは扱わない。
層を追加すること自体ではなく、どの変更の影響を抑えられるかを判断する。
