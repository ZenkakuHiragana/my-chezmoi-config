# 互換性と移行

既存の利用者や保存済みデータが、約束された条件で使い続けられるかを確認する。
移行を伴う場合は、変更後へ移す過程と失敗後の状態も調べる。

## 何との互換性が必要か

公開された利用方法と対応環境を確認し、どの利用者やデータがその契約に依存するかを調べる。
対象は API だけでなく、他のプログラムが読む出力や設定、文書化された操作方法にも及ぶ。

変更のレビューでは、保つと決まった契約と、変更が認められた契約を分ける。
利用者がいない内部実装や、同時に更新できる部品に、根拠なく旧版対応を要求しない。
変更後も古い利用者が残る場合は、その条件で必要な互換性を調べる。

呼び出しや読み込みが成功しても、結果の意味が変われば利用側は壊れ得る。
既定値や失敗時の結果を比較し、同じ入力を同じ意味で扱えるかを確認する。
新しい項目や値の追加でも、古い利用側の解析や分岐が受け入れられるかを確かめる。

## データと実行環境の移行

移行処理は、以前のデータが持つ意味を変更後の表現へ保てるかを確認する。
途中で止まった場合には、移行済みと未移行を区別でき、再実行によって重複や欠落が生じないかを調べる。
壊れたデータや対象外の版を、正常に移行したものとして扱わないかも見る。

旧版と新版が混在する期間がある場合は、双方の読み書きと配備順を照合する。
片方が書いた値をもう片方が壊す場合や、先に必要な準備が済んでいない期間を作る場合を調べる。

大きなデータを変更する場合は、所要時間とロックが通常の利用へ与える影響を確認する。
復旧方針が元へ戻すことなら、コードだけでなく保存済みデータも戻せるかを確かめる。
戻せない操作では、残った状態からの復旧方法が成立するかを調べる。

必要な利用者の作業と制限が、移行手順や配布物の説明に反映されているかを確認する。
版番号の更新だけで互換性を保ったとはせず、影響する利用方法とデータを根拠に判断する。
