# 観測性と運用性

利用者や運用者が、処理の結果と現在の状態を把握し、問題が起きたときに必要な対処へ進めるかを確認する。

## 結果と原因が分かるか

通常の利用方法で、成功と失敗、受付と完了を区別できるかを確認する。
作業を受け付けただけなのに完了と表示したり、一部の失敗を全体の成功に混ぜたりしていないかを調べる。

エラーを受け取った人が、失敗した操作と対象を特定できるかを確かめる。
原因に応じて対処を変える必要がある箇所では、その違いを出力から読み取れるかを見る。
内部の値を大量に表示することと、原因を調べるための情報があることを混同しない。

処理が複数の部品にまたがる場合は、関連する記録を結び付け、一つの操作を追えるかを確認する。
再試行や部分成功の記録によって、同じ作業を別の作業と取り違えないかも調べる。

ログや指標は、それを読む人が必要とする判断に使えるかを確かめる。
利用者が経験する失敗や遅延と、内部の状態を対応付けられるかを見る。
記録量の増大や秘密情報の混入が、診断や安全な運用を妨げていないかも確認する。

## 起動から復旧まで

起動時には、必要な設定や依存先を使えるかが、処理を開始する条件に反映されるかを確認する。
終了時には、新しい受付と実行中の仕事をどう扱うかを調べ、終了したと報告した後に未管理の処理が残らないかを確かめる。

状態を変更する管理操作は、途中で止まった場合にも残った状態を識別できるかを確認する。
復旧や切り戻しが必要な場合は、実際の状態と利用できる権限で手順を実行できるかを調べる。
コードだけを戻しても、保存したデータや外部への作用まで戻るとは判断しない。

警報がある場合は、誰が何に対処するための通知かを確かめる。
対処不要な通知に重要な異常が埋もれたり、利用への影響を判断できない情報だけで対応を求めたりしていないかを調べる。

必要な出力や手順の不足は、できなくなる判断や対処と結び付けて示す。
既存の道具で目的を果たせる場合に、指標や監視画面、運用文書を形式的に追加させない。
