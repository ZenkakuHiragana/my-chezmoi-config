# 並行処理と非同期

複数の処理が互いの進行に影響しても、状態が正しく保たれ、必要な処理が完了できるかを確認する。

## 実行順による違い

同じ状態を読み書きする処理を調べ、どの順序で実行され得るかを確かめる。
スレッド間の並行実行に加え、待機中に別の処理が進む場合や、コールバックから同じ処理へ入り直す場合も扱う。

確認と更新が別の操作なら、その間に前提が変わらないかを調べる。
個々の読み書きが安全でも、組み合わせた操作が不可分とは限らない。
ロックやトランザクションを適用した後の順序をたどり、何が失われたり重複したりするかを確認する。

新しい値を公開する箇所では、必要な初期化が済み、他の処理から整合した状態を読めるかを確かめる。
更新中の値を読む側も含めて、実行環境が保証する可視性と同期を確認する。

## 待機と終了

処理が何かを待つ箇所では、待たれる側が進むために必要な資源を調べる。
互いが保持するロックを待つ構造や、処理を進める実行枠を待機側が使い切る構造がないかを確認する。
ロックを保持して外部の処理を呼ぶ場合は、その処理による再入や追加のロック取得もたどる。

同期入出力は、どのスレッドや実行枠で完了を待つかを確認する。
イベントループや共有の実行枠を占有し、他の処理が必要な応答や期限を守れなくなるかを、実際の呼び出し経路と入出力先に照らして調べる。

開始した非同期処理は、誰が完了を確認し、失敗を受け取るかを確かめる。
呼び出し元が終了した後も続ける処理では、継続の目的と資源を管理する主体があるかを見る。

タイムアウトやキャンセル要求を、停止の完了と混同しない。
遅れて届いた結果や後始末が、次の実行の状態を上書きしないかを調べる。
終了時に待つ処理と中断する処理の扱いも確認する。

## 受け付ける仕事の量

入力が処理能力を上回る場合は、待機中の仕事と同時実行がどこまで増えるかを調べる。
受付を制限する仕組みがある場合は、制限に達したときに仕事を失ったり、送り手を待たせ続けたりしないかを確認する。

再試行は、各層の回数だけでなく全体で発生する呼び出し数を確かめる。
複数の層での再試行が負荷を掛け合わせたり、一斉の再試行が復旧を妨げたりする条件を調べる。
待機と再試行を含む総時間が、利用側の期限に収まるかも確認する。

問題の指摘には、問題が起きる実行順や待機条件を示す。
テストを根拠にする場合も、その順序を実際に作っているかを確認し、一度成功したことだけで安全とはしない。
