# 性能

対象の使われ方に対して、必要な速さと処理量を得られ、資源を無駄に消費していないかを確認する。
一回の処理の費用だけでなく、入力の量と呼び出す頻度によって積み上がる費用を調べる。

## 費用が増える仕組み

結果を得るまでの処理をたどり、計算している時間と、外部の処理を待つ時間を区別する。
繰り返しの中から別の集合を毎回検索している場合は、双方の件数が増えたときに仕事がどう増えるかを確かめる。
外部への呼び出しでも、一回の応答時間だけでなく、同じ要求で何回待つかを見る。

同じ値の変換や解析を繰り返す箇所では、入力が変わっていないのに同じ結果を作り直していないかを調べる。
コピーや一時的な集合の作成では、その独立した値や全件の保持が本当に必要かを確認する。
寿命や変更の分離を保つためのコピーと、使われない中間結果を区別する。

データ量が増える処理では、保持するメモリや保存領域にも着目する。
逐次処理できる入力をすべて展開したり、保持量に制限のないキャッシュへ保存し続けたりしていないかを調べる。
キャッシュには、再利用の利益だけでなく、更新や無効化の費用も含める。

## 実際の負荷と照合する

想定する入力の量と分布を、利用側や既存の運用資料から確認する。
高頻度で実行する小さな処理と、まれに実行する大きな処理を、同じ優先度で扱わない。
規模を確認できない部分に任意の数値を置いて、性能問題を立証したことにしない。

並列化している場合は、処理を増やすことで速くなる範囲と、共有資源を奪い合う範囲を調べる。
待機列や再試行が増えることで、完了までの時間がさらに延びる状態にならないかを確かめる。

測定を根拠にする場合は、対象の版と実行条件、測定した処理を確認する。
平均値が一部の遅い応答を隠していないか、局所的な高速化が全体の所要時間にも反映されるかを調べる。
計算量から分かる増え方と、実測した時間や使用量は区別する。

指摘では、どの処理が何に応じて増え、利用にどう影響するかを示す。
無駄な処理が確認できた場合も、根拠のないキャッシュや低水準の実装を解決策として押し付けない。
