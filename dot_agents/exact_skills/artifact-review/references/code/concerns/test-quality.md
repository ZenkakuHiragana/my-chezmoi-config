# テスト品質

テストが対象の挙動を正しく判定し、失敗したときに原因を調べられるかを確認する。
テストコードも保守対象として扱う。

## 期待結果と判定方法

テストの入力と期待結果を、対象の契約に照らす。
どの不具合があれば失敗する検査なのかを読み取り、処理を呼び出しただけで結果を確認していない箇所を調べる。
実装と同じ計算で期待値を作る場合は、双方が同じ誤りを持っても通らないかを確かめる。

確認する値や作用が、利用者や呼び出し元に約束する結果へ対応しているかを見る。
内部の呼び出し回数や順序を固定する場合は、その関係自体が契約なのかを確認する。
動作を保った内部変更でも壊れるテストと、必要な順序を守るテストを区別する。

## 代替部品と入力データ

依存先をモックやフェイクへ置き換えている場合は、今回確認する挙動に必要な性質を再現しているかを調べる。
都合のよい値を返すだけで、実物との受け渡しの問題を隠していないかを見る。
反対に、検査に無関係な内部動作まで同じにすることは要求しない。

入力データと準備処理から、何の条件を作ったテストかを読み取れるかを確認する。
大きなデータの塊に重要な違いを埋めたり、共通化した補助処理を何度も展開しなければ条件が分からなかったりしないかを調べる。

テスト名と失敗時の表示が、確認する挙動を説明しているかを確かめる。
失敗したときに、期待と異なる値や条件を特定できるかを見る。

## 再現性と失敗の扱い

時刻や乱数、外部の応答で結果が変わる場合は、必要な条件を制御できるかを確認する。
実行順や他のテストが残した状態に依存していないかも調べる。
並行処理で状態の成立を待つテストでは、一定時間待つだけでなく狙う状態が成立してから判定しているかを確かめる。

テストの無効化や例外の握りつぶしが、不合格を隠していないかを調べる。
スナップショットや期待値の更新は、実装の出力へ合わせただけでなく、契約に基づく変更かを確認する。

指摘には、見逃す不具合や誤って失敗する条件を示す。
テストがあることや件数の多さを、判定が正しいことの代わりにしない。
