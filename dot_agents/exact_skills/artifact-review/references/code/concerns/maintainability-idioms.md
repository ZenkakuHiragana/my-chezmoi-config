# 保守性と慣用表現

保守者がコードの意味を正しく読み取り、変更の影響を把握できるかを確認する。
言語や既存の仕組みが検出できる誤りを、人が注意して防ぐだけの構造へ置き換えていないかを調べる。

## 値と状態の表現

値を作る箇所と使う箇所を読み、どの値が有効で、どの組み合わせが成立するかを確認する。
異なる意味の値を同じ形で扱うことで取り違えやすくなったり、各利用側で同じ制約を判定し直したりしていないかを調べる。

扱う種類が決まっている場合は、種類の追加や改名を検出できる表現かを確かめる。
例えば、型名を文字列で比較して処理を選ぶ実装では、名前を変えたときに分岐の修正漏れを検出できるかを調べる。
実行時に拡張する必要がある集合には、その性質を確認せず固定した列挙型を要求しない。

型検査の迂回や警告の抑制がある箇所では、なぜ必要かを確認し、失われる保証をどこで保つかを調べる。
エラーを明確にする既存の型や処理を使わず、同じ意味を独自の値へ変えていないかも確かめる。

## 名前と既存の書き方

名前が、利用する場所で必要な役割を伝えているかを確認する。
狭い範囲では周囲から分かることを、広く使う名前では契約を識別するために必要なことを考慮する。
長い名前や略語のない名前を一律に良いとは扱わない。

同じ概念には一貫した呼び方を使い、異なる概念を混同していないかを調べる。
実装方法だけを示す名前のために、対象分野での意味を読み取れなくなっている場合は、その利用箇所を示す。

周辺の実装と基盤の機能を読み、同じ仕事を担う処理が既にあるかを確認する。
独自の方法を採ったために、挙動やエラーの扱いが周囲と食い違っていないかを調べる。
規約は適用範囲内で使い、規約のない部分を好みの構文へ書き換えさせない。

## 同じ知識を別々に直す負担

同じ意味の規則や値が複数箇所にある場合は、その意味を変えるときに何を更新するかをたどる。
各箇所を独立に手作業で揃える必要があるなら、更新漏れを招く関係が現在の構造にないかを確認する。
同期漏れのテストがあるだけで、その保守負担まで解消されたとは扱わない。

数値や処理が似ていても、独立に変わる意味を持つ場合は別の知識として扱う。
指摘では、同じ変更に追従する必要がある根拠と、現在どこへ知識が分散しているかを示す。
