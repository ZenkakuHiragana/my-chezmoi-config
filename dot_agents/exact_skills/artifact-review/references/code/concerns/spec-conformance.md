# 仕様照合

対象に適用される仕様を調べ、実装がその要求と制限に合っているかを確認する。
仕様書がある場合だけでなく、利用する API やデータ形式に定められた条件も扱う。

## 何を基準に判断するか

レビュー依頼と対象の資料から、期待される動作を確認する。
変更のレビューでは、変えるよう求められた内容と、引き続き守る内容を区別する。
置き換える予定の古い説明だけを根拠に、依頼された変更を仕様違反としない。

外部の API や実行環境を利用している箇所は、実際に使用する版と機能を確かめ、その定義元の資料を読む。
資料が指定されていなければ、対象の依存設定や参照先から定義元を探す。
検索結果の要約や似た名前の API で判断せず、該当する本文と適用条件を確認する。

仕様書がない箇所は、型の定義、利用側の処理、テスト、説明を照合し、何が約束されているかを確かめる。
現在の実装がそう動くことと、そう動くべきであることは区別する。
資料同士が食い違い、どれを採用するか決まっていなければ、その点を未確認として残す。

## 定義と使い方を照合する

まず、意味が実装の外で定まる使い方を確認する。
API の呼び出しなら、定義された引数と戻り値を実際の受け渡しへ対応付ける。
設定やデータ形式なら、値の意味と割当が定義に合うかを確かめる。
名前や値が存在するだけでなく、その用途に使ってよいかを調べる。

呼び出しの前後で満たす条件も照合する。
例えば、初期化後にだけ呼べる処理なら、実際の呼び出し順を確認する。
値を変更する操作なら、変更してよい対象と、その変更が見える範囲を利用側までたどる。

仕様から実装を読むときは、必要な動作が抜けていないかを確認する。
実装から仕様を読むときは、余計な動作や制約を加えていないかを確かめる。
仕様が複数の実現方法を認めている部分を、レビュー担当者の好みで一つに固定しない。

関連するテストや文書、生成物も、同じ契約を表しているかを確認する。
構文検査やテストが通っていても、未確認の外部仕様まで満たしたとは扱わない。

## 根拠と未確認事項

仕様違反を指摘するときは、適用する記述を引用し、資料の場所と対象の版を示す。
その記述に対して、実装のどの使い方が食い違うかを説明する。

取得できない資料や解消できない食い違いがあれば、そのために判断できない箇所を返す。
他の確認可能な箇所の検査は続ける。
検索で見つからなかったことを仕様上の不在とせず、推測した仕様で合否を決めない。
