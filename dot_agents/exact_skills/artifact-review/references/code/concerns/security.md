# セキュリティとプライバシー

権限のない操作や信頼できない入力によって、保護すべき情報と機能が侵害されないかを確認する。

## 保護する対象と入力

対象の利用方法と配備環境から、誰がどの操作を行え、何を見てよいかを確認する。
その上で、外部の利用者が制御できる値を入力から実際の処理までたどる。
通常の画面を通らない呼び出しや、保存した値を後で使う経路も含める。

本人を確認する処理と、その対象への操作を許可する処理を区別する。
ログインできたことだけで他の利用者のデータへアクセスできたり、対象の識別子を変更するだけで認可を迂回できたりしないかを調べる。

防御がどの境界で行われるかを確認する。
対象の関数内に検査がない場合も、呼び出し側や基盤が保証する条件を適用する。
反対に、通常の呼び出し順でだけ成り立つ検査を、別の入口からも必ず通るとは扱わない。

## 入力の使われ方

入力をコマンド、クエリ、表示内容へ組み込む処理では、入力をデータとして扱う仕組みが組み込み先に適しているかを確認する。
汎用の文字列置換を行っただけで、どの用途にも安全と判断しない。

ログへ外部入力を含める場合は、記録形式と閲覧・集計側の解釈まで確認する。
入力中の改行や区切り文字などが別の記録や項目として扱われ、発生していない出来事や異なる主体の操作に見えないかを調べる。

ファイルや通信先を指定する値は、検証した対象と実際に操作する対象が一致するかを調べる。
パスの解決やリダイレクト、確認後の状態変化によって、許可した範囲の外へ到達しないかを確かめる。

入力の大きさや処理回数を利用者が増やせる場合は、消費する資源をたどり、他の利用を妨げるまで処理させられないかを確認する。
制限がある場合は、その制限を実際に消費が増える前に適用できるかを見る。

## 秘密と失敗時の保護

秘密情報が必要になる箇所と、その情報を保存または送信する箇所を確認する。
ログ、エラー、例示用データから、本来見せない相手へ内容が漏れないかを調べる。

暗号や認証を使う処理では、用途に合う方式を保守された実装で使っているかを確認する。
方式の名称だけで判断せず、鍵や乱数の扱い、相手を検証する条件まで調べる。

設定が欠けた場合や外部の検証に失敗した場合も、必要な保護を保てるかを確認する。
エラーを無視したり別経路へ切り替えたりすることで、検査を通らず操作できないかを見る。

指摘では、制御可能な入力がどの防御を越え、何を侵害するかを示す。
実行する検証は与えられた権限内に限り、侵害や情報送信を実際に起こさなければ説明できないとは考えない。
