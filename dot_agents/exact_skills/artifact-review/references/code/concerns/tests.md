# テスト網羅

対象が守るべき挙動について、不具合を検出する検査が揃っているかを確認する。
変更のレビューでは、変更によって影響を受ける既存の挙動も対象にする。

## 契約から検査をたどる

利用側が必要とする結果と、結果が変わる条件を実装と仕様から確認する。
それぞれを検査する既存テストを読み、実行しているだけでなく、必要な結果を判定しているかを確かめる。

条件の境目や入力の組み合わせは、実装が取り違え得る違いから選ぶ。
例えば複数条件で実行を許可する処理では、個々の条件を別々に満たすだけのテストで足りるかを調べる。
状態を引き継ぐ処理なら、操作の順序や繰り返しによって結果が変わる箇所を確認する。

失敗時にも守るべき条件を、成功時と分けて調べる。
後始末や部分失敗の扱いが、成功する入力だけのテストでは未確認になっていないかを見る。
不具合修正では、元の不具合が戻ったときに失敗する検査があるかを確かめる。

## 検査する範囲のつながり

部品ごとのテストでは確認できない受け渡しを調べる。
双方が別々の前提で成功している場合や、代替部品によって実際の不一致が隠れる場合は、どの契約が検査されていないかを特定する。

重要な利用方法について、入口から必要な結果へ至るつながりを何で確認できるかを調べる。
生成されたコードや実行時の登録に依存する処理も、実際に使われる形で参照を解決できるかを見る。
すべてを大規模な総合テストで確認させるのではなく、必要な境界を確かめられる検査があるかを判断する。

型検査や静的解析が保証する範囲も確認する。
同じ性質を重ねて検査するためだけのテストを要求せず、それらが捉えられない動作の違いを調べる。
性能や実行順が問題になる場合は、その性質を判定できる条件で検査しているかを見る。

## 検査の不足を判断する

網羅率は未実行の箇所を探す手掛かりに使う。
すべての行を通っていても、期待結果や条件が不足していれば、契約の検査が揃ったとは扱わない。

プロジェクトで必須とする検査と、対象の失敗時の影響を照合する。
実機など必要な環境を使えない場合は、代用できた性質と未確認の性質を分ける。
不足を指摘するときは、守られていない挙動と、既存の検査ではなぜ見逃すかを示す。
件数の目標や無関係な境界例を新たな条件にしない。
