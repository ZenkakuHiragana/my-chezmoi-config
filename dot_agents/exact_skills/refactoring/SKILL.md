# リファクタリング

既存挙動を変えずに、構造、名前、責務境界、重複、読みやすさを改善する。

## 評価軸

- 挙動の維持
- 公開 API / 契約の安定性
- 凝集度と結合度
- 責務の明確さ
- 名前の正確さ
- 重複削減
- 複雑さと読みやすさ
- 依存方向
- テストしやすさと変更範囲の小ささ
- 古い経路、重複経路、未使用経路の削除

## 品質ゲート

- 意図された挙動は変えない。挙動の変更なしでは目的を達成できないと判明した場合は、その変更を別作業として分けて返答で説明する。
- 意味のある差分は名前変更、移動、抽出、不要削除、ロジック維持、意図的な挙動変更のどれかに分類できるようにする。
- 補助関数、API、慣用表現、抽象化を置き換える前に、意味が同じだと分かる根拠を確認する。
- 公開インターフェイス、スキーマ、設定、入口の整合を保つ。
- 網羅率が弱い場合は特性把握テストまたは変更前後確認を置く。
- 古い参照を残さない。
- 対象テストと静的検査を実行し、各結果を記録する。実行できない場合は、未実施の確認と理由を記録して完了扱いにしない。

## 手順

1. 現在の構造、呼び出し経路、不変条件を整理する。
2. 変更前と変更後の名前、API、経路の意味の対応表を作る。
3. まとまった最小のリファクタリングを選ぶ。
4. 削除、統合、抽出を優先する。
5. 短さだけを理由に意味が違う補助関数 / API へ置換しない。
6. 変更した名前、意味、経路を参照しているコード、テスト、文書、プロンプト本文を同時更新する。
7. 変更した面を再読し、古い名前や説明なしの意味置換を探す。
8. 直接確認と変更前後の根拠で検証する。

## 失敗時の扱い

テスト、静的検査、変更前後確認のいずれかが失敗したときは完了扱いにしない。今回の変更だけを戻す。既存の変更との境界を分けて安全に戻せない場合は、戻す操作をせず停止し、残った変更、失敗した確認、再開条件を返答で示す。

## 返す内容

変更対象、保った挙動、変更前後の観測、実施した確認、未実施または失敗した確認と理由、残る制限を返答に含める。

## 完了条件

- 変更前後の挙動を観測できる確認を実行し、結果を返した。
- 必須の確認が失敗または未実施のまま完了扱いにしていない。
- 残る制限と、確認を再開する条件を返した。
