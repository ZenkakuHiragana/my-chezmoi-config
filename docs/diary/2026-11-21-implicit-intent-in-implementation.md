# 「余計なことをするな」は「言われたことだけやれ」ではない

pie-boy にセッションの切り替えを頼んだとき、モデルの応答中は切り替えられないようになっていた。そんな指定はしていない。でも、それは欲しい挙動だった。「余計なことをするな」と「それくらいは考えてくれ」は矛盾しない。難しいのは、どちらなのかを、実装する前に何を見て判断できるかだ。

## 旧版では何をモデル任せにしていたか

`brownfield-code-change` には既存の利用側を調べる手順があり、`software-design` には利用場面と期待結果を作って設計を比べる手順があった。応答中の切り替えを場面に選べば検討はできる。抜けていたのは、そもそもなぜ「応答中」に着目するのかだった。しかも設計に進む前に「依頼された結果と守るべき条件を確定できた」ことを求めていた。設計してみて初めて違いが見える場合に、順序が逆になっていた。

今回の仮説は、**依頼された変更を、結果を使う側までたどれば、字面だけでは見えない期待の一部を見つけられる**というものだ。セッション切り替えなら、まず切り替えるとどの状態が変わるか、その状態を進行中の処理も使うかを調べる。「返答が別の会話に入る経路はあるか」は実装で調べられる。「そうなると元の会話の続きを読めない」は、その差が利用者にとって問題になる理由だ。どちらか一方だけでは、ガードが必要だとは言えない。最初から返答先が固定されているなら、取り違えを防ぐためにガードが必要だという説明は外れる。逆に、安全に切り替えられても操作を禁止してほしいかは、コードからは決まらない。これは過去のガードの理由を後付けで断定する話ではない。

そこで、実装前に現在の入口で既にできることと足りないことを分け、変更する値を誰が作り、誰が何に使うかをたどるようにした。どの結果を保つかと、それをどう表現するかは別の判断だ。設計では、新しい入口・型・操作を設ける案を、既存の使い方に不足分だけ足す案と比べる。利用者の選択が要る箇所が残る場合は、どちらを選んでも成立する部分だけを独立に確認して実装へ渡す。この区別が本当に成立するかは設計者だけで決めず、確認者も調べる。

## 新しいモードは必要だったか

過去のガードを伏せて同じ答えが出るか試すことはしなかった。代わりに、既存の道具のコピーに二つの新しい変更を加えた。

一つ目は「バックアップを取り込む前に、今回選ばれる会話をタイトルで確認したい」。改修途中の手順で最初に出た設計案は、既存の出力を保つため、別に `--preview` を作るものだった。ここは一発で当たったわけではない。主担当が利用説明と出力を調べ直すと、取り込まずに同じ選択・変換を行う `--dry-run` は既にあった。足りないのは人間が読む行のタイトルで、機械が読む要約 JSON まで変える必要はなかった。この比較を設計手順に組み込み、試作では新しいモードを作らなかった。古いコピーと新しいコピーを渡すと、実際に選ばれた方だけが表示された。タイトルは変換後の文書からではなく選択した会話から取ったので、文書が 0 件でも読めた。

二つ目は「いま整形器をかけると、どのファイルが変わるか、書き換えずに知りたい」。こちらは既存の入口が実際に書き込む。試作では `--check` を加え、別のロジックで予想するのではなく、通常の整形と同じ計算をして最後の書き込みだけを省いた。整形前・整形済みの 2 ファイルを渡すと、変更予定は前者の 1 箇所。確認前後で両方の内容と更新時刻は同じで、コピーを通常整形すると予告した方だけが変わった。

## 実証したことと、していないこと

最初の結果報告では「スキルを変えた」「試作が動いた」を並べた。それでは「なぜ改善できたと言えるのか」には答えていない。実物で示せたのは、一例目では既存の入口で依頼を満たせたこと、二例目では入口を足しても整形の判定を二重に持たずに済んだことだ。試作品は元の道具には取り込んでいない。

運用する二つのスキルには、暗黙の期待を探す手掛かりと、もっともらしい説明が外れたときにそれを退ける手順が加わった。ただし、一例目では途中で主担当が判断し直しているし、二例目が旧版ではできなかったという根拠もない。**新しい手順が未知の依頼でも安定して良い実装を引き出す、という中心の仮説は未実証**のままだ。
