# AI に搭載する永続記憶に関するメモ

AI さんに過去のセッションでの対話で学んだことや決定事項を覚えて、次の判断に役立てて欲しい。
だが「記憶」という体で好き勝手に作文されてしまうとその時の作文で取り違えたり勘違いした内容がそのまま引き継がれてしまう。
既存の実装にある永続記憶を掲げるシステムはどこかでこれをやっていることが多く、
運用の重さから見ても記憶の品質から見ても使いにくいと感じている。

ここで欲しいものは、

- 検討内容を引き継げること: 何を目指したか、何を決めた/決めてないか。その理由は何だったか
- 経験を活かすこと: 何をどんな条件で試したら何が起きたか、過去の行動に対してユーザーがどう反応したか

ここでやりたいことは、

- セッションログを採掘して本文を検索可能なようにインデックスを作る。
  - 情報として必要なのはユーザーの発言とアシスタントの応答本文。
  - 拡張機能による指示の差し込みやツール実行出力そのものは分量の割に得られる情報が少ないとみなしている。
- 過去の会話の本文を検索して、誰がどんな発言をしたのかを振り返ることを可能にする。
  - エージェントが自発的にやるかどうかではなく、そのような手段を持つという話。
- エージェントの判断に利用できるように導線を張る。思い出すべき時と思い出し方を指示しなければ思い出されないので。
  - 拡張機能による指示の差し込みは最近のモデルだとプロンプトインジェクションを疑って従わない。最初から知っている状態でないとダメそう。

試したものは以下だ。

- Magic Context
  - いつ思い出すかが不安定で、忘却システムのために忘れられる。
  - 忘れること自体は悪いことではないが、あまり有効に作用している感じがしなかった。
  - 指示の差し込みによる悪影響が見られた。
- Hindsight
  - 運用が非常に重い。記憶の取り込みに LLM を、取り込んだ記憶の整理に LLM を、思い出すのに LLM を使う構成で、タイムアウトも厳しい。
  - Pi 統合ではセッション中の注入が重い割にはあまり積極的に思い出しに行こうとする姿勢が見られなかった。
  - 指示の差し込みが裏でかなりたくさん入るらしく、コンテキストの汚染が懸念となった。
- CASS (coding_agent_session_search): ツール実行の膨大な出力まですべて取り込む仕様であり、インデックスの肥大化が問題となった（11GB を実測）
  - Pi の生ログはツール出力込みで 3 億字を超えていた。ユーザー発言と返答本文だけにすると約 760 万字まで減った。
  - 取り込むときに custom_message の種類の区別を消していて、拡張機能の差し込みとユーザー発言を分けられなかった。
  - 埋め込みも試した。意味索引の初回作成（バックフィル）は候補が約 53 万件あり、時間がかかった。
  - 埋め込みの識別に接続先 URL まで含まれていて、推論先を替えると互換性が切れる作りだった。

欲しいものを全部載せた拡張機能やすぐ使えるものはどう調べても見つけられなかった。
そこで、セッションログを既存の検索基盤に取り込む部分と問い合わせ部分だけを自作することにした。
検討したものは以下だ。

- SQLite の FTS5 trigram などで自作: つらい。
  - trigram は3文字区切りのトークン化で、最初から使える。
  - lindera-sqlite を使えば日本語の形態素解析までやったインデックス化ができる。
  - 索引の差分更新や埋め込みモデルによる意味検索との結果の統合を自作する必要がある。
- PGroonga: 最初から形態素解析エンジン MeCab を使えるらしいが、PostgreSQL サーバーを建てる必要がある。よく検討してないけど、これも多分索引の保守は自作寄りでしょう。
- Elasticsearch, OpenSearch: この辺から検索用の基盤という感じになってくるが、こいつらは Java 製でサーバーが重いらしい。
- QMD: 日本語の語句分割が1文字ずつであり、インデックス品質に不安がある。
  - 埋め込みの接頭辞は embeddinggemma と Qwen3-Embedding の分しか用意されておらず、Ruri の `検索クエリ: `／`検索文書: ` を付けられない。
  - 総合検索（`qmd query`）は、検索語の言い換えと並べ替えにも小さなモデルを使うので CPU では重い。
- mgrep: ファイルを Mixedbread のクラウドへ送って検索する方式で、ログインも要る。

語句索引による検索の他に、どうしても意味の近いもので検索する仕組みも欲しい。
埋め込みモデルを使うことになるが、こっちもいろいろな事情があった。

- Magic Context などの埋め込みモデル対応の実装は既定が `Xenova/all-MiniLM-L6-v2` など日本語非対応のものも多く、選定時に注意が必要。
- 埋め込みモデルは訓練時に問いと答えを識別する接頭辞を付ける。同じ接頭辞を推論時にも付けないと性能が下がるとされている。
  - 質問文には `query: `、応答には `passage: ` と付けてから続く文章を入力する、ということを行う。
  - 日本語に強い Ruri-v3 では質問文には `検索クエリ: `、応答には `検索文書: ` を付ける。
  - モデルを変えられる検索基盤ではモデルと同時に接頭辞の指定が索引作成時と検索時の両方でできることが求められる。
- Qwen3-Embedding は多言語で高い性能を発揮するという記録がある。Cloudflare の無料枠でも使える。
- Ruri-v3 はさらに強い日本語性能を発揮するようだ。英語での性能は分からないが、日本語を主体とする会話をするので日本語性能だけ見れば良いだろう。
- 外部の埋め込み API（Cloudflare Workers AI の無料枠、OpenAI、Gemini）も比べたが、やっぱりリクエストの度に金がかかるのは気になる。
  - むしろもっと気になるのは、金がかかること以上にそのための支払い手段を登録しなきゃないということだったりする。

## 検索システム Meilisearch を使う

良さそうだと思ったのは Meilisearch だ。

- UniDic による日本語形態素解析に標準対応
- 索引の差分更新と保守をやってくれる
- 埋め込みモデルによる意味検索を組み合わせることができる
- Docker ですぐ建てて、REST API ですぐ使える
- 唯一気になるのは埋め込み設定の URL を変えると埋め込みをやり直すこと。モデルならともかく。

というわけでこういう計画となった。
詳細は containers/session-search/README.md にある。

- Docker で Meilisearch を常駐させる。
  - 事情が変わったら Windows バイナリを使う手もある。
- データ置き場を決める。~/.docker/meilisearch とか。適当に。
- データ置き場に config.toml を置く。
- Ollama で埋め込みモデルを建てる。
- 埋め込みモデルは Ruri v3 310m（Q8_0 の GGUF）にする。Modelfile を調整して入力量を最大化する。
- CPU で足りる。文書 153 件の埋め込みが約 8 分。検索時の埋め込みば 0.1 秒もかからない。
  - ちなみに文書の埋め込みは GPU だと10.5秒。
  - Ollama は `num_ctx 8192` だけだと約 2,048 トークンで入力を弾いた。`num_batch 8192` も要る。
- Meilisearch のハイブリッド検索はクエリの埋め込みが約 1.5 秒で間に合わないと文字検索だけの結果を返す。
  - Ollama の自動モデル解放処理との相性が悪いので `OLLAMA_KEEP_ALIVE=-1` にする。

## セッション検索システムを作る

- Piのセッションからユーザー発言1つ + そのターンのエージェント本文を1文書として埋め込む
  - 複数の応答をつなぐ
  - ツール出力、思考、ツール呼び出し、custom_message は含めない
  - 分割はしないで一息に埋め込む
- Meilisearch の `multimodal` テンプレートで頑張って問いには `検索クエリ: `、文書には `検索文書: ` を付けて Ruri v3 に送る
- 一括取り込みを Python で書く
- エージェント向け検索ツールをシェルスクリプトで書く
- Pi での会話に追従するための拡張機能を検討する
