# スキルを Python 風の構文で書く

## 調べた問題

11-15 に、確認者やレビューの指摘を受けて、頼まれていない仕組みを足す失敗が 3 件続いた（CASS、pi-session-index、pi-scratchpad の設計）。原因を調べる途中で、ユーザーはこう述べた。

> そろそろまたスキルの本文を読めなくなってきたから、自分が読んでも何が指示されていないのか分からなくなってきたんだよね。

brownfield-code-change は、11-08 の 78 行から 166 行に増えていた。AI が「もう書いてある」と言っても、本文が読めなければ確かめられない。ユーザーは、11-12 と 11-14 に話した Python 風の表記を試すことにした。

> 結局文章で論理構造を表現するのがつらいのよ。

11-12 の試作（`.opencode/work/python-prompt/artifact-review.md`）は、補助関数 `condition`、`constraint`、`execute` を置き、`with constraint(...)` で制約が効く範囲を表していた。

## 試したこと

1. 試作 1 では、brownfield-code-change 全体を書いた。節ごとの関数、変数、引数、f 文字列、コメント（`# 未定:`）を使った。1 回目の照合で、意味のずれが十数か所見つかった。`if` と `elif` で原文の条件を排他にした箇所、制約の範囲が狭まった箇所、`return` で後の工程まで止めた箇所などである。
2. ユーザーは試作 1 を読み、次の 4 点を挙げた。
   - メインの処理を最後に書くと、段階の流れがスキルの一番最後に出る。
   - `with constraint` の中に複雑な指示を書くと、どんな条件で何を守るかが構造から見えない。
   - 変数名も自然言語になるので、指示と識別子の対応を付けづらい。
   - コメントが指示になるかが分からない。コンテキストも増える。
3. 使う構文を絞った。`return` と `import` をやめ、`while` と `break` を入れ、`execute` を `do` に変えた。
4. 試作 2 では、「レビューして完了する」節だけを書いた。ユーザーは「結構分かるな」と言ったうえで、次の点を挙げた。
   - 全部 Python でいい。`def` が章のように働いている。
   - `do` と `constraint` のどちらに書くか迷う文がある。
   - 入れ子より `and` と `or` で書く方がよい。
   - トークン数を測ってほしい。
5. 試作 3 では、本文全体を 1 つのコードフェンスに入れ、`condition` を一つの判定ずつに分けて肯定形にした。照合は 9 回行った。

## 分かったこと

- Python の構文が意味を決めるのは、骨組みだけだった。試作 1 では、意味が骨組みの外へ漏れていた。漏れた先は、関数の並び順の慣習、文字列、変数名、コメントである。
- `with` が表すのは「ここからここまで」という範囲だけだった。試作 1 の `with constraint` に入れた 50 文を分けると、範囲の中で効き続ける制限は 21 文だった。残りは、きっかけ付きの規則が 8 文、判定の仕方が 21 文だった（分け方は AI の判断）。判定の仕方は、それが効く `condition` の文の中へ移した。
- `return` は、戻り先と、文中の「ユーザーへ返す」との違いが読めない。`import` はパスを書けず、2 回目以降は何もしない。`break` が抜けるのは一番内側のループだけである。どれも Python 3.15 で実行して確かめた。`do` は Python の予約語ではない。
- トークン数（o200k_base）は、「レビューして完了する」節の原文が 2,856、試作 2 の本体が 3,553、試作 3 の本体が 3,871 だった。字下げの空白は 200 前後で、空白は 4 個でも 16 個でも 1 トークンになる。試作 3 で増えたのは、ほとんどが文字列の中身である。照合で見つかった抜けを埋めた分にあたる。
- 判定を `if` に切り出すと、判定がどこにあり、何を基準にしているかが見える。基準の入っていない判定も見つかった。例えば「設計に無い入力を、この作業で扱う」には、扱うかどうかの決め方が無い。
- `condition` の中身は意味判断である。判定に失敗したとき、真と偽のどちらになるかは決まっていない。`not condition(...)` は、判定できないときに先へ進む側へ倒れうる。試作 3 で「要調査・判定不能が残る場合は完了としない」を `not (… or …)` で書いたところ、照合で、判定できないときに完了してよい側へ倒れると指摘された。
- 「確かめられなければ偽」を一律に決めても、安全にはならない。完了の判定では、偽は止まる側である。足さずに済む出口（変更前からある独立した欠陥として報告する、など）では、偽は出口を通れない側で、作業を足す側へ押す。
- 試作 3 の `condition` 35 個を、11-07 の日記の仮説（効かない指示がある）に当てはめた。
  - AI の予想では、作業を足す入口の判定は真に偏る。「約束の成立を妨げる欠陥である」「前提が崩れた箇所がある」「性質を回復できる」がこれにあたる。
  - 足さずに済む出口の判定は、偽に偏る。「今回の要求を妨げないことを確かめた」がこれにあたる。
  - 同じ基準で別のサブエージェントにも分類させた。どちらかが偏りを予想した 20 個のうち、向きが一致したのは 8 個だった。AI が AI の判断の偏りを予想しても、そろわない。
- 一番大きい判断は、`condition` ではなく `do` の中にあった。今回の扱いと直す範囲を決める判断と、指摘の成立を確かめる判断である。
- 11-11 の再判定は、この予想の一部をすでに実測していた。成立の確認では却下がほとんど出ず、扱いの決定では成立した指摘のほとんどが解消するになった。AI はこれを思い出さずに、測る案を出した。AI が出した「問いの形を変える」も、成立の確認については 11-11 の K1 と K2 で試して外れていた。
- 書き換えは間違えやすい。試作 3 の照合では、8 回目まで毎回違う指摘が出た。見つかったものには次のようなものがある。
  - 変更前からある独立した欠陥を、「そう扱おうとしたときだけ」確かめる形にしていた。これで、既存の欠陥を修正範囲に加える道が開いていた。
  - 「修正案を採れなかったことを、欠陥が解消したことにしない」が、完了の判定には効いていたが、修正へ進むかの判定には効いていなかった。

## ユーザーが決めたこと

- 構文は作り込みすぎない。

  > あくまでも自然言語として読んだ時に通じる範囲にしないといけないはず。

- `return` と `import` は使わない。`while` と `break` は使う。手順は `do` で書く。
- 本文全体を 1 つの ```python のコードフェンスに入れる。
- `condition` の中身は肯定形で書く。`and` と `or` を混ぜるときは括弧を付ける。
- いくつもの判断に効く基準は、効く範囲を `with constraint` で囲む。
- 書き方の決まりを prompt-work にまとめる。brownfield-code-change を、この形に置き換えてみる。

## 入れた変更

- prompt-work に `references/python-style.md`（Python 風の指示の書き方）を足し、「関連資料」に案内を書いた。
- brownfield-code-change の本文を、Python 風に置き換えた。意味は変えない方針で、照合を 4 回行った。最後の照合の結果は「なし」だった。行数は 166 行から 322 行、トークン数は 4,397 から 5,918（1.35 倍）になった。
- 原文から決まらなかった点は、本文で決めずに残した。
  - 設計に無い入力を「この作業で扱う」かどうか
  - どの条件にも当たらない指摘を、直すか報告だけにするか
  - 「設計の検討へ戻す」で戻した後、その指摘を今回は扱わないと決めてよいか
  - 設計を変える案でも、実装の誤りを正す案でもない場合の扱い
  - 実装中に「勝手に確定しない」で確定しなかった選択を、その後どう扱うか
- 書き換えで AI が選んだことは、覚え書きに残した。置き場所は `.opencode/work/python-prompt/brownfield-review-3-notes.md` と `.pi/work/python-style-skills/conversion-notes.md` である。例えば、依頼された結果を確定できないときは、実装だけでなく設計も止めてユーザーへ返す形にした。

## 決まっていないこと

- AI がこの形の指示に従うかは、まだ試していない。自然文の版と比べる試験もしていない。
- 判定が正しくなるわけではない。判定の基準は、文字列の中の自然文のまま残る。11-11 の「ユーザーの判定に合う判定を得る方法は、見つかっていない」は変わらない。
- `do` の中に残った大きな判断を、どう扱うか。
- 意味の照合も AI が行った。照合のたびに違う指摘が出ていたので、漏れが無いとは言えない。
- 指示のレビュー（artifact-review）が、この形の本文をどう読むかは確かめていない。
- ほかのスキルへ広げるかは、決めていない。
