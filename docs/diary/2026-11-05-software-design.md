# 良い実装を書いてくれよ、頼むから

review-orchestration, artifact-review, brownfield-code-change などのスキルを揃えて久しいが、
未だに AI と喧嘩ばかりしている。レビュワーが指摘して、親エージェントがその指摘の妥当性を判断し、
別の監査者が指摘の妥当性の判断の妥当性を判断するという猛烈なシステムを構築しているが、
最近の実態としては監査が新たな要求を作り出している事例が目立つ。
どうもこういうスキルを組む時は「普通に」考えると失敗するようなのだ。

例えば依頼した内容にない余計な変更を入れたとするだろ。
そういうのは困るからそうなってないか確認してと指示するわけだ。こんな感じに。

> 既存の要求との不一致を成立させる

この指示は成立しない。なぜか？成立させると言ったら **何が何でも** 成立させるからだ。
こじつけに繋がるおそれがあるということだ。そういう挙動を許すと「論理的に正しいが実態として正しくない」指摘がバンバン出てくる。例えば……

- TUI のあるレイアウトでターミナルの幅が横2マスの時に正しく表示されなくなる
- シェーダーの処理 A を改良して処理 B にした結果、元々表示される画素との差分を取ると最大で 1e-16 のズレがあるので要求にある「元の処理と同じ」を満たさない
- 入力欄に OSC52 等の制御文字をどうにかして突っ込むとそれをエスケープせずに処理してしまう

分かるんだけど、分かるんだけどさあ。違うじゃん。そうじゃないじゃん。
こういうのが出てくるとなまじ論理的には成立するものだから親エージェントは **必ず** そういった指摘を **最小の変更で** 修正するわけだ。
それを5回も10回も繰り返すうちに、見るも無惨なゴミが出来上がるのである。

だからそうならない仕組みが必要なんだよ。判断に任せるのではなく原理的にそうならざるを得ない設計が必要なんだ。
指摘に対応するんじゃなくて、そういう指摘が起こらない成果物の形を探ってほしいんだよ。

## 現状の分析

- artifact-review による指摘を200件くらい集計した結果、指摘が修正につながった件数 / 指摘の総数 = 90% 程度であった。
  - いくつか実際に指摘の内容を自分で眺めてみたが、割と妥当な指摘も多い。上に挙げたようなヤバいやつは体感2割くらいという印象。
  - 要件契約 + 実際の差分 + 固定した観点という組み合わせは、悪くはない。たぶん。
  - 観点の書き方にこれまで出てきたような「こじつけられる判断」「無効な指示」が含まれていないかは気になる。
    - でも現時点で本物の指摘が出ている以上、高優先度の問題はそこではない。
- 指摘の定式化: 条件 Q を満たすとき、受け手 R で違い E が発生し、それにより性質 P が満たされなくなる
  - 条件 Q とは何か、その命題は妥当か（≠ 論理的に成り立つか）
  - 受け手 R とは何か。依頼と作業対象に合致した存在であるか。
  - 違い E とは何か。
  - 性質 P とは何か。本来依頼が達成された時その性質が満たされているべきであるという主張を成り立たせる必要があるが、その根拠は何か。
  - 上記の判断を誰がやるか。親エージェントか、レビュワーか、その両方か。
- 親エージェントの対応は「鵜呑みにする」以外には想定しない方が良さそうだ。
  - 現時点で reviewer エージェントの応答には「鵜呑みにすんな」って書いてある。
  - review-orhcestration にも「鵜呑みにすんな」って書いてある。
  - それでも絶対に鵜呑みにして局所修正を繰り返してトークンを焼き尽くす。
- 現行の review-audit は新たな要求を作り出していることがある。
- 自分が改めて判断してみた20件では review-audit エージェントによる費用対効果はあまり高くないと見積もれる結果であった。
  - review-audit の言うことが正しい: 9件くらい
  - 親エージェントの言うことが正しい: 8件くらい
  - 判定不能: 残り

問題は、

- 問題点を正しく発見すること → artifact-review およびレビュワーがヤバい指摘を挙げてくる
- 問題点を誤解なく伝えること → 無理（後述）
- 問題点を正しく解消するための行動をさせること → 無理（後述）

このあたりにありそうだ。

## 問題点の伝え方の問題なのか

「これが問題である（から直せ）」という言い方ではなく、
「こういう性質を満たしていることが望ましい」という言い方にしてはどうか、と考えた。

> 親へ渡す「満たすべき条件」自体が、新しい設計判断を含んでいる可能性がある。

などと GPT に言われた。名前を変えて消えたことにはできないというわけだ。満たすべき条件とはすなわち解消すべき問題なのだ。

さて、それを検証すべく、こういう実験をやった。

1. たくさんあるセッションログから、実際の依頼を再現するのに必要な文脈とレビュワーの指摘をもってくる。
2. その指摘の表現を変えて、次にどうするかをサブエージェントに答えさせる。対照実験として元々の言い方のままで反応を調べる条件も置く。

結果は変わらなかった。元々の言い方でも望ましい状態を伝える書き方でも、
「その状態になるように局所修正する」という意図の答えが大半であった。

どうも「レビュワーがわざわざ特定の状況と再現条件を提示してきた」
という事実そのものが修正指示と捉えられるようで（それもそうか）、
言い方をちょっと変える程度ではやっぱりダメそうだった。

レビュー手続きの変更の中心を「レビュワーから親への情報の受け渡し」に絞るという部分を維持するのなら、
言い方をちょっとでなく変えないといけない。
問題を伝えないといけないのに、それを局所修正する方法を知られてしまったら局所修正に入ってしまうのだから難しい。

伝えないといけないのに伝えてはいけないんだ。
こうなったら「保守性・責務分離の観点で問題がある」などと artifact-review の観点名だけを伝えるくらいしかアイデアが出てこない。

## 指摘を伝えるとはどういうことなのか

ここで気づいたのは、

> 詳細な状況と再現条件を提示して修正を要求するとその状況を最小の変更で解消しようとする

という行動は、サブエージェントがそのように伝えた場合に結果的に問題になるというだけの話であって、
仮に全く同じ文言を人間が指示した場合は一転して

> 指示追従性能が高く、無用な変更をしない優秀な作業者

という評価になる。つまりこの挙動は **表裏一体** なのだ。

問題になるのは、 **(元の依頼の指示A + 修正指示B) を合成した結果を得るのが難しい** という一点に絞られるのではないか。
こう考えるとこれまでのサブエージェントによる指摘の通達が機能しにくいことや指摘の判断について AI 同士で喧嘩が始まる挙動も納得がいくように思える。

仮にこの説を前提に話を進めると、3つの方向性が考えられる。

1つ目は、指示を合成する方法を考えること。
「元の依頼Aを頼んだら、成果物に対して修正事項Bが発生した。これを上手に取り込んでより高品質な成果を要求する依頼 (A + B) をセッションの中で達成する方法とは」
みたいな疑問が浮かぶだろう。「指摘への対応ではなく、その指摘を生じさせない成果物を作る依頼を達成させる」という話の延長でもある。

> 実のところ指示の合成なんて大仰なものを考えるまでもなく、1つのセッションで4つくらいやってほしいことを伝えてみればそれを全部やってくれるというところから説明ができる。実際にそういうことを最近やったが、難しいことは特に起こらず4つの項目が無事に（レビューで紛糾したものの）実装された。
>
> これは指示 (A + B + C + D) である。別の例では1つの機能の実装が完全に終わってコミットまで積んでから、そのセッションでそのまま別の依頼を投げたことがあった。
> これは指摘という形になっていないだけでやっていることは指示A + 指示Bである。
>
> こうしてみると極めて挙動は一貫しているとみえる。**指示があったら、その通りになる。** 何度か言ってるが、まさにそれだ。

2つめは、局所修正を繰り返した結果高品質な成果物となるにはどんな指示をどんな順番で与えるべきかを考えること。
今まで見てきたひどい例のいくつかは、レビュー周回が10周以上にわたって続いたりした結果
目も当てられない例外分岐の束が出来上がるといったものだった。

3つめは、そもそもレビュワーがまともな指摘だけを飛ばすようになるにはどうするか。
2つめの類型ともいえるが、そもそも幅2マスのターミナルで「正しく」表示されることを要求するような指摘は本来出てはいけない。
幅2マスにした瞬間クラッシュしたりフリーズする、なら対応が必要だが正しく表示されないというのは普通は指摘には当たらない。
そういう「常識的な」判断を分解し、レビュワーを賢くすることで親エージェントが指摘を鵜呑みにして良い状態を作る方法だ。
過去にもなんかそんなことを考えたような気がしないでもないが……何だったかな。忘れた。

## 猛烈な指示

普通にやりたいことを伝えても、人間なら当然できるような判断であっても、絶対に成し遂げられない NG ワードというのがある。例えば、

- 必要なら: 必要であるかどうかを的確に判断できるなら AI は間違えることはない
- 解釈が変わるなら: 1文字でも違えば解釈を変えることができる。したがって常に成り立つ
- 根拠を示す: 何かしらの文言にこじつけるための作文が必ず成立するため、常に成り立つ
- 余計なものがあれば消す: いかなる ~~醜い~~ 実装であっても動作するならそれは必要な要素の集まりである。よって常に成り立たない
- 読みにくければ: コンテキストに載ればどんなデータでも容易く「読む」ことができるので、そこに人間のような読解負荷や抵抗は存在しない。よって常に成り立たない

こういう罠を完全に回避して、うっかり書いてしまいがちな実行不能な指示を書かないことを最近のスキル執筆の考え方としている。
そういう指示を操作可能な手順に無理やり変換して猛烈な勢いでスキルを書き殴ることになるので、そういう思想で書いた指示を「猛烈な指示」と呼んでいる。

これの要点は、

- 学術的・実務的知見に裏付けて何を基準とするかを決める
- それを実現するために必要な判断を操作可能な形に分解し、猛烈な勢いで書き殴る
- それによって本質的にできない判断を迂回する

mechanism-textbook では、情報の展開の仕方や章の構成について設計書を書き、その設計についてレビューを通すという流れがあった。
似た流れをソフトウェアの設計・実装に使えないか？と考えている。

というわけで実際のソフトウェア設計における実務的知見をこれでもかと調査してもらった。

## ソフトウェア設計の知見

以下 GPT-6 Pro の応答コピペ。

> [How to Design Programs](https://htdp.org/2020-8-1/Book/part_preface.html) の設計手順は、最初に情報をどうデータとして表すかを決め、具体例でその意味を確かめ、それから関数の入出力、目的、処理の骨格へ進む。処理の骨格をデータ定義から導くため、「何となく処理を分割してから名前を付ける」とは順序が逆になる。主に教育用の体系だが、中間表現を埋める作業ではなく、次の設計操作を導く材料として使う点が今回に合う。

> [DDD の原典](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf)にも、ドメインモデルと実装モデルを別々に作り、複雑な対応関係でつなぐことへの警告がある。モデルから用語と責務を取り出し、コードをその表現にする。一方で、実装しにくいモデルならモデル側も修正する。設計担当が実装の制約から離れてはいけない、とされている。

> [Parnas の古典的なモジュール分割論](https://www.cs.umd.edu/class/spring2003/cmsc838p/Design/criteria.pdf)では、モジュールをサブルーチンではなく責任の割り当てとして扱う。処理の流れをそのまま分割する案と、他から隠すべき設計判断を単位にする案を比較し、理解と変更の影響がどう変わるかを示している。

> [Ousterhout の講義](https://web.stanford.edu/~ouster/cgi-bin/cs190-spring16/lecture.php?topic=modularDesign)でも、インターフェイスは関数宣言だけではなく、利用側が知る必要のある副作用や振る舞いを含む。関数を細かく分けても、呼び出し側がほぼ同じ知識を持ち続けるなら、情報を隠せていない。

> [Beck と Cunningham の CRC](https://c2.com/doc/oopsla89/paper.html) は、名前・責務・協力相手を用いて、具体的な場面を動かしながら設計する方法だ。カードの記入自体より、ある仕事を誰が引き受け、足りない情報を誰に求めるかを、その場面に沿って確かめることが中心にある。

> [Bloch と Garrod の API 設計講義](https://www.cs.cmu.edu/~charlie/courses/17-214/2021-spring/slides/20210325-api-design-1-process-and-naming.pdf)では、短い API 案を作り、利用例へ当てはめ、実装前からその API を使うコードを書く。その後に試作実装を作り、そこで見つかった問題を設計へ戻す。最初から詳細な仕様を完成させるのではなく、使用を通じて具体化する手順である。

> ### レビュワーに、設計を使う仕事を割り当てる
>
> 最も直接的なのは、SEI の [ARID：Active Reviews for Intermediate Designs](https://sei.cmu.edu/documents/1962/2000_004_001_13685.pdf) だった。まだ完全な仕様書になっていない設計について、利用者となる開発者が、与えられたサービスを使うコードや擬似コードを作る。設計者の説明を聞いて賛否を述べるだけではなく、実際に利用できるかを試す。使用の検査中は、設計者が実装上の意図を説明して助けることも制限する。

> [Perspective-Based Reading](https://www.cs.umd.edu/projects/SoftEng/ESEG/manual/pbr_package/node21.html) にも近い区別がある。観点名を渡すだけのチェックリストと、設計者・試験者などの役割に応じた具体的な活動をさせる読解手順は別物として扱われている。

> [arc42](https://docs.arc42.org/section-5/) も、静的な構成と実行時の振る舞いを分け、詳細化では網羅性より設計上の関連性を優先している。全メソッドを文書化する方向とは違う。

> [Google での設計文書の実務紹介](https://www.industrialempathy.com/posts/design-docs-at-google/)も、完全な API 定義やデータ定義の複製ではなく、設計判断とトレードオフを記述し、試作へ参照する形を勧めている。

> [AWS の形式手法の事例](https://lamport.azurewebsites.net/tla/amazon-excerpt.html)は、実装の細部を省いたモデルで、レビューや通常の試験をすり抜けた設計上の誤りを見つけたものだ。ただし、そのモデルを通った実装が正しいことまでは保証しない、と同じ報告で区別している。

> 2026年の [Automating Domain-Driven Design](https://arxiv.org/html/2603.26244v1) は、用語整理から構造設計へ進む五段階の LLM 手順を実企業の題材で評価した。初期の成果には有用性があった一方、後段では誤りが累積し、実用に耐えない成果になったと報告している。特定の題材・モデルによる事例研究だが、段階を増やし、前段の文章を次へ渡すだけでは足りないことを示す直接的な材料になる。

> [Google の Go スタイル](https://google.github.io/styleguide/go/decisions)でも、ローカル名は使用時の文脈を反映し、周囲が既に示す情報を繰り返さないようにしている。一方、同じスコープに似た意味の値が並ぶ場合には、区別を名前へ加える。

> [認知的次元の原典](https://www.cl.cam.ac.uk/~afb21/CognitiveDimensions/CDtutorial.pdf)も、抽象化によって変更を容易にすると、抽象を学ぶ負担や隠れた依存が増える、といった交換関係を扱っている。しかも、この枠組み自体を精密な計測器ではなく、設計上の関係を議論する道具として位置付けている。
