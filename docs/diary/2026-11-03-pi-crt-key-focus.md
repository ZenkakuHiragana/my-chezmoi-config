# pi-crt のキー操作: モードの取り違えを UI 設計の原則から考える

## 調べた問題

pi-crt を使っていて、ユーザーは次の三つが気になった。

> - RADIO の検索をクリックした時、テキストボックスが広がるのにそれとは別に `Alt+O` でフォーカスを当てないとキーワードを入力できないのは奇妙に感じる。
> - `Alt+O` でモードを切り替えていることを時々忘れてプロンプトの入力をやろうとして引っかかってしまう。
> - TERM 以外のタブを見ている時にプロンプトの入力をやることがそんなにないことに気づいた。しかしこの入力欄はスラッシュコマンドの入力やショートカットキーの受け付けも兼ねているので、どうするのが快適か判断に迷っている。

AI は最初に、キーの行き先をページの中身と入力欄の中身から決める案を出した。ユーザーは、Pi のショートカットをいつでも使えるようにすることには賛成した。そのうえで、次の二点を挙げ、UI 設計の原則を調べるよう求めた。

> `Esc` はエージェントの応答中に押すと作業が中断されてしまうので誤爆が許されない。
> パネル操作をしている時の視線とパネル操作モードであることを示す位置がズレていることも気づきにくい原因かもしれない。

## pi-crt の今の作り

コミット ad40c0a の時点のコードを読んだ。

- `Alt+O` で「パネル操作」に入り、`Esc` か `Alt+O` で入力欄に戻る。パネル操作中は、`Ctrl+C`、`Alt+H/J/K/L`、`Alt+1`〜`Alt+9`、`PgUp`/`PgDn` 以外のキーをすべてパネルが受け取り、入力欄にも Pi にも渡さない（`shell/input.ts` の `PASS_THROUGH`）。
- RADIO の検索窓に文字が入るのは、パネル操作中で、SEARCH パネルが選ばれているときだけ（`shell/input.ts` の `typingList`）。検索窓をクリックすると、SEARCH パネルの中の「入力中」の印だけが変わる（`panels/radio.ts`）。パネル操作の状態も選ばれたパネルも変わらないので、見た目は入力中なのにキーは入力欄に行く。
- 検索窓に入力している間は、`Ctrl+C` 以外のすべてのキーが検索窓に行く。`Alt+O` でも抜けられない。

原則と照らすと、次の三つがずれていた。

1. パネル操作中も、入力欄がカーソルを描き続ける。入力欄がカーソルを隠すのは、検索窓に入力している間だけ（`shell/editor.ts`）。
2. パネル操作中であることは、入力欄の枠線の `◆ パネル名` と、選ばれたパネルの見出しの色でしか分からない（`shell/editor.ts`、`screen/frame.ts`）。パネルを見ているときは入力欄の枠線が、入力欄を見ているときはパネルの見出しが、視界から外れる。
3. `Esc` が「パネル操作を抜ける」と「Pi の中断」の両方を担う。Pi の `Esc` は、作業中なら中断（`app.interrupt`）、入力欄が空なら 2 回押しで `/tree` を開く（Pi 1.5.0 の `docs/keybindings.md`、`docs/settings.md` の `doubleEscapeAction`。ユーザーの設定は `"tree"`）。

## GUI 一般の原則

### モードの定義

- Larry Tesler はモードを「一定時間続き、特定の対象に結びつかず、入力の解釈を変える以外の役割を持たない UI の状態」と定義した（Wikipedia「Mode (user interface)」、二次）。
- Jef Raskin は『The Humane Interface』（42 ページ）で、ある操作について UI がモードを持つ条件を二つ挙げた。今の状態がユーザーの注意の向いている場所（locus of attention）に無いこと。そして、状態によって同じ操作に違う応答を返すこと（同じ Wikipedia の記事が引用している。書籍の本文は読んでいない）。
- 同じ記事は、ユーザーが自分で状態を変えたときや、操作している場所で状態の変化を強く知らせるときは、ユーザーが状態を把握しているのでモードにならないと説明する（二次）。

ユーザーが挙げた「視線とモード表示の位置のずれ」は、この定義の一つ目の条件にあたる。

### モードの取り違えを減らす方法

Nielsen Norman Group の記事（Laubheimer 2019「Modes in User Interfaces: When They Help and When They Hurt Users」、本文）は、モードの取り違え（mode slip）を減らす方法を次のようにまとめている。

- 今のモードをはっきり見せる。背景や枠の強調、カーソルの形の変化などの強い合図を使う。気を抜いていても気づけるように、合図は少なくとも二つ重ねることを強く勧める。
- 取り違えると作業の損失などの重い結果になる場合は、モードを使わない。概念が似ていても、別々の操作に分ける。
- 押している間だけ効くモード（spring-loaded mode、quasimode）は取り違えを防ぐ。ただし見つけにくく、長く続ける操作には向かない。
- 確認の表示は最後の手段で、多用すると読まずに承認されるようになる。

記事は、1991 年の航空機事故を例に挙げている。同じ入力が、モードによって降下角とも降下率とも解釈され、どちらのモードかが表示から分かりにくかった。

## TUI のキー操作に特有のこと

### キーを受け取る部品は一つで、それを見せる

- Textual では、キーの入力を受け取る部品は同時に一つだけで、その部品が入力のフォーカスを持つ（公式文書「Input」）。文書の例は、フォーカスを持つ部品の枠を別の色で描く。フォーカスできる部品は、既定でクリックするとフォーカスを得る（API 文書の `FOCUS_ON_CLICK`、既定値 `True`）。
- lazygit は、フォーカスのある区画とない区画の枠の色を設定で分ける。その区画で検索している間は、さらに別の色にする（`docs/Config.md` の `activeBorderColor`、`inactiveBorderColor`、`searchingActiveBorderColor`）。
- WCAG 2.4.7（Focus Visible）は、キーボードで操作できる UI に、フォーカスの位置が見える操作のしかたを少なくとも一つ用意することを求める（W3C「Understanding Success Criterion 2.4.7」）。Web の基準だが、目的は「どこがキーを受け取るかが分かること」で、TUI にもそのまま当てはまる。

### 内側のアプリとキーがぶつかる

ターミナル多重化ソフトの Zellij は、自分のキーが内側のエディターなどのキーとぶつかる問題に対して、0.41 で「Unlock-First（non-colliding）」の設定を加えた（公式チュートリアル「Dealing with Colliding Keyboard Shortcuts」、公式文書「Keybinding Presets」）。先に `Ctrl+G` で鍵を開け、そのあとの 1 文字で外側の操作を選ぶ。開発者は、少し慣れれば速く、効率的で、頭の中で一貫した操作になったと書いている。効果を測った研究ではない。

### `Esc` は端末では意味がぶれやすい

端末では、`Esc` キーと、Alt（Meta）の前置きと、ファンクションキーの列の始まりが、どれも同じ `^[` のバイトで届く。tmux は、`^[` のあとに続きが来るかをタイマーで待って区別する（tmux Wiki「Modifier Keys」、既定 500 ミリ秒）。TUI の `Esc` は、もともと意味を取り違えやすいキーである。

## 調査からの判断

AI は、調べた原則から次の案を出した。どれもまだ実装しておらず、pi-crt の設計メモにも書いていない。

1. `Esc` をパネル操作の出入りに使わない。`Esc` はどこでも Pi のものにする。例外は、カーソルが入っている入力中の検索窓を閉じるときだけにする。Pi 自身も選択画面を `Esc` で閉じる。カーソルが目の前にあるので、取り違えにくい。
2. キーの行き先を、見ている場所に二重に出す。パネルがキーを持っている間は、入力欄のカーソルを消し、入力欄を薄く描く。選ばれたパネルは、今までどおり見出しの色と選択中の行の色で示す。
3. Pi のショートカットはいつでも効くようにする。パネルが使わない文字を打つと、その文字は入力欄に入り、キーも入力欄に移る。
4. クリックした場所がキーを受け取る。検索窓をクリックすればそのまま打てる。入力欄をクリックすれば入力欄に戻る。

パネルのキーをすべて Alt との組み合わせにしてモードをなくす案も考えた。しかし、Pi が `Alt+↑`（キューに入れたメッセージを戻す）や `Alt+Enter`（追加のメッセージをキューに入れる）を使っていてぶつかるため、AI は取り下げた。

ユーザーは、残っていた二つの問いに次のように答えた。

- ページを開いたときにキーをどちらに渡すか（AI は、前に出した「TRANSCRIPT の無いページはパネルに渡す」案と、「いつも入力欄に渡す」案を並べた）:

  > 前回の通り、TERM 以外ではパネルの方にキーを渡すのをデフォルトにしたいかな。それで違和感があったら、また戻すことを提案したい。

- 入力中の検索窓だけは `Esc` で閉じてよいか:

  > いいよ。さらに `Tab` と `Alt+O` でもフォーカスを外せるといいかも。今は `Alt+O` で戻ることもできないから。

AI が前に出した案は「TRANSCRIPT が出ていないページ」を基準にしていた。その基準では、TERM の中でも TRANSCRIPT の無い内側のページ（実行ログだけを出す LOG）はパネルにキーを渡す。ユーザーの「TERM 以外」とはこの点が違うと尋ねたところ、ユーザーは TRANSCRIPT を基準にすることを選んだ。

> なるほど。一旦 TRANSCRIPT が出ていないページという条件にしてみるか。実際に使ってみて判断するのが一番分かりやすいから、一旦それで進めてみよう。

## 使ってみて分かったこと

実装して反映したあと、ユーザーは実際に使い、次の点を指摘した。原則だけでは見えず、使って初めて分かったことである。

### 枠の色は別の意味を持っていた

AI は、パネルがキーを持つ間、入力欄の枠を薄い色にした。

> 入力欄が空の時、薄くなるのは枠線だけになる。枠線の色は推論強度を示すものになっているので、紛らわしい。

枠の色はすでに推論の強さを表しており、別の合図に使うと、二つの意味が混ざる。枠の色は変えず、入力欄の文字とカーソルだけを薄字にした。上下の枠線は薄字にしない。

### 打った文字を入力欄に回すと、送信の事故になる

最初の案では、パネルが使わない文字を打つと、その文字が入力欄に入り、キーも入力欄に移った。

> パネルの操作に使うキーでなくてスラッシュコマンドでもないキー（`a` とか）を打ってしまうと入力欄に戻ってしまう。試してないけど、多分そのまま Enter を押すとプロンプト送信になってしまうのではないか？

これは `Esc` の誤爆と同じ種類の事故である。パネルが使わない文字は捨てることにした。例外は、空の入力欄に打った `/`（スラッシュコマンド）と `!`（シェルのコマンド）だけで、この二つは入力欄に入り、キーも入力欄に移る。AI は Pi 1.5.0 の文書（`docs/keybindings.md`、`docs/usage.md`）を調べ、修飾キーなしで操作の始まりになる文字がこの二つだけだと確かめた。`@` はファイルを探す補完だが、プロンプトを書く途中で使うものなので、例外にしなかった。文字が入っている入力欄では、`/` も `!` もコマンドの始まりにならないので捨てる。

> すでにプロンプトが入力されている状態で `/` や `!` を入力しても入力欄にフォーカスが移ってしまう。こういう時はスラッシュコマンドにもコマンド実行モードにもならないので、意図と異なる。

IME を一時的に止める方法は端末の標準には無く、IME で確定した文字も捨てることにした。

### 案内は明るさではなく、知らせる時機で目立たせる

空の入力欄に `alt+o to type` を薄字で出したところ、ユーザーは目立たないと指摘した。AI は案内を明るい色にしたが、ユーザーはそれを退けた。

> alt+o to type が目立たない件はたぶん直し方はそれじゃない。薄い字のままでよくて、他の表現が必要なんだ。

AI は、案内が要るのはプロンプトを打とうとした瞬間だけで、それ以外の時間に案内を明るくするとパネルを見る邪魔になる、と整理した。足りなかったのは案内の明るさではなく、打った文字が捨てられたことの知らせである。ユーザーは次の形を選んだ。

> 空の入力欄を `///` で埋めるのは良さそうだ。文字を捨てた瞬間に光らせるのもよいが、その時は `ALT+O TO TYPE` などと表示を変えてはどうか。入力欄に何か入ってる時はその案内を出す場所がないので、入力ができていないことに気づいた時に改めて表示するという案だ。

- 空の入力欄は薄字のまま斜線（`╱`）で埋め、`alt+o to type` をその中央に置く。斜線は GUI で「使えない欄」を示すのによく使う模様である。
- 文字を捨てたときは、上の枠線のパネル名の場所を `ALT+O TO TYPE` に 1 秒だけ変える。入力欄に文字があって案内を置けないときも、入力できていないことに気づいた時点で案内が出る。

AI は最初、この案内を反転表示にした。ユーザーは強調のしかたが pi-crt のほかの部分とそろっていないと指摘した。

> ここだけ強調の方法が違うのは不自然だな。

pi-crt には、エージェントが別の画面で作業を終えたときにタブを `warning` 色で点滅させる表し方がすでにある。案内もこれにそろえ、同じ時計で点滅させた。

### 端の場合は、使う幅で区切る

監査は、上の枠線が `◆` までで埋まって案内の 1 文字目も置けない幅（入力欄全体で 17 桁ほど）で案内が出ないことを、何度も問題にした。ユーザーは、herdr のペインで作れる最も狭い画面を示して判断した。

> こんな幅にする奴が悪いだろ。たぶん Pi もそこまで想定してないんじゃないの。STANDBY も見えてないし、この状態で表示を成り立たせるのは無理だ。何もする必要がない。

## 理論では決まらないこと

- ページを替えるとキーの行き先が変わる作りが、取り違えを増やすか減らすかは、原則からは決まらない。ユーザーが使ってみて判断する。
- パネルがキーを持っているときに `j`・`k`・`z` など、パネルが使う文字で始まる英字を打つと、1 文字目はパネルの操作になる（ほかの文字は捨てる）。IME の変換候補は、パネル操作中は変な位置に出る。ユーザーはこのままでよいとした。
- 合図を二つ重ねれば取り違えが十分に減るかは、NN/g の推奨であって、測った値ではない。
- Raskin の書籍と、Norman のモードの誤りについての論文は、本文を読んでいない。
