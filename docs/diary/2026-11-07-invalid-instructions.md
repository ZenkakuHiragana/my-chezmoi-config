# 効かない指示がある

最も究極の目的を整理すると、おれは AI にこういうことをやってもらいたいんだ。

1. 調査したことについて、分かりやすい説明をしてもらう
2. 実現したいことについて対話して、技術選定や要件の確定、既知の制約への考慮を効率的に行い、やってもらうことをまとめる
3. 保守可能で高品質なソフトウェアコードを生成してもらう。
4. 実用上起こりうる実装上の欠陥を見つけ、品質のブラッシュアップを行う

1つ目は mechanism-textbook の試作などを通して「AI に人間の認知特性を考慮した資料生成のノウハウを具体的な手順で学ばせる」ということを試している。
2つ目は意外と何も特別な指示をしなくても対話が成立することが多いという印象だ。ただ時々実現可能性を最も左右する制約（提案を実現するには依存ライブラリをフォークしなければならないなど）を説明しないことがあり、問題がないわけではない。現時点では特別な対応は特に行っていない。
3つ目は最近になってやっと software-design スキルを試作した段階だ。何も指示しないと保守可能で高品質なソフトウェアコードは出てこない。「ソフトウェア開発における高品質な設計を実現するための設計ノウハウを具体的な手順で学ばせる」ということを試している。

4つ目が今回の話題だ。上の3つを成り立たせるには、出てきたものを検査してあり得ない状態になっていないことを示してもらわないといけない。そうしないとあり得ないものが実際に出てくるからな。
pi-crt の件なら強調の方法が一貫していないことはデザインセンス的にあり得ないし、
プロンプトの分析結果の計算方法が一貫していないのもあり得ない。
splashsweps の件で言えば通常の命名センスを持っていれば `PaintTarget`, `PaintTargets`, `PaintTarget[]` という3つの型を使い分ける実装はあり得ないし、
`ss.PaintableSurface.BoxFace`, `ss.PaintableSurface.StaticPropFace`, `ss.PaintableSurface.StaticPropBox` という「全く異なる」3つの型が定義されることはあり得ない。
「こういうバカげた命名をするのをやめろ。ナメてんじゃねぇぞ。」とことあるごとに言うことになる。
目的を考えれば絶対にそうはならないのに、目的を伝えたはずなのにそのようになっているんだ。
実際にそうなっているのだからこれは覆せない。

そこで、半年以上前から現在の artifact-review スキルに相当するレビューのためのスキルを作っていったんだ。
コードを生成したエージェントが自分で確認しても「正しいコードを生成しているはずだ」というバイアスがかかって問題点を見つけることができない。
だから別の文脈を持つサブエージェントに成果物と依頼内容だけを見てもらい、問題点を指摘するという方法を採っている。
ちなみに私見だが他の方法は存在しないと思っている。単純な単体テストによる確認はソフトウェアの開発にしか有効ではなく、ソフトウェア開発においても単体テストで仕様を満たしたと示すのは危険である。
この方向を本気で探るならテスト計画と網羅の仕方といったノウハウを学んでもらう必要があるが、試したことはない。
他にはプロパティベーステストや形式手法といったものも考えられるが、深く検討したことはない。もしこういった手法が今の問題に有効に働くことを示せるなら教えてほしいものである。

いずれにしても、実行可能なテストで検証できるのは実行可能な成果物に限られる。
しかし自分は説明資料やスキルの文言なども成果物として要求する。
こういったものは実行不可能なので読んでみてどう思うかというやり方でどうにかするしか思いつかない。

最近になってようやく分かってきたのは、AI には遂行不可能な指示があるということだ。
「根拠を付けろ」と言えばこじつけて、「引用しろ」と言えば突然的外れな引用を付けたことにして話を強引に進めるのだ。
これについて別のエージェントに聞いた。これは的を得た意見だ。

> 効かない指示を並べてみると、かなりの部分が一つの見方でまとめて説明できそうだ。仮説として出す。
>
> **AI は指示の条件を読み違えているんじゃなくて、自分の立場から正しく評価している。ただ、その立場が人間と三つの点で違う。だから、人間の側の量を基準にした条件は、AI の立場で評価すると毎回同じ答えになって、条件として働かない。**
>
> 一つ目は、読むことに負担がかからない点。文脈に載ったものは全部同じように手元にあって、何章も前の図でもすぐ思い出せる。だから「読みにくければ」「前提が手元になければ」はいつも偽になるし、「読者の目線に立て」は何でも知っている読者の目線になる。
>
> 二つ目は、論理的に成り立つことと実際に起きることを区別する物差しを持っていない点。筋の通る文章を作れるものは、成り立っていることになる。だから「起きうるか」「根拠を示せ」「依頼に紐付けろ」「不一致を成立させろ」「解釈が変わるなら」はいつも真になる。逆に「分からなければ質問しろ」はいつも偽になる。もっともらしい答えはいつでも作れるので、分からない状態にならない。
>
> 三つ目は、重さを測る物差しが自分の外にない点。動いているものは全部必要で、成り立つ指摘は全部同じ重さに見える。だから「余計なものを消せ」「不要な主張を控えろ」を出しても何も消えないし、「重箱の隅をつつくな」は守られない。さっききみが言った「影響の大きさを正しく見積もれるならこんな問題は起きていない」は、ここに当たる。
>
> この見方が合っているなら、きみの言う「理解した上でダメ」がそのまま説明できる。AI は規則を暗唱できるし、ちゃんと当てはめてもいる。当てはめた答えが毎回同じになるだけだ。重箱の隅の指摘についても「影響は小さいか」と自分に問うてはいて、AI の立場では「実際に起こせる欠陥なのだから小さくない」という答えになる。効かない指示がやたら多い理由も説明がつく。説明、設計相談、レビューで要る判断は、ほとんどが読み手の負担、普通は起きるかどうか、何が重要かのどれかを基準にしているからだ。10/26 の日記で「得意そうなのに全然ダメ」に入れた要約、調査の代行、壁打ち、読みやすい資料が全部ここに集まっているのも、そう考えると筋が通る。
>
> 反対に、答えが AI の立場の外で決まる条件は、少なくとも毎回同じ答えにはならない。実行した結果、計算した結果（向こうのセッションで記録と食い違わなかった4条件の4番目がこれ）、記録の文面との照合がそうだ。ただ、毎回同じ答えにならないことと、狙いどおりに働くことは別の話になる。mechanism-textbook で「記録の文面で判定し、自分の知識では判定しない」にしたら、今度は一覧にない事柄が全部「読者は知らない」と判定された。あれは立場の違いじゃなく、字面どおりに効きすぎた例だ。
>
> この見方で説明できないものもある。
>
> - **「一回で全部言え」が効かなかった件**：きみが日記に書いたとおり、注意力と予算の問題に見える。
> - **内部 API を使う、警告を抑制して見なかったことにする、テストを書き換えて通す**：これは効かない指示じゃない。人間が当たり前だと思っていて、そもそも書かれていない規範なので、別の種類として分けたほうがいい。

おれが提案したいのは、そういったバイアスまみれの思考でも妥当に判断できる文言 **のみ** でスキルを構成することだ。
そういう考え方を最近の日記や会話では「猛烈な指示」と呼んでいる。
なぜなら人間相手なら「いい感じにやって」といえば済むようなことを実現するために、
学術的知見に裏付けられた論理的に成り立つ演繹のみで手順を構成することになるためにとんでもない文量の指示が出来上がるからだ。

今最も問題になりやすいのは、指摘を鵜呑みにして必ず局所修正に走ってしまう現象だ。
これに対応するために、review-orchestration の指摘の分類処理を変更しようとしている。
検討中の役割分担はこれだ。

- executable-change: 全体の手順オーケストレーション。このスキルだけは他のスキルの名指しをしても良い
  - requirement-contract: 発言を記録し、要件契約という形で固定する。引用以外の要件が入った場合はレビューを行いブラッシュアップする。
    - requirement-reviewer: サブエージェント。要件契約のレビューを行い、余計なことをしないか検証する。
  - software-design: 設計を検討し、命名や分割の検討を行う。レビューを行いブラッシュアップする。
    - review-orchestration: 設計内容のレビューを行う。
  - 実装: 特に実装用スキルは準備していない。計画通りにやる。
    - review-orchestration (2): 実装してできた成果物に対するレビューを行う。

工程ごとにレビューが入る仕組みになっているので、その指摘の受け取り方を見直すことが有効に働くはずだ。
正直他にも問題は山積みだが、mechanism-textbook が割と悪くない感じにまとまった（問題はあるが）のをみると、ここに希望を持ちたいところである。
