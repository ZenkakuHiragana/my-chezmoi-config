# 問題解決を評価する五つの軸

## 目的

AI の問題解決では、何らかの原因候補、事実、差分、懸念、対策を提示したこと自体を前進とみなせない。

- 原因候補を一つ出したことと、原因を突き止めたことは違う。
- 正しい指摘を一つ出したことと、価値ある指摘をしたことは違う。
- 対策を一つ提示したことと、元の問題を解決したことは違う。
- 正しい結論へ到達したことと、合理的な問題解決を行ったことも違う。

本稿は、この差を評価するための五つの軸を定義する。

| 軸 | 短い問い |
| --- | --- |
| **Grounding** | 正しいか |
| **Materiality** | 関係あるか |
| **Integration** | 反映したか |
| **Completion** | 終わらせたか |
| **Economy** | 割に合うか |

五つは順序を持つが、同じ概念ではない。各軸は独立した失敗を検出する。

## 1. Grounding — 正しいか

> **その主張は、対象世界との接触によって支持されているか。**

ここでいう「正しいか」は、最終的な真理を保証できたかという意味ではない。

問題解決の時点で利用可能な、

- コード
- 仕様
- 実行結果
- ログ
- benchmark
- ユーザーの明示意図
- その他の権威ある資料

に接地しているかを見る。

たとえば、

> 普通のソフトウェアなら後方互換性が必要だろう

という一般論は候補にはなるが、対象プロジェクトで後方互換性を要求する根拠にはならない。

一方、信頼できる一次資料を確認し、その記載から妥当に推論した結果、一次資料そのものが誤っていた場合がある。このとき最終結論は誤りでも、問題解決手続きとしての Grounding まで直ちに否定されるわけではない。

Grounding が見るのは、**モデルの事前分布だけで世界を作っていないか**である。

## 2. Materiality — 関係あるか

> **その事実・差・懸念・原因候補は、元の困りごとの説明または解消に実質的な差を作るか。**

真であることと、重要であることは別である。

実コードを調べて完全に正しい差を見つけても、その差が今回の異常、目的、コスト、リスクに何も影響しないなら、問題解決上の価値は低い。

Materiality の接続先は、モデルが現在採用している problem frame ではない。そこを基準にすると、モデルが自分で作った問題を自分で重要だと評価できてしまう。

接続先は、元の依頼で解消したかったものに置く。

たとえば、新しい事実によって、

- 異常の説明が変わる
- 原因候補の順位が変わる
- 実行可能な解法集合が変わる
- 必要な作業が変わる
- 元々問題だったコストやリスクの理解が変わる

なら material である。

Materiality が低い典型例は、**正しいがどうでもよい重箱の隅**である。

## 3. Integration — 反映したか

> **得た material な情報を、問題像・仮説・設計・判断へ反映したか。**

重要な情報を取得できても、それを局所的な発見として報告するだけでは問題解決は進まない。

たとえば、

```text
仮説 A を採用している
↓
新しい事実によって A が反証される
↓
「A は誤りでした」と報告する
↓
A を前提とした設計はそのまま残す
```

なら Integration に失敗している。

同様に、性能問題を調べている最中に、ある API が高コストな再計算を引き起こすことを発見したとしても、

> 注意が必要です

とだけ報告し、原因仮説、設計案、優先順位を再評価しなければ、その発見は問題像へ統合されていない。

情報取得の成果は「新しい事実」だけではない。

必要なら、**更新された問題像**でなければならない。

## 4. Completion — 終わらせたか

> **更新後の問題像に基づいて、元の問い・依頼を本当に閉じたか。**

Integration に成功しても、仕事全体が終わったとは限らない。

たとえば、

```text
原因候補 A を得た
↓
A が症状と material に関係することを確認した
↓
A を問題像へ統合した
```

ところまで正しく進んでも、

- 他の有力な原因候補が残っている
- A が必要条件なのか十分条件なのか分からない
- 修正後に元の症状が消えるか確認していない
- 本来の依頼に含まれる別の完了条件が残っている

なら Completion はまだ満たしていない。

Premature closure は、多くの場合ここで起きる。

```text
原因候補を一つ得た
→ 原因究明を終えたとみなす

現実の差を一つ得た
→ 問題説明を終えたとみなす

もっともらしい対策を一つ作った
→ 問題解決を終えたとみなす
```

モデルが中間成果を生成したことと、元のタスクが閉じたことを区別するための軸が Completion である。

## 5. Economy — 割に合うか

> **得た確からしさや前進量に対して、支払った調査・検証コストは妥当だったか。**

Grounding を強くするために調査を増やし続ければよいわけではない。

情報取得には少なくとも次の費用がある。

- wall-clock time
- tool / API cost
- context consumption
- 無関係な情報による S/N 低下
- 新しい debugging subproblem を作る危険
- 元の問題を見失う危険
- 人間が監督・確認する注意コスト

たとえば、既存コードを数分確認すれば区別できる問題について、専用 probe を設計・実装・debug して長時間を使ったなら、最終結論が正しくても Economy は悪い。

Economy が要求するのは最小調査ではない。

> **重要な判断を変える可能性が高く、誤った場合の損失が大きい点へ、安価な現実接触から順に投資すること**

である。

## 五軸は別々に失敗する

五軸を一つの「品質」の語へ潰すと、失敗箇所が見えなくなる。

| 状態 | 典型的な故障 |
| --- | --- |
| Grounding × | 一般論や prior だけで原因・制約を作る |
| Grounding ○ / Materiality × | 正しいがどうでもよい重箱の隅をつつく |
| Materiality ○ / Integration × | 重要な事実を発見したが、問題像や設計を変えない |
| Integration ○ / Completion × | 問題像は更新したが、中間成果で作業を終える |
| Completion ○ / Economy × | 最終的には解いたが、必要以上の探索・検証コストを払う |

Materiality がない内容を Integration すると、さらに悪い。

どうでもよい論点が要件、設計、レビューへ正式に組み込まれ、元の作業を膨らませるからである。

したがって、五軸は単なるチェックリストではなく、**価値のない作業がどこで価値ある問題解決へ偽装されたかを局所化する座標系**として使える。

## 「本質的な解決」を五軸で捉える

「本質的」という語は曖昧である。

大きな設計変更であること、抽象度が高いこと、原因を深く掘ったこと自体を意味しない。

本稿では、本質的な解決を次のように捉える。

> **元の問題に material な原因・拘束・構造へ grounded に接触し、その意味を問題像と解法へ integration し、元の困りごとを completion まで運び、そのための費用が economy に見合っていること。**

この定義なら、局所的な一行修正でも本質的な場合がある。

逆に、大規模な再設計でも、元の問題に material でなければ本質的ではない。

## 手続き的合理性

五軸を置くと、最終結論の正誤とは別に、問題解決過程そのものを評価できる。

望ましい状態は概ね次のように表せる。

> **重要な結論について、その時点で安く取得できる有力な反証を無視せず、現実から得た根拠に対して妥当に推論し、その結果を問題像へ反映し、元の問いを閉じ、追加調査の限界効用がコストを下回るところで停止する。**

これは正解保証ではない。

P4 のように未知の未知が残る状況では、最終的な正解を常に保証することはできない。

そこで必要になるのが、**納得できる誤り方**である。

結果が誤っていても、

- 当時利用可能な有力な根拠へ接地していた
- 元の問題に material な論点を扱っていた
- 得た事実を問題像へ反映していた
- その時点で合理的な完了条件を満たしていた
- 追加確認の期待価値よりコストが高かった

なら、失敗を局所化できる。

```text
source が誤っていた
観測が例外だった
取得できなかった外部意味論があった
因果推論を誤った
```

といった形で、次の改善対象を特定できる。

逆に、最終的に正解していても、

- 安価な反証を読まなかった
- 無関係な差を大量に調べた
- prior から余計な制約を発明した
- 反証された仮説を理由だけ変えて延命した

のであれば、手続きは合理的ではない。

## 既存の問題解決理論との関係

problem–solution co-evolution、Sensemaking–Coevolution–Implementation Theory、double-loop learning などには、本稿と接続する観点がある。

特に、

- 現在の問題設定を所与として固定しない
- 解決案や観測によって問題像へ戻る
- 局所修正だけでなく、前提や判断基準そのものを再検討する

という点は Integration と強く関係する。

ただし、本稿の五軸はこれらの理論から導出したものではない。本稿では詳細な理論比較を扱わず、五軸を AI の問題解決過程を評価するための実務的な分類として置く。

## 結論

AI が何かを調べ、何かを指摘し、何かを提案したという事実だけでは、その作業に価値があったとは言えない。

問題解決の価値は、少なくとも次の五つを分離して評価する必要がある。

```text
Grounding    正しいか
Materiality  関係あるか
Integration  反映したか
Completion   終わらせたか
Economy      割に合うか
```

この分離によって、premature closure、重箱の隅、本質的でない対策、無駄な探索、反証を活用しない調査を、同じ「なんとなく質が悪い」という評価から切り離して扱える。
