# 問題解決における認識の連続過程

## 目的

AI の問題解決では、「必要な情報が足りない」という一つの表現の下に、性質の異なる複数の問題が混在する。

少なくとも次は別問題である。

1. **何を確認する必要があるかを発見すること**
2. **その確認に必要な根拠を取得すること**
3. **取得した根拠によって問題像を更新すること**
4. **更新後の問題像で元の問いが閉じたか再判定すること**

本稿は、これらを一つの解決法へ統合しない。

目的は、**別々の責務として分離したまま、どの順序と依存関係で接続されるかを示すこと**である。

## 全体像

```text
依頼・現在の作業文脈
        ↓
[1] 認識対象の発見
    何を確認する必要があるか
        ↓
[2] 根拠への接地
    どの情報源を、どの順序で、どう確認するか
        ↓
[3] 問題像の較正
    得た根拠によって、何を維持・撤回・変更するか
        ↓
[4] 完了の再判定
    更新後の問題像で、元の問いは閉じたか
        │
        └──── 未完了・新しい未知が露出 ────→ [1] または [2]
```

矢印は固定された工程順を意味しない。

実装、実験、レビュー、ユーザーとの対話から新しい観測が出れば、どの時点からでも前段へ戻りうる。

この図が示すのは、**後段が前段の責務を代替できない**という依存関係である。

## 1. 認識対象の発見

### 問い

> **今回の判断を変えうるのに、まだ確認対象として取り上げていないものは何か。**

これは P4 の中でも最も難しい部分の一つである。

たとえばコード中に `Vector(...)` が存在しても、

- 毎回 allocation が発生する
- performance concern に効く

という意味論をモデルが知らなければ、「Vector の allocation semantics を調べる」という問い自体が生まれない。

同様に `SetViewPort` の存在を見ても、その API が `ScrW` / `ScrH` の意味まで変えることを知らなければ、その副作用を確認対象として切り出せない。

この段階の失敗は、検索器を改善しても直接は救えない。

検索は、少なくとも何らかの問い、seed、trigger が存在してから始まるからである。

### 出力

この段階が後段へ渡すものは、答えではなく**確認対象または根拠要求の候補**である。

```text
この API の副作用を確認する必要がある
この制約が本当に存在するか確認する必要がある
この挙動が project-specific か framework 固有か区別する必要がある
```

### 未解決性

認識対象の発見を、モデル自身の「知らないことに気づく能力」だけへ依存すると、Unknown Unknown を安定して拾えない。

したがって、外生的な trigger、proactive information delivery、LSP や API 境界からの意味論注入などは、この段階への介入として位置づく。

本稿では具体的な介入方式を扱わない。

## 2. 根拠への接地

### 問い

> **確認対象について、どの根拠を、どの順序で、どの探索方法によって確認するか。**

ここから先は `evidence-retrieval.md` の責務である。

同資料では、根拠収集を少なくとも次の課題へ分けている。

1. 問いを根拠要求へ変換する
2. 根拠要求から探索計画を作る
3. 情報源の性質に合った検索を行う
4. 検索結果を根拠として記録する
5. 複数根拠を採否判断する
6. 情報源と索引を保守する

重要なのは、**認識対象の発見と根拠収集を同一視しないこと**である。

```text
「Vector の allocation semantics を確認すべき」
```

まで出れば、どの情報源をどう探すかは retrieval の問題になる。

しかし、その問い自体が存在しなければ、優れた retrieval system も起動しない。

### 出力

後段へ渡すべきものは、単なる検索結果ではない。

```text
確認した問い
取得した根拠
その根拠が何を権威付けられるか
支持 / 反証 / 未決
不在の場合は探索範囲と停止条件
```

まで区別する必要がある。

## 3. 問題像の較正

### 問い

> **取得した根拠によって、現在の問題像の何を維持し、何を撤回し、何を変更するか。**

正しい情報を得たことは、正しい問題像を得たことを意味しない。

形成済みの問題像が強い場合、新しい根拠を既存フレームへ吸収し、問題像を維持できる。

この故障の機序は `consistency-pressure.md` で扱う。

較正では、少なくとも次の状態差を保つ。

```text
支持された仮説
  → 維持

反証された仮説
  → 捨てる、または修正

新しい拘束
  → 問題像へ統合

未決
  → 未決のまま保持
```

ここで重要なのは、新しい情報を列挙することではない。

必要なら、

- 原因候補の順位を変える
- 調査方向を変える
- 要件を削る
- 設計案を捨てる
- 既存実装を巻き戻す

ところまで伝播させる。

## 4. 完了の再判定

### 問い

> **更新後の問題像に基づいて、元の依頼・困りごと・問いは本当に閉じたか。**

原因候補、重要な事実、対策を一つ得たことは、完了を意味しない。

較正後には、元の問いへ戻る必要がある。

```text
何を解消したかったか
何が分かれば終了だったか
どの受け入れ条件が残っているか
有力な未解決仮説が残っていないか
修正後に元の症状が消えたか
```

この再判定を省くと、premature closure や task abandonment が起きる。

完了の質は `problem-solving-evaluation.md` の **Completion** で評価する。

## 各段階の失敗は代替できない

四つの責務は相互に接続しているが、後段を強化しても前段の失敗を消せない。

| 失敗 | 後段を強化しても残る理由 |
| --- | --- |
| 認識対象を発見しない | 問いがないので retrieval が起動しない |
| 根拠取得を誤る | 更新対象へ渡る事実そのものが誤る |
| 問題像を更新しない | 正しい根拠も既存フレームへ吸収される |
| 完了を再判定しない | 中間成果が本タスク完了へ昇格する |

この分離は、問題を「もっと賢いモデル」「もっと良い検索」「もっと強いレビュー」という一つの解決策へ潰さないために必要である。

## ループとしての性質

この過程は一方向の pipeline ではない。

たとえば、

```text
根拠を取得
→ 予想外の副作用を発見
→ 新しい確認対象が生まれる
→ 別の根拠を取得
→ 原因仮説を変更
→ 実装して観測
→ さらに新しい未知が露出
```

という往復が自然に発生する。

したがって、重要なのは段階を一度ずつ通過することではない。

> **現在どの種類の未解決を扱っているかを混同せず、必要に応じて正しい責務へ戻れること**

である。

## 五軸との関係

`problem-solving-evaluation.md` の五軸は、この連続過程を別の角度から評価する。

```text
Grounding
  主に [2] 根拠への接地を評価する

Materiality
  [1] で発見した論点と、元の問題との関係を評価する

Integration
  [3] 問題像の較正を評価する

Completion
  [4] 完了の再判定を評価する

Economy
  [1]〜[4] 全体の費用対効果を横断評価する
```

この対応は完全な一対一ではない。

たとえば Materiality は根拠取得後にも再評価されるし、Economy は全段階へ作用する。

しかし、**認識プロセスの責務境界**と**問題解決の評価軸**を混同しないための見取り図として有効である。

## 結論

AI の問題解決で「情報が足りない」というとき、少なくとも四つの別問題を区別する必要がある。

```text
何を確認するかを発見する
        ↓
根拠へ接地する
        ↓
問題像を較正する
        ↓
元の問いの完了を再判定する
```

この分離によって、

- retrieval が悪いのか
- そもそも問いが生成されていないのか
- 正しい情報を得たのに問題像へ反映していないのか
- 問題像は更新したが途中で作業を終えたのか

を別々に扱える。

本稿の役割は、この四つを一つの巨大な「問題理解」へまとめることではなく、**相互依存する独立責務として接続すること**である。
