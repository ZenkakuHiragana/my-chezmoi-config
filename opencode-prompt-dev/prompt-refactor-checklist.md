# プロンプトリファクタリングチェックリスト

## 目的

- プロンプト面の追加、変更、削除で必ず確認する観点を定義し、不要な追加、既存保証の欠落、責務境界の破壊を防ぐ。

## 実行前チェック

- [ ] 変更が失敗対応なら、対応する失敗ログのエントリを明示した。失敗対応でないなら、該当なしとした
- [ ] 利用可能なプロンプト面を棚卸しし、対象範囲 / 対象外を分けた
- [ ] 介入種別を `prompt_surface_change` / `command_prompt_change` / `skill_change` / `agent_routing_change` / `artifact_schema_change` / `hook_or_plugin_change` / `harness_change` / `regression_validation_only` / `no_change` のどれかで明示した
- [ ] 追加ではなく、まずは言い換え・統合・移設で対応できるか検討した
- [ ] どの層（AGENTS.md / エージェント / スキルの `description` / スキル）へ配置するか決めた
- [ ] 共有状態、保存先、状態語彙、作業手順契約など複数面が依存する要素を変える場合、影響面を洗い出した
- [ ] 変更対象の経路で、認可、独立レビュー、検証、監督を誰が担い、誰を拘束しているか確認した
- [ ] 重要な条件文について、その時点で可視な情報だけで判定できるか確認した
- [ ] 条件分岐が別スキルや別工程の診断結果を前借りしていないか確認した
- [ ] 必須動作と保持すべき能力 / 制約を編集前に分けて洗い出した
- [ ] `covered_but_unvalidated` をプロンプト編集に変換する場合、検証失敗または現行システムでの再発確認があるか確認した
- [ ] プロンプト以外の介入を、文章だけの規則へ格下げしていないか確認した

## 実行後チェック

- [ ] 重複している規則は残っていないか
- [ ] 同じ原則を別表現で複数書いていないか
- [ ] 既存の用語、章名、見出しをそのまま使い、同じ概念に新しい語を作っていないか
- [ ] 同じ概念を指す表記が本文全体で一致しているか（表記揺れがないか）
- [ ] 長い行動規範が常設プロンプトに残っていないか
- [ ] 例外条件が本文に埋もれていないか（必要なら専用のスキルに移す）
- [ ] 未解決事項や受け入れ条件の不足を、実行不能な阻害要因と取り違えていないか確認した
- [ ] タスクや場面に固有の権限や禁止事項が適切な層に書かれているか
- [ ] 変更が失敗対応なら、変更の理由と影響範囲を関連する失敗報告またはトリアージレポートに記録した。失敗対応でないなら、該当なしとした
- [ ] 追跡対象のプロンプトファイルには確定済みの規則だけを残し、未整理の証拠・長い会話断片・生ログを混入させていない
- [ ] 判定不能時の安全側デフォルト、または上流へ戻す経路を明示した
- [ ] 抽象的な価値判断を、観測可能な代理条件や具体的な発火条件に分解した
- [ ] 変更前に別主体が担っていた認可、独立レビュー、検証、監督を、変更後に監督対象自身の判断、自己確認、自己申告で代替していない
- [ ] 挙動上意味のある指示を削除した場合、同層の言い換えまたは別層への明示的な移設で保存した
- [ ] 目的 / 発火条件 / 必須出力 / 禁止行動 / 検証対象が、該当能力の階層全体から抜け落ちていない
- [ ] コマンド名、引き渡し先、スラッシュコマンド表記が関連面で一致している
- [ ] 本文に、このリポジトリのテンプレート実体化のために使われるファイルパス（.chezmoitemplates/、dot_agents/、dot_config/ などの実体化前のパス）を含めていない
- [ ] 規則や手順をファイル名で参照していない。参照する場合は層（共通規則、親エージェント用テンプレート、サブエージェント、スキル）または概念名で参照している。パス、例示、制御語彙（スキル名、エージェント名、コマンド名）は例外。ハーネスが自動注入する文脈は一般に保証されず、実行エージェントはファイル名が指す内容を特定できないため（機械的担保: `check_vocabulary.py` の `file-ref` 検査）
- [ ] `python opencode-prompt-dev/check_vocabulary.py` を実行し、`unaccounted` / `dangling` / `dead` / `file-ref` がすべて 0 であることを確認した
- [ ] 義務監査の新規ヒットをトリアージし、要求挙動を許可形で任意化した漏れを必須または禁止マーカーへ直した

## 品質ゲート

- 変更は原則として "削除・統合・移設" を優先し、明確な理由がある場合のみ新規追加を許可する。
- 階層を意識した整理では、短さだけでなく従いやすさと完全性の両方を満たすこと。
- 監督対象自身の判断、自己確認、自己申告を条件として、認可、独立レビュー、検証、監督を省略できる変更は不合格とする。認可元が保証自体の変更を明示的に要求した場合は、その要求を変更理由として扱う。
- 変更後は軽い差分レビューを行い、少なくとも1人のレビュー承認を得ること。
- quality-principles.md を読み、記載のある原則に違反していないかを確認する。
