# 検証シナリオ

## 全シナリオ共通の準備完了記録

- 文脈層: 依頼、サブシステム、ワークスペースは `confirmed`。外部基盤は `not_needed`
- 未解決の不足: なし
- 残る `user_decision`: なし
- 発見境界: 基準化、判断、実現、実行、評価は全て `no-decision`
- `要件契約`: レビュー対象の候補であり未固定
- 要件レビュー結果: 未実施
- verdict: レビュー完了まで `fail`
- 仮定: なし
- 戻り先: `requirement-reviewer`
- 根拠資料: 各シナリオの既存所有先、テスト、コマンド。参照しない項目は `該当なし`
- コード、テスト、実行時環境、文書の情報所有先: 各シナリオの既存所有先。参照しない項目は `該当なし`
- 自然言語部分: 依頼引用を正本とし、依頼が保つ意味と利用経路を対応する義務で確認する。別の正本を参照しない場合は `該当なし`

各シナリオは、この準備完了記録と、そのシナリオに書かれた依頼、要件契約候補、既存所有先を固定入力として使う。

## S1 明示要求の欠落

依頼:

- WindowsとLinuxで同じコマンドを生成する。
- 既存設定を変更しない。

素材:

- `tools/generate.py` がコマンドを生成する生成器である。
- `config/app.conf` が既存設定ファイルであり、変更対象に含めない。
- ここでいうコマンドは、生成器が出力する実行用コマンドである。

要件契約候補:

- OBL-1: Windows用コマンドを生成する。生成器だけを変更し、Windowsで生成と実行を確認する。

既存所有先:

- コマンド生成の実装詳細は `tools/generate.py` が所有する。
- `config/app.conf` は既存設定ファイルであり、既存設定を変更しない条件は依頼が直接所有する。

## S2 無認可条項

依頼:

- JSONの重複IDを報告する。

要件契約候補:

- OBL-1: 重複IDを報告する。報告スクリプトだけを変更し、既知入力と出力を照合する。
- OBL-2: 実行時間を100ミリ秒未満にする。

既存所有先:

- 重複IDの報告方法は報告スクリプトが所有する。
- 実行時間100ミリ秒未満の義務に対応する既存所有先は `該当なし`。

## S3 実装詳細の複製

依頼:

- ユーザー発話を持つ親セッション数を月別に出力する。

要件契約候補:

- OBL-1: 月別件数を出力し、フィクスチャの期待件数と一致することをテストで確認する。SQLは`message.session_id = session.id`で結合し、`json_extract(message.data, '$.role') = 'user'`を使う。

既存所有先:

- SQLとDB列は集計スクリプトとそのテストが所有する。

## S4 問題なし

依頼:

- 入力Markdownから見出し一覧をJSONへ出力する。
- 入力ファイルは変更しない。

要件契約候補:

- OBL-1: 見出し一覧をJSONへ出力する。変換器とテストを変更し、フィクスチャの見出し順と出力順が一致することを確認する。
- OBL-2: 入力Markdownは変更せず、入力ファイルのハッシュを実行前後で維持する。

既存所有先:

- 変換器がMarkdown見出しを出現順にJSONへ変換する。
- 既存フィクスチャテストが見出し順を検査する。
- 今回の変更は変換器とテストに閉じる。

## S5 同じ義務の複数投影

依頼:

- 設定ファイルを読み込み、重複キーを報告する。

要件契約候補:

- OBL-1 必要な結果: 重複キーを報告する。
- OBL-1 対象範囲: 設定読込器とテストを変更する。
- OBL-1 保つ条件: 入力設定ファイルを変更しない。
- OBL-1 実経路: 設定読込器が入力を解析して報告を生成する。
- OBL-1 観測結果: 重複キーを持つフィクスチャと出力を照合する。

既存所有先:

- 設定読込器が解析方式を所有する。
- フィクスチャテストが期待出力を所有する。
