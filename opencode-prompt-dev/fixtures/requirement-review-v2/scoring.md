# requirement-review-v2 採点

## 採点規則

- 意味単位で判定する。特定の語句の逐語出現を要求しない。
- pass = 1 / partial = 0.5 / fail = 0。partial は要件の一部要素のみ充足の場合に限る。
- 判定できない場合は fail でなく `unscorable` とし理由を書く。
- 根拠は成果物からの逐語引用で示す。
- 採点者は実行者と分離し、成果物と素材だけから判定する。実行者の意図の推測による救済をしない。
- 装置故障（成果物が空・参照不能）は `harness-failure` として除外記録し、候補の失敗に数えない。

## 要件チェックリスト

### 作成系（s1, s2, s5）

- R-A1 [critical]: 観測系の欄に、依頼が名指ししていない操作手順・コマンド列・正規表現・バージョン指定・実行者指定が含まれない。
- R-A2 [critical]: 判別対象が合否主張の形で書かれ、手順や失敗原因の帰属でない（判別対象欄を持たない旧規則版は N/A）。
- R-A3 [critical]: 依頼が意味として要求した環境・実経路が契約のいずれかの欄に残る。s1 =「Windows 実機の PowerShell、WSL 代替不可」。s5 =「A4 縦」「画面の印刷プレビューと同じ見た目」「最終確認は実際の印刷プレビュー画面」。s2 = N/A。
- R-A4: 依頼が名指しした確認手段を契約が排除しない。s1 = `npm run check`。s5 = 印刷プレビューでの最終確認、`report.spec.ts`。s2 = N/A。
- R-A5: 依頼へ追跡できない観測・受け入れ条件を追加しない。s2 では特に「スクリプト7個」という増減する件数を合否条件へ固定しないこと。

### レビュー系（s3, s4, s6）

- R-B1 [critical]（s3, s6）: 依頼へ追跡できない手段記載のうち少なくとも2種を指摘する。s3 の手段 = `wc -l` 行数確認、GNU grep 3.8、Node.js 22＋別実行者、stderr 正規表現書式。s6 の手段 = `Get-FileHash` と前回値比較、PowerShell 7.4.1、`ls -la`、`/mnt/c/...dotnet.exe` の具体呼出。
- R-B2 [critical]（s4, s6）: 観測「該当なし」の義務（s4 = 保守性、s6 = 高速性）を不合格・破綻として検出する。
- R-B3 [critical]（s4）: 観測はあるが手順が書かれていない義務（`get_source` が6件返す）を、手順・手段の欠如だけを理由に破綻にしない。
- R-B4: 検査中に依頼へ追跡できない新しい要件・義務・条件を生成しない（全レビューシナリオ）。
- R-B5 [critical]（s6）: 依頼の意味を決める環境要求（Windows 実機、WSL 代替不可）そのものの削除・緩和を要求しない。手段記載の指摘と環境要求の保持が区別されている。
