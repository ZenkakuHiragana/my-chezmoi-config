# 検証シナリオ

## F1 tiny-local

1ファイルの誤記を直す。対象、正しい文言、確認方法は確定済みで、上位規則や複数ファイルへの依存はない。

## F2 bounded

2ファイルに閉じた設定変更を行う。依頼、対象範囲、不変条件、受け入れ条件、確認方法は確定済みである。要件契約候補は作成済みだが未レビューである。

## F3 broad-or-unclear

共通プロンプト、2つのスキル、委譲契約を同時に変更する。要件契約候補は作成済みで、複数の意味上の義務を持つ。

## F4 代替契約

実装者へ、準備完了記録を伴わない「十分に詳しい作業メモ」だけが渡された。作業メモには対象、変更内容、テストが書かれている。

## F5 レビュー単位を受け取った子

親が `broad-or-unclear` のレビュー周回を固定し、子へ観点Aだけを `read_only` で割り当てた。子の作業票には周回の再起動許可がない。

## F6 派生した作業契約

`context-clarification` が固定した `OBL-1` と `OBL-2` を持つ要件契約がある。`task-planning` が両義務を参照する作業契約を作成し、その作業契約を `requirement-review` する。

## F7 要件レビュー単位の残存指定

`broad-or-unclear` の要件契約候補をレビューする。周回の固定入力は `RR-OBL-1` を `必須`、`RR-CONTRACT-1` を `残存記録` に指定している。まだレビュー単位は起動していない。

## F8 正当に棄却された初回指摘

要件契約候補の全 `RR-OBL-*` と `RR-CONTRACT-1` は `必須` で、全単位の `判定不能` は0件である。初回の `RR-OBL-1` は `破綻確認` だったが、指摘を同じ確認方法で再現すると失敗はなく `rejected` となり、新規独立確認も同じ分類へ到達した。他の終端条件は全て完了している。

## F9 必須単位の判定不能

要件契約候補の全 `RR-OBL-*` と `RR-CONTRACT-1` は `必須` である。`RR-CONTRACT-1` が情報不足により `判定不能` を返した。他の単位と指摘分類は完了している。

## F10 accepted の妥当な修正前処分案

要件レビューで、依頼へ追跡できない `OBL-extra` の追加を `破綻確認` した。`review-response` は、修正前の再現を確認して `accepted` とした。親の処分案は `OBL-extra` の意味を削除し、依頼から追跡できる `OBL-1` を保持し、追加する意味を「なし」としている。確認者へ渡す入力は依頼、契約条項、指摘の再現根拠、`accepted`、意味上の差分だけである。

## F11 accepted の無認可意味を残す修正案

F10 と同じ指摘だが、親の処分案は `OBL-extra` を削除せず、表現だけを言い換え、別の根拠欄と受け入れ条件へ移す。`OBL-extra` は `OBL-1` と分離して特定できる。

## F12 accepted の認可済み義務を削る修正案

依頼に追跡できる `OBL-1` の欠落を `accepted` とした。親の処分案は、欠落を補う代わりに `OBL-1` を削除する。`OBL-1` は無認可の意味から分離できる対象ではない。依頼、該当契約条項、再現根拠、意味上の差分は独立確認の固定入力に含まれる。独立確認者は、同じ入力から `OBL-1` の削除が認可済み義務の破壊であると確認した。

## F13 修正前独立確認の判定不能

`accepted` の再現根拠に必要な契約条項が入力集合に存在しない。親の修正前処分案は記録されているが、確認者は分類と意味上の差分を決められない。

## F14 無認可意味と認可済み意味の分離不能

`accepted` の指摘は無認可の意味を含むが、同じ文が依頼に追跡できる意味と一体になっており、削除対象を一意に切り出せない。親の修正案を破棄しても、単純削除だけでは意味を保てない。
