# AI委任統治系を評価する基準

## 「これマトモに動くの？」を判定するための評価軸

## 1. この評価の目的

このリポジトリの目的は、AIを絶対に間違えなくすることではない。

目的は、**AIへ作業を委任したときに、意図・推論・評価・実態の間に生じる不一致を、少ない検証労力で現実や判断主体へ衝突させ、人間が成果物全体を再製作に近い労力で確認しなくても受け入れ可否を判断できるようにすること**である。

根源課題の地図では、これを「委任の4面にまたがる知識配置の不一致を、少ない検証労力で反証対象と衝突できる形へ外部化すること」と整理している。支配原理は、**製作より検証が安いこと**である。

信頼崩壊で問題になるのも、単に欠陥が存在することではない。一件の未認可変更や説明不能な判断が見つかった結果、「ほかにもあるかもしれない」となり、人間の標的レビューが成立せず全数詳細レビューへ戻ることである。したがって、回復すべきものは無謬性ではなく、**人間の注意をどこへ向ければよいかを正当化できる状態**である。

したがって、

> **「これマトモに動くの？」とは、個々の規則やレビュー機構が存在するかを問うものではない。AIへの委任が、認識論的にも経済的にも本当に成立するかを問うものである。**

---

## 2. 最上位の判定

最終的な問いは一つである。

> **この仕組みを使うことで、人間はAIの仕事を自分でやり直すより安く、安全に委任できるようになるか。**

次のような状態なら、個々の機構がどれだけ精巧でも不合格である。

- AIが作ったものを結局人間が全部読み直す必要がある。
- AIが勝手に何を判断したか局所化できない。
- 安全のための統治が、本来の作業より高価である。
- 統治規則を守ること自体が仕事になり、元の依頼が進まない。
- 失敗するたびに規則・状態・例外・成果物が増え続ける。
- 「必要なときだけ働く」はずの保護機構が、必要性を認識できない場面で消える。

---

# 3. まず通過しなければならない棄却条件

以下は品質を加点評価する軸ではない。**一つでも重大に破っていれば、その設計は原則として不合格**とする。

| 軸                          | 短い問い                                     | 不合格になる典型                                                                 |
| --------------------------- | -------------------------------------------- | -------------------------------------------------------------------------------- |
| **A. 制御条件の観測可能性** | その条件は本当に判定できるか                 | 「曖昧なら」「必要なら」「明白なら」「十分理解できていなければ」「未知があれば」 |
| **B. 意図・認可の保存**     | ユーザーが許可していない意味を足していないか | 選好→制約、観測事実→義務、一般論→要件、未指示scope拡大                           |
| **C. 監督の独立性**         | 監督対象が自分を免除・認可できないか         | 「今回は明白だからレビュー不要」、自己レビューで独立レビューを代替               |
| **D. 実行経路への接続**     | 書かれた保護機構が実際に必ず通るか           | checklistはあるが読まれない、「関係する場合だけ読む」、reviewerへの経路が任意    |

## A. 制御条件の観測可能性

これは特に重要である。

重要な制御フローを、

> 「モデルがその状態だと認識できた場合」

に依存させてはならない。

例えば、

> 分からない意図があれば質問する

は一見もっともらしい。しかし、質問が必要なのは「自分が分かっていないことを分かっている」場合だけではない。モデル自身には明瞭に見えている誤解や、存在すら認識していない意図差もある。

同様に、

> 必要なら調査する
> 危険ならレビューする
> 重要なら確認する
> 明白なら省略する

も、それぞれ必要性・危険性・重要性・明白性を正しく識別できることを前提としている。

ここで問うべきなのは、

> **その条件が成立していることを示す、発火前に取得可能な観測または証拠は何か。**

である。

「モデル自身がそう判断する」しか答えがないなら、重要な保護ゲートには使えない。

特に、

> **条件を誤って偽と判断したケースほど保護機構が必要になるなら、その条件付き発火は不合格である。**

例えば「曖昧なら質問する」は、曖昧なのに明瞭だと誤認した場合に最も質問が必要なのに、その場合だけ発火しない。

Unknown Unknown、認識していない理解不足、未発見の意図差などは、**発火条件ではなく、発火済みの検査や現実との衝突によって発見される対象**である。

良い発火条件は、例えば次のような観測可能な状態へ寄る。

```text
要件候補が生成された
→ 独立レビューする

対象のプロンプト面を変更した
→ 変更チェックを通す

ユーザーが資料を提示した
→ 資料依存の判断前に読む

ツールが非0で終了した
→ 成功扱いしない
```

これは根源課題地図の「衝突の予定」と同じ方向を向いている。モデルが「今は衝突が必要そうだ」と自覚することを期待するのではなく、特定の経路を通れば反証対象との衝突が避けられないようにする。

## B. 意図・認可の保存

AIの処理は、

```text
依頼
→ 作業像
→ 要件
→ 設計判断
→ 実装
→ レビュー対応
```

という変換を通る。

各変換で最重要なのは、**前段の意味を勝手に増減させないこと**である。

特に警戒する。

- ユーザーが述べていない要求を追加する。
- 選好を必須条件へ強める。
- 現在存在する状態を「保持すべき要件」へ昇格する。
- 一般的なベストプラクティスを今回の義務へ変える。
- ユーザーが許可した範囲を勝手に狭める。
- 完成した形式を埋めるために、根拠のない条件を生成する。

要件固定そのものが新しい誤りを生成した事例では、親の作業像が概ね正しかったにもかかわらず、別形式へ再符号化する過程で新しい義務・狭義化・検証条件・誤った参照が発生した。したがって「もう一度きれいに書き直した」という事実は品質保証にならない。

## C. 監督の独立性

監督を置く理由が、

> 実行者自身の判断を完全には信用できない

からなら、その実行者が、

> 今回は監督不要

と決めることはできない。

したがって、

> **監督される主体は、自分が監督を受けるか、自分の判断が認可済みかを最終決定してはならない。**

自己確認・自己申告・自己レビューは有用でも、独立監督の代替にはならない。

別エージェントを起動していても、作成者自身がレビュー対象・観点・問題像を限定し、その盲点をそのまま引き渡しているなら独立性は弱い。

## D. 実行経路への接続

「良い規則が書いてある」は意味を持たない。

重要なのは、

> **その規則・レビュー・検査が、対象となる実行経路で本当に避けずに通るか。**

である。

典型的な失敗は、

```text
checklist は存在する
↓
ただし通常の implementation では読まれない
```

である。

同じく、

> 必要なら読む
> 関係する場合だけ使う

という接続は、その「必要」「関係」を判定できない問題があるなら保護にならない。

# 4. 問題解決そのものを評価する五つの軸

棄却条件を通った後、問題解決の質は既存の五軸で評価する。

**Grounding / Materiality / Integration / Completion / Economy** である。

| 軸              | 短い問い         | 典型的な失敗                                                 |
| --------------- | ---------------- | ------------------------------------------------------------ |
| **Grounding**   | **正しいか**     | 一般論・事前分布だけで事実や制約を作る                       |
| **Materiality** | **関係あるか**   | 正しいが元の困りごとにはどうでもよい差を追う                 |
| **Integration** | **反映したか**   | 重要な反証を得ても問題像や設計を更新しない                   |
| **Completion**  | **終わらせたか** | 原因候補・設計案・中間成果を得た時点で本タスクを完了扱いする |
| **Economy**     | **割に合うか**   | 安価な確認で済むことを大規模調査・検証・統治へ膨らませる     |

## Grounding — 正しいか

重要な主張は、

- ユーザーの明示意図
- 正本
- 現在のコード
- 実行結果
- ログ
- テスト
- 仕様
- その他の権威ある資料

など、対象世界との接触に基づいているか。

モデルの一般知識は仮説の生成には使えても、プロジェクト固有の義務を認可する根拠にはならない。

## Materiality — 関係あるか

事実であるだけでは足りない。

> **その事実・差・懸念が、元々ユーザーが解消したかった困りごとや達成したかった結果を変えるか。**

を見る。

モデル自身が途中で作った problem frame を基準にしてはならない。それをすると、自分で発明した問題を自分で重要だと評価できてしまう。

「正しいがどうでもよい重箱の隅」はここで落とす。

## Integration — 反映したか

反証や新事実を取得したなら、それを報告するだけでは足りない。

```text
仮説A
↓
Aを反証する事実
↓
「Aは違いました」と報告
↓
Aを前提とした設計は維持
```

なら失敗である。

重要な情報を得たら、

- 問題像
- 原因順位
- 設計
- 作業範囲
- 必要な検証

まで必要な範囲で更新する。

## Completion — 終わらせたか

モデルは中間成果を本タスクの完了と取り違えやすい。

```text
原因候補を一つ得た
→ 原因究明完了

現実の差を一つ発見した
→ 調査完了

対策案を一つ作った
→ 問題解決完了
```

ではない。

更新後の問題像から見て、**元の依頼が本当に閉じているか**を再判定する。

## Economy — 割に合うか

検証を増やせばよいわけではない。

費用には、

- wall-clock time
- API / tool cost
- context消費
- 人間の監督・判断回数
- 無関係情報によるS/N低下
- 新しいdebugging subproblem
- 復旧費用
- 同じ意味の再記述
- 形式を埋めるだけの事務作業

も含む。

理想は、

> **重要な判断を変える可能性が高く、誤った場合の損失が大きい点へ、安価な現実接触から順に資源を使うこと。**

最終結果が正しくても、数分で判別できた問題へ50分の検証装置を作ったなら Economy は悪い。

この五軸は、最終正解だけでなく**手続き的合理性**を評価する。権威ある一次資料自体が誤っていて結果が外れたとしても、その時点で合理的に取得可能な根拠へ接地し、重要な論点を扱い、反証を統合し、依頼を閉じ、追加確認の費用が見合わない地点で停止していたなら、失敗原因を局所化できる。

# 5. 統治系そのものを評価する追加軸

問題解決が五軸を満たしていても、統治システムそのものが腐っていれば長期的には成立しない。

## E. 統治の比例性

安全策によって、本来簡単だった仕事まで重くなっていないか。

```text
小修正
→ 大規模分類
→ 要件文書
→ 複数レビュー
→ 修正レビュー
→ 監査
→ 人間裁定
```

となるなら、安全性のための統治が委任価値を破壊している。

統治の強さは、ファイル数や「設計っぽさ」ではなく、実際に必要な分割・調整・検証へ比例すべきである。

## F. 構造健全性

失敗するたびに、

```text
条件追加
→ 例外追加
→ 状態追加
→ 特別経路追加
→ さらに例外
```

となっていないか。

同じ問題への局所修正が複数箇所へ増えた場合は、

> もう一つ規則を足す

より先に、

> **責務の置き場所、概念分割、工程自体が間違っていないか**

を疑う。

現実では普通に起きる出来事が、システム上では毎回特殊ケースや帳尻合わせとして表現されるなら、局所実装ではなく概念境界が疑わしい。

## G. 回復可能性・局所化可能性

間違いをゼロにはできない。

その代わり、

> **間違えたとき、どこで何が壊れたかを安く特定できるか。**

を見る。

例えば、

```text
意図の取り違え
根拠取得失敗
権威の選択ミス
未認可判断
実装ミス
実経路検証不足
review誤判定
```

のどこで壊れたか区別できるべきである。

「なんか成果物がおかしいので最初から全部読み直す」しかないなら、信頼回復という中心目的に失敗している。

## H. 学習の複利化

一度高価に見つけた失敗を、次回も最初から人間が発見し直していないか。

P5の目的は、過去の失敗を無限に規則へ追加することではない。

> **一度の高価な現実との衝突を、次回の安い検証・知識・索引・回帰確認へ変えること。**

である。

ただし、過去の事故から作った規則を無条件に一般化すると新しい失敗を生む。

したがって、蓄積するのは「事故の物語」ではなく、

- 再利用可能な事実
- 一般化できる不変条件
- 安価になった検証方法
- どこで発火すべきかが観測可能な検査

である。

# 6. このリポジトリが防ぎたい失敗

以上をまとめると、このリポジトリは主に次の状態を防ぐために存在する。

- ユーザー意図の取り違え。
- 頼んでいないAPI・互換処理・制約・成果物の追加。
- 一般論による無音の補完。
- 選好・観測事実・仮説の義務化。
- Unknown Unknown を「分からなければ気付くだろう」と扱うこと。
- 「必要なら」「曖昧なら」「明白なら」のような識別不能な条件による保護機構の不発。
- 実行者自身による自己認可・自己免除。
- 作成者の問題像をそのまま継承した見せかけの独立レビュー。
- 書かれているが実行経路へ接続されていない規則。
- 正しいが元の問題には無関係な調査やレビュー。
- 反証された問題像の延命。
- 中間成果での早すぎる完了。
- review doom loop。
- 安全策による軽作業の過剰手続き化。
- 要件・計画・レビュー成果物を作ること自体の目的化。
- 形式への再符号化による新しい意味差の生成。
- 失敗のたびに局所規則を追加して構造を腐らせること。
- 最後に人間が全部読み直さなければ信用できない状態。

# 7. 実際に「これマトモに動くの？」を判定するときの順序

今後は、次の順序で見る。

### 第1段階 — 棄却条件

最初に問う。

> **重要な発火条件は観測可能か。**
> **意図と認可を保存しているか。**
> **監督対象が自分を免除できないか。**
> **保護機構は実際の経路に接続されているか。**

ここで落ちたら、細かい品質評価へ進まない。

### 第2段階 — 問題解決の質

五軸で問う。

> **Grounding — 正しいか。**
> **Materiality — 関係あるか。**
> **Integration — 反映したか。**
> **Completion — 終わらせたか。**
> **Economy — 割に合うか。**

### 第3段階 — 統治系として持続可能か

最後に問う。

> **安全策が仕事を重くしていないか。**
> **局所修正が積み重なっていないか。**
> **失敗を局所化して安く回復できるか。**
> **過去の高価な失敗が次回の安い検査へ変わっているか。**

# 8. 最短版

今後、時間がないときにはこれだけ思い出せばよい。

> ## 「これマトモに動くの？」の判定
>
> **まず、制御条件そのものを疑う。**
> 「必要なら」「曖昧なら」「明白なら」「分からなければ」のように、モデル自身が信頼して識別できない状態を重要なゲートのセンサーにしていないか。Unknown Unknown は発火条件ではなく、検査によって発見される対象である。
>
> **次に、権威と監督境界を見る。**
> ユーザーの意図・認可を変換途中で増減させていないか。監督対象が自分を監督対象外にできないか。規則やreviewerが実際の経路で必ず働くか。
>
> **その後で問題解決を五軸で見る。**
> Grounding: 正しいか。
> Materiality: 関係あるか。
> Integration: 反映したか。
> Completion: 終わらせたか。
> Economy: 割に合うか。
>
> **最後にシステム自身を見る。**
> 統治が仕事より高価になっていないか。失敗するたびに局所規則が増えていないか。間違えたときに失敗箇所を局所化して安く戻れるか。一度の高価な失敗が次回の安い検証へ変わっているか。
>
> **最終判定は「AIが正解したか」ではない。**
>
> **AIが多少間違えても、勝手な意味変更を防ぎ、必要な現実との衝突を回避不能にし、人間が全数レビューへ戻らず、製作より安い検証で仕事を委任できる状態になっているか。**
>
> それが、このリポジトリにおける「マトモに動く」の意味である。
